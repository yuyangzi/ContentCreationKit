# MCP 生态：从浏览器第二接口到跨行业标准

## 类型标签

`#MCP` `#Agentic-Web` `#WebMCP` `#Agent基础设施` `#技术标准` `#开源治理`

## 主线

2026 年，MCP 从 Anthropic 的单项目开源协议扩展为跨行业标准，同时浏览器开始为 Agent 暴露第二套接口。两条线在同一时间推进：协议层从有状态走向无状态、从 Anthropic 单项目走向 Linux Foundation 跨厂商治理；运行时层从 IDE 插件走向浏览器、云函数、CI/CD、操作系统。Agent 的竞争正在从「哪个模型更聪明」转向「谁能成为 Agent 的运行时和工具协议」。

## 协议层：从开源协议到跨行业标准

2026 年 7 月 28 日，Anthropic 发布 MCP 协议史上最大规模更新（2026-07-28 规范），核心变化包括从有状态到无状态（MCP Server 可运行在 Serverless 和 Edge 基础设施上）、MCP Apps 标准化（可在对话中渲染交互式 UI 组件）、Tasks 扩展标准化（支持不阻塞聊天的长时间运行任务）、企业级认证（原生支持 OAuth 2.0 / OIDC）、MCP Tunnels 研究预览（通过 Cloudflare 打通私有网络内的 MCP Server）。

**关键数据**：

- 月 SDK 下载量突破 4 亿（同比 4 倍增长）
- Claude 已有 950+ MCP 连接器
- 公开 MCP Server 数量 22,311 个（PulseMCP 统计）
- MCP 已移交 Linux Foundation 的 Agentic AI Foundation (AAIF) 治理，OpenAI、Google、Microsoft、AWS 等均为联合治理方

MCP 已从 Anthropic 的单项目开源协议进化为跨行业标准，被 ChatGPT、Claude、Cursor、Gemini、Microsoft Copilot、VS Code 等主流 AI 客户端原生支持。

## 运行时层：浏览器作为 Agent 运行时

AI Agent 正在从聊天产品和 IDE 插件，进入 Web、云函数、CI/CD、操作系统和开发工具链等基础设施层。如果网页、云函数、CI/CD、操作系统都开始为 Agent 暴露结构化接口，软件系统的人机交互方式会发生根本变化：Agent 不再主要依赖模拟点击、解析像素、猜测 DOM 状态来操作软件，而是通过标准化、可授权、可审计的工具调用直接完成任务。

### WebMCP：网页的第二套接口

过去让 Agent 操作网页，常见方案是 Playwright、Puppeteer、Selenium 或各类 RPA 工具——它们能跑，但本质仍是在复刻人的浏览行为，依赖选择器、页面布局、加载时序和脚本注入，遇到动态页面、复杂权限、反自动化机制或 UI 改版就容易变脆。

WebMCP 的想法更激进：它不是让 Agent 更像人一样点按钮，而是让网页把 JavaScript 函数、HTML 表单、DOM 可操作能力以浏览器原生协议暴露给 Agent——网页开始拥有面向智能体的第二套接口。Google 已启动 WebMCP origin trial，让网站可以将 JavaScript 函数和 HTML 表单暴露为浏览器 AI Agent 可调用的结构化工具。

**WebMCP 和 MCP 的关系**：MCP 更像 Agent 访问文件、工具、数据库和外部服务的通用工具协议，而 WebMCP 试图把类似的工具暴露逻辑带进浏览器和网页上下文里。它们不一定是竞争关系，更可能是在不同运行时里解决同一个问题：让 Agent 从「看见界面再猜动作」转向「理解工具再执行任务」。WebMCP 是 MCP 工具体系向浏览器运行时延伸的一个样本。

### 基础设施信号

Agent 进入基础设施层的信号密集出现：

- **Azure Functions**：发布 Serverless Agents Runtime，支持以 `.agent.md` 方式定义 Agent，并连接 MCP 工具服务器——云函数从执行函数变成托管任务型智能体
- **GitLab 19.0**：将 Agentic AI 嵌入 Secrets、Merge Requests、供应链安全等流程——代码、CI、密钥、供应链和操作系统权限都变成运行时问题
- **Windows**：平台安全围绕 AI Agent 展开，微软试图把 Windows 定位成可信 Agent 操作系统

## 安全挑战：标准普及与安全治理的赛跑

MCP Server 数量从数千到 2.2 万，但 OX Security 在 2026 年 4 月披露了所有 MCP SDK 实现中的系统性 RCE 漏洞。当网页开始主动告诉 Agent「我能做什么」，Web 的语义层就不再只服务 SEO、可访问性和人类交互，它还会服务自动任务执行——而「可调用」本身在缺乏授权、回滚、审计机制时会变成风险放大器。

## 关键矛盾

1. **可调用 vs 可审计**：Agent 时代的软件接口必须可授权、可回滚、可审计，否则「可调用」本身就会变成风险放大器
2. **协议治理的开放性**：当 OpenAI、Google、AWS 都坐上 MCP 治理桌，Anthropic 的「先发优势」还能维持多久？开放治理下协议演进方向的分歧与共识
3. **浏览器碎片化**：WebMCP 如果只有 Chrome 支持，它更像生态试验；如果 Firefox、Safari、Edge 跟进，它才可能成为 Agentic Web 的基础标准
4. **自动化行业的再分层**：传统 RPA、爬虫、网页自动化不会立刻消失，但底层点击和脚本能力可能被浏览器原生协议吞掉，价值会转向流程建模、企业权限、安全审计和跨系统编排
5. **标准普及 vs 安全治理**：MCP 生态扩张速度（月下载 4 亿）远快于安全治理成熟度（RCE 漏洞仍在）——赛跑的输赢决定 Agent 基础设施的可信度

## 创作方向建议

1. **MCP 生态全景**（推荐）：从协议演进（Anthropic 单项目 → Linux Foundation 跨厂商治理）到运行时扩展（浏览器/云函数/CI/CD/操作系统），呈现 MCP 如何从一个 API 规范变成 Agent 基础设施——落点在「谁能定义 Agent 与软件世界之间的协议边界」
2. **浏览器的第二接口**：聚焦 WebMCP——为什么「让 Agent 点按钮」不是长期方案，网页如何从人类 UI 变成同时服务人和 Agent 的双接口系统，前端开发是否需要像设计人类 UI 一样为 Agent 设计 DOM 能力
3. **协议治理的开放性命题**：当所有巨头都坐上 MCP 治理桌，开放治理下协议演进的分歧与共识——Anthropic 的先发优势 vs 跨厂商的生态利益
4. **安全与普及的赛跑**：MCP Server 2.2 万个 vs 系统性 RCE 漏洞——标准普及速度与安全治理成熟度的赛跑，决定 Agent 基础设施的可信度
