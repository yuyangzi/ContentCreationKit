# Anthropic 的 1.8 亿行 Rocq 证明：规格才是信任边界

## 类型标签

`#形式化验证` `#Rocq` `#RISC-V` `#OSS-Fuzz` `#内存安全` `#规格缺口` `#Anthropic` `#Theorem`

## 主线

2026 年 10 月 22 日，Anthropic Frontier Red Team 与 Theorem 联合发布一项实验：让 Claude 为 123 个 OSS-Fuzz 开源库、239 个入口点生成形式化证明，证明这些程序在任意小于 64 MB 的输入下都不会崩。产出的证明约 1.8 亿行 Rocq，典型一份证明 60 万行，对应中位长度 1.8 万条 RISC-V 指令的二进制。

Hacker News 讨论 473 分、312 条评论。争论的焦点不是「证明对不对」，而是「证明的是不是你想要的东西」。

这件事真正的价值不在证明规模，而在它暴露了 AI 时代软件信任链的新结构：当证明代码量大到无人能逐行审阅，人类唯一还能审的，只剩规格（spec）、语义模型和检查器。

## 它到底证了什么

先把范围说清楚，否则很容易被「零崩溃」误导。

证明对象是编译后的 RISC-V 二进制，不是源码。证明性质是：对任意小于 64 MB 的输入、任意被建模的 Linux 响应和内存布局，程序都会正常退出，不触发内存安全错误，也不让断言失败。前提假设是：单线程、静态链接、固定内存预算、RISC-V CPU、Linux。

规格从哪来？不是人写的。Anthropic 把项目原有的 fuzz test 机械转换为规格：「这个 fuzz test 永远不会崩」。fuzz test 原本是开发者写的入口点，任何让程序崩掉的输入都算 bug；现在把「不崩」变成定理，让证明器去覆盖所有输入，而不是靠随机变异碰运气。

这一步是整件事的关键。它绕开了形式化验证最大的拦路虎——写规格。代价是：你能证明的性质，被限制在「原测试所表达的性质」之内。

## 为什么证明能不用人审

1.8 亿行代码没人读得完。Anthropic 的论证是：不需要读。Rocq 内核会检查证明是否满足规格，所以开发者只需信任三样东西：

1. RISC-V 指令与 Linux 进程的形式语义模型
2. 被证明的定理陈述本身
3. Rocq 证明检查器

可信基从「每一行业务代码」缩小到「三个组件」，而且这三个组件不随项目数量增长。这是形式化验证的经济学：一次性把信任成本集中，之后每个新项目都复用。

但「不用人审」不等于「没有风险」。如果语义模型漏了一种内存布局，如果定理陈述写窄了，如果 Rocq 内核有 bug，证明依然会过。Anthropic 自己在文中写明：formally verified ≠ bug-free。

## 证明过程中挖出的 bug

这是最能说服工程师的部分。为了完成证明，Claude 必须排除所有可达的崩溃路径，于是它找到了 fuzzer 很难碰到的输入：

- 一个解压器里的计数器下溢导致越界写，只在约 20 MB、且内存布局极特殊的输入上触发
- 一个图像解码器的越界读，需要 64 MB 输入和超过 2 GB 内存
- 一个库的越界读，需要对同一文件的两个句柄按特定顺序调用
- libexpat 中 CVE-2026-56132 的重新发现，需要深度嵌套输入
- 一个从不崩溃的逻辑 bug：限制应用可加载哪些文件的功能，并不总是生效

差别在搜索方式。fuzzer 通常把输入限制在 1 MB 以内，靠覆盖率引导；证明要求覆盖所有输入，所以会走到 fuzzer 永远到不了的角落。

另一个值得记的细节：为了证明 cpp-httplib 不崩，Claude 必须排除 `std::set` 析构函数递归过深导致的栈溢出，进而要证明 libc++ 红黑树的重平衡确实把树高控制在 O(log n)——在机器码层面。

## 成本账

形式化验证过去只在空客航电这类场景可用，原因是人力：seL4 内核实现 2 人年，验证 20 人年。现在瓶颈换成了 token。

Anthropic 公布了两组效率数据：

- 36 个真实 OSS-Fuzz 小任务上，Opus 5.5 用比 Opus 5 少约 40% 的 token 证完一半任务
- 允许 agent 共享工作区、互相拷贝证明后，比单独工作少用 17% 的 token；34 个完成的任务里有 30 个比单干更便宜，另有 2 个单干根本没证完

证明像软件一样可以复用。大部分证明都在处理每个程序都有的部分——C 运行时初始化、AddressSanitizer——所以不同程序的证明高度重叠。这也是 Mathlib 能靠 700 多名贡献者堆到近 30 万条定理的原因。

## 几个延伸实验

同一篇里还有三条支线，信息密度不低：

- **zlib**：让 Claude 为 RFC 1950 写形式规格，再证明 Linux 内核里的 zlib 实现符合该规格。这次直接在 x86 二进制上做，用的是 Claude 生成并大量测试过的 x86 语义
- **Python 解释器**：用 Rust 写一个 Python 大子集的解释器，用 Verus 证明它符合论文里的 CPython 语义；再用 170 万个随机生成的 Python 程序做经验对比，99.95% 行为一致
- **PDF 阅读器**：验证一个简单安全性质时，一周内找到的安全 bug 数量，相当于平时一年的报告量

## 关键矛盾

1. **规格缺口没有消失，只是被挪走了**。测试转规格解决了「写不出规格」，但没解决「规格是否表达意图」。证完「这个 fuzz test 不崩」，不等于「这个库没有安全问题」
2. **可信基变小，但没有变没**。RISC-V 与 Linux 语义模型由 Theorem 提供，Rocq 内核是第三方，定理陈述由模型生成。三者任何一处出错，结论都不成立
3. **适用范围窄得诚实**。单线程、静态链接、固定内存、RISC-V、Linux——真实生产软件大量不满足。扩展到多线程、多架构、动态链接，是另一个量级的工作
4. **成本仍然高**。数百亿 token 级别的证明开销，目前只对「被广泛复用、值得一次性投入」的基础库划算。普通业务代码用不起
5. **「AI 自己修 bug 再自己证」的循环**。Claude 发现 bug 后直接打补丁、重新生成规格、继续证明。效率很高，但谁来审这些补丁？证明保证的是补丁后的代码符合规格，不是补丁本身是正确修法
6. **与安全叙事的张力**。Anthropic 的开场白是「AI 现在很容易找到并利用 bug」，解法是「用 AI 证明没有 bug」。攻防两侧用的是同一种能力，防守方要赢，必须比攻击方更快、更便宜

## 创作方向建议

### 方向 A：当证明量大到无人能读，人还能审什么（推荐）

主线是信任链的收缩：从审代码，到审规格，到审语义模型和检查器。核心判断——AI 把「写证明」的成本打下来了，却把「写对规格」变成了唯一的瓶颈。可与 OpenAI 的 ETH Lean 证明对照：数学侧证的是陈述，代码侧证的是测试转出来的规格，两者卡在同一条边界上。

### 方向 B：fuzz test 的终结？

技术向，面向测试与安全工程师。讲 fuzz 的极限（输入空间无限、覆盖率引导有偏、1 MB 上限），以及「把 fuzz test 变成定理」这个转换为什么成立。落点可以是：fuzz 证明「跑过的没崩」，形式化证明「跑不到的也不崩」。

### 方向 C：token 作为验证成本

从 40% 与 17% 两组效率数据切入，算一笔账：证明一个库要多少 token、复用能省多少、什么规模的库才值得证。适合喜欢算账的读者，也能接上「AI 账单」系列的计量视角。
