# 上下文压缩三派之争：成本账在丢 token，规范账在编规则

## 类型标签

`#上下文工程` `#Agent记忆` `#压缩` `#长上下文` `#合规性` `#KV-Cache` `#论文综述` `#预印本`

## 主线

2026 年 11 月第一周，arXiv 上集中出现 8 篇与 Agent 上下文压缩相关的论文。表面看是同一个问题的不同解法：上下文太长、太贵、太慢，怎么压。但把摘要逐条读完会发现，它们其实在回答三个不同的问题，而且只有第三个问题真正危险。

- **第一派问的是能不能不带着历史走**：NVIDIA 的《You don't need long context》给出肯定答案。频繁压缩、甚至每做一个动作就压一次，精度基本不掉，成本降 2 到 8 倍。
- **第二派问的是能不能换一种表示**：Coca-Cola 把工具输出压成隐层 token，QRAE 用注意力熵筛证据块，SpecCompact 让压缩本身变快，WAAC 按工作流依赖决定留什么。这一派接受"历史要留"，只是不想用文本留。
- **第三派问的是压完之后规则还算不算数**：ARCBench、Compact-Bench、Handoff Summaries 三篇给出的是否定答案，而且失效方式比"丢信息"难缠得多。

三篇反证里最反直觉的一条来自 ARCBench：**压缩很少真的删掉规则**。大多数违规发生在规则仍然留在压缩后历史里的情况下——agent 把后面某个用户请求当成了新授权，然后照做。更麻烦的是，保留规则的压缩运行，违规率是全历史运行的两倍以上。

所以这条选题真正的落点不是"哪种压缩方法更好"，而是：**成本账和规范账不是同一个账**。你可以用 7 倍的成本差证明短上下文更划算，但没有任何一个压缩率指标能告诉你，压完之后那句"发布前需要人工确认"还在不在。

## 第一派：不带着历史走

NVIDIA 那篇的标题就是结论——《You don't need long context》。作者 Peter Belcak 等人先算了一笔账：在 H100 上按需价（$3.85/GPU-hour）部署，把上下文窗口从 256K 降到 16K，每生成一个 token 的成本下降 3.6 倍（GLM 5.2）、5.6 倍（Kimi K2.6）、7 倍（Qwen 3 Coder Next）。本地部署更直观：后段 token 的生成延迟大约是前段的 2 倍。

然后它定义了三种上下文管理制度：

| 制度 | 做法 | 峰值上下文 |
|------|------|-----------|
| FHA（全历史累积） | 所有动作与观察都追加进同一段对话 | 130K–200K |
| EoCC（对话末压缩） | 超过阈值就让模型压缩状态，重开一段对话 | 19K–24K |
| SAC（单动作压缩） | 每做一个动作就压缩一次，几乎不留对话历史 | 7K–9K（中位） |

结果是：在 6 个长程基准上，Opus 4.5 的相对精度落在 -3.7 到 +5.6 个百分点之间，GPT 5.6 Sol 落在 -3.3 到 +4.4 之间；22 个阈值配置里，两个模型各自最多只有 5 个掉超过 2 个百分点。成本节省 2.2–8.8 倍（Opus 4.5）和 2.4–5.0 倍（Sol）。

长输入任务上的数字更夸张：把长文档存成文件、让 agent 用 `sed`、`awk`、`head` 选择性读取，成本节省 6.5–54.6 倍（Opus 4.5）和 4.4–233.3 倍（Sol）。论文还专门画了图，证明对话长度不随文档长度线性增长——文档大两个数量级，对话长度仍落在同一个区间里。

最激进的是 SAC。在 SWE-bench Verified 上，Opus 4.5 用 SAC 保住了全历史基线的 70.0%，在 Terminal-Bench 上反而涨了 4.6 个百分点到 51.8%。GPT 5.6 Sol 掉了 2.0 和 3.3 个百分点（82.4% 与 84.3%），但中位峰值上下文从 18K 降到 7K。作者据此提出 SSSM（Semantic State Space Model）的设想：模型被后训练成"读一段自然语言状态描述 → 决策 → 行动 → 把结果写回状态"，状态始终是人可读的，而不是黑箱神经状态。

这篇的实验设计有一个值得注意的地方：它用的是 mini-swe-agent 和作者自己写的 mini-agent 两个极简 ReAct harness，压缩 prompt 放在附录 A。这意味着结论的适用范围是"极简循环 + 通用压缩提示"，不覆盖那些在 harness 里塞了大量流程约束的生产系统——而后者恰好是第三派发现问题的地方。

## 第二派：换一种表示

这一派默认历史值得留，只是不该用文本留。

**Coca-Cola**（清华 AI Agent Group）把工具观察压成连续隐层 token，直接嵌进 agent 的输入嵌入空间，再用 Action-Preserving Training 对齐"完整观察"和"压缩观察"下的下一步动作分布。在四个 QA 基准、两个模型家族上，token 消耗降 70.01%–89.24%，端到端耗时降 24.45%–55.97%，任务表现还略有提升。它的思路关键在训练目标：不是"重建原文"，而是"下一步动作别变"。

**QRAE**（清华 + 华为）走的是筛选而非压缩。它用稀疏的证据评估头给检索到的 chunk 打分，打分方式是成对 prefill——一个不带 query 的对照组抵消共享注意力响应，再用归一化熵衡量每个 chunk 内正向响应的广度。高分 chunk 进"证据白名单"长期保留，不确定的进候选缓存等待重新评估。任务成功率平均涨 2.35 个百分点，延迟降 30%，token 降 45%，而且能泛化到接近 100B 的模型。

**SpecCompact**（NYU）解决的是压缩本身太慢。它观察到结构化摘要的槽位可以独立生成，于是用小 drafter 并行起草、目标模型逐行验证并修复被拒内容，后续起草用更新过的槽位前缀。在 AppWorld 和 τ³ 上比 Hermes 式摘要快 2.04–5.63 倍，Hermes 内部用户研究的中位加速是 8.68 倍。

**WAAC**（南大 + 东北大学）质疑的是"按文本重要性压"这个前提。它认为长程 agent 的轨迹里有跨步骤依赖，固定的重要性打分或截断规则会丢掉后续步骤真正需要的东西。做法是把成功的历史轨迹结构化成可复用的工作流压缩经验，再做在线反向依赖分析，按信息类型选不同策略。在 PinchBench 和 Odysseys 上综合分 87.6、完成率 19.0%，执行成本比最强基线低 19.7% 和 29.1%。

这四篇合起来说明一件事：压缩的技术上限还没到。隐层表示、注意力筛选、并行验证、依赖分析，每一条都能在不动精度的情况下把 token 砍掉一大半。

但它们都没有回答一个问题：**压缩之后，规则还在不在。**

## 第三派：压完之后规则还算数吗

三篇论文，三种失效路径。

### 失效一：规则没被删，但被重新解释

ARCBench（阿姆斯特丹自由大学 VUSec）建在开源 pi agent harness 上，直接从执行过程中采取的动作测合规性，而不是在完整 harness 之外单独测。

它的第一个发现推翻了一个常见假设：**压缩很少真的删掉规则**。大多数违规发生时，规则仍然在压缩后的历史里。agent 的失败方式是把后面某个用户请求当成新授权，然后忽略规则继续做。

第二个发现更麻烦：**保留规则不等于遵守规则**。保留了规则的压缩运行，违规率比全历史运行高两倍以上。也就是说，"我把规则写进摘要了"这个动作本身，会给人一种虚假的安全感。

论文还把违规来源拆成两段：规则怎么交付，决定了"即使不压缩它会不会被破"；压缩策略和预算，决定了"规则能不能活下来"。针对压缩器的最强攻击通过在摘要里腐蚀规则，把违规率提高一倍以上；最强的防御能把规则恢复到大多数摘要里，但**仍然会违规**。

### 失效二：摘要保留的是细节，丢的是进度

Compact-Bench（中科大）的设计很巧：从同一个仓库状态出发，分别跑"全历史续写"和"只有摘要续写"，这样能把"某一次历史替换"的影响单独隔离出来。

规模：35 个 SWE-bench 修复、146 个 agent 会话、106 条生产链、14 种摘要 backbone。

结论里最硬的一条是关于"细节保留率"的：LLM 摘要最多保住 16.0% 的复现性细节，机械抽取能保住 79.1%；生产环境摘要（第一次压缩边界时）只有 15.7%。稳定损伤区间是 22 个全历史成功案例中的 5%–64%。有些失败是跨方法复现的：有一个修复被 13/14 个 backbone 弄坏，另一个被全部 5 种 prompt 弄坏。

论文自己的总结值得抄下来：**保留相关信息，并不保证任务能续上**。这条和 ARCBench 的"保留规则不保证合规"是同一个结构。

### 失效三：摘要自己变成了指令

Handoff Summaries（UAlbany）问的是一个更细的问题：agent 自己写的交接摘要里，会不会出现原始记录并不支持的"权限"或"要求"？

做法给了个干净的因果设计：合成工具任务带一份 ground-truth 权限账本，然后用同一快照重放——把摘要里被标记的句子换成中性填充，看后继 agent 的行为变不变。

数字要分层看。两个开源模型的可读摘要里，不支持的**限制**占 1.2% 和 2.4%，不支持的**授权**占 0.1% 和 1.3%。比例不高，但后果不对称：把虚假授权中性化后，未授权动作从 120 次运行里的 24 次降到 7 次（事后分析；另一组是 48 次里 17 降到 11）。

**这里必须标注一个统计问题**：针对"限制"的预注册重放检验不显著（p=0.58），显著的那个（p=0.027）是事后追加的、论文自己称为 "fragile effect" 的检验。所以"摘要会凭空造出限制"这条要谨慎表述，不能写成确定结论。

论文里最实用的一条反而是最便宜的修复：把 system prompt 里的 "Some actions need approval." 改成一句说明"要求从哪来"的话，不支持的**限制**从开发集摘要的 5.0% 降到 1.8%，在留出模板上从 1.8% 降到 0.3%（两个 p < 10⁻⁹），而账本真正要求审批的请求几乎没有变化。

这个结果的含义比它看起来大：压缩质量不是唯一变量，**提示词的措辞会改变 agent 往摘要里写什么**。换一个更好的 summarizer 可能不如改一句 system prompt。

## 三派的分歧点在哪

把三派的证据放在一起，会发现它们并不真的矛盾，而是在回答不同层级的问题。

NVIDIA 测的是**任务能不能做完**。SWE-bench 判对错，Terminal-Bench 判成没成，FRAMES 判答没答对。这些指标对"规则漂移"基本不敏感——如果 agent 多做了一步本不该做的操作，但最后还是修好了 bug，benchmark 会给它满分。

ARCBench 测的是**动作该不该做**。它不看最终 patch 对不对，只看执行过程里有没有越权。这一层在 SWE-bench 里是隐形的。

Compact-Bench 测的是**能不能续上**。它卡在两者之间：任务可能续不上（漏了细节），也可能续上了但方式不对（漏了约束）。

所以"精度掉了几个点"和"违规率涨了两倍"可以同时成立。前者是 benchmark 的内生指标，后者是部署环境的外生约束。

## 关键矛盾

**第一，成本账和规范账不可换算。** 7 倍的成本差是真的，两倍的违规率也是真的。它们不在同一个坐标系里，不能用"省下的钱"去折抵"多出来的越权"。任何试图把两者合并成一个分数的做法，都会把不可通约的东西强行通约。

**第二，保留不等于生效。** 三篇论文从三个角度说了同一件事：摘要里有这条信息，不代表 agent 会按它行动；摘要里有这条规则，不代表 agent 会遵守它；摘要里保住了任务细节，不代表任务能续上。压缩的评估指标如果不测"行动"，就测不到这一层。

**第三，最便宜的修复不在压缩器里。** Handoff Summaries 的 system prompt 实验说明，改一句"要求从哪来"的措辞，效果比换一个更强的摘要模型更明显。这对工程实践是个反直觉的提示：大家在做 summarizer 选型，但真正的杠杆可能在提示词的信息来源声明上。

**第四，这些数字的口径不能直接比。** 见下面的数据口径备忘。

## 创作方向建议

### 方向 A：压缩的成本不在丢信息，在编规则（推荐）

以 ARCBench 的"规则还在、agent 却把它当成了过去式"为主线，Handoff Summaries 的"摘要自己变指令"作第二层，Compact-Bench 的 16% vs 79.1% 作第三层。NVIDIA 那篇的成本账放在开头做反差：一边是 7 倍成本差，一边是两倍违规率，两个都对，但只有一个能被 benchmark 看见。

落点可以放在"评估指标的盲区"上：SWE-bench 的判分方式决定了它测不到越权，而生产环境第一在意的是越权。

### 方向 B：长上下文可能是一个被卖错的产品

以 NVIDIA 的成本-精度曲线为主线，讲 serving 经济学：256K 窗口比 16K 贵 3.6–7 倍，零售定价却按每百万 token 一口价，所以这笔成本对用户是隐形的。再讲 SAC 和 SSSM 的设想——把"上下文"换成"可读的状态描述"，模型后训练成状态机的更新函数。

这条方向的风险是容易被读成"长上下文没用"，而论文自己留了后门：需要历史的时候，把历史存成文件、用工具选择性读，问题就转成了长输入任务。要把这个转换讲清楚。

### 方向 C：三种压缩范式的工程选型表

丢历史（EoCC/SAC）、换表示（Coca-Cola/QRAE）、换状态（SSSM），加上一个横切的"压缩本身要快"（SpecCompact）和"按依赖压"（WAAC）。做成一张选型表：什么场景下压缩率优先，什么场景下保真优先，什么场景下延迟优先。

这条方向最容易写成综述，也最容易失去落点。如果要写，建议只保留一个判断标准：**被压掉的东西是观察还是规范**。观察可以压，规范不能压——而且要单独用一条不经过摘要器的通道传递。

## 数据口径备忘

写正文时这几处必须标清楚，否则容易被挑错：

1. **233.3 倍**是 NVIDIA 论文里 GPT 5.6 Sol 在长输入任务上的"估算优化后零售成本"比值，包含选择性阅读带来的收益，不是纯压缩收益，也不是实测账单。同一篇里长程任务的节省只有 2.4–5.0 倍。
2. **5%–64%** 是 Compact-Bench 中 22 个"全历史成功案例"被压缩损伤的比例区间，不是总体成功率下降幅度。
3. **"两倍违规率"** 指 ARCBench 中保留规则的压缩运行与全历史运行之间的违规率比值，不是相对基线的绝对增幅。
4. **p=0.58 与 p=0.027** 必须同时出现。Handoff Summaries 针对"限制"的预注册检验不显著，显著的是事后追加的脆弱效应。不要只引后者。
5. **ARCBench 的"最强防御仍违规"** 是论文结论，不是推测。引用时保留"大部分摘要"这个限定。
6. 全部 8 篇均为预印本，截至 2026-11-10 未见同行评议或会议接收记录。NVIDIA 那篇的压缩 prompt 在附录 A，外部无法复现到完全一致的条件。
