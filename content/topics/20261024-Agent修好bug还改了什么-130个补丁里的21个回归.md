# Agent 修好了 bug，还改了什么：130 个补丁里的 21 个回归

## 类型标签

`#Agent评测` `#代码审查` `#回归测试` `#供应链安全` `#PatchThePlanet` `#TrailOfBits`

## 主线

2026 年 10 月 21 日，Trail of Bits 发布两个 Agent 插件 patching-bugs 和 regression-hunt，同时公布了一组来自 Patch the Planet 的实测：130 多个已合并 PR 里确认 21 个回归，其中 16 个功能回归、1 个性能回归、4 个构建/测试回归，没有破坏安全防护。

这组数字的价值不在「16% 的回归率」，而在它把 Agent 修 bug 的评估拆成了两件事：修好一个 bug，和证明没有改坏别的东西。前者看通过率，后者看证据链。Trail of Bits 的做法是给每个结论配一个可执行的 PoC，再用三角验证排除「碰巧通过」。

同一批数据里还有一个更刺眼的数字：单轮扫描出 58 个候选回归，最终确认 21 个，精确率约 36%。也就是说，Agent 报出来的东西大部分要人来筛。这让「Agent 自动修漏洞」的叙事从产能问题变成了信噪比问题。

## 三个数字

- **21 / 130+**：已合并 PR 中的确认回归数，约 16%
- **21 / 58**：单轮扫描的候选里，最终确认的比例，约 36% 精确率
- **25%**：regression-hunt 相比 baseline Codex 的误报下降，95% 置信区间 14%–38%

三个数字要一起看。只引 16% 会显得 Agent 很危险；只引 25% 会显得工具很有效。合起来才是完整判断：Agent 会引入回归，也会抓到回归，但抓的时候噪声仍然很大。

## 为什么「修好」不等于「没改坏」

Trail of Bits 对回归的定义很窄：一次变更引入的新缺陷，破坏的是此前正确且受支持的行为，而且这条路径真实用户或攻击者能够到达。

这个定义排除了四类东西：

- 误报
- 不完整的修复
- 潜伏已久的 bug
- 本来就存在的问题

只有全部通过，才计为回归。这套判定被写进 regression-hunt 的「adjudication agent」步骤，举证责任在 Agent 一侧，不在人一侧。

## regression-hunt 的四步

1. **枚举**：沿 diff 追踪调用方，一直到真实接口，列出候选回归
2. **复现**：在真实部署上复现每个候选，不是单元测试，是构建并运行起来的实例
3. **重放**：换一个 fresh-context agent，在同一部署上重放 PoC
4. **裁决**：检查前面的证据是否满足回归的定义

第三步是关键。同一个 Agent 复现、同一个 Agent 判定，会形成自评闭环。换一个上下文重放，至少能排除「上一次的推理污染了这一次的判断」。

## patching-bugs 的 three-arm proof

这是整套方法里最值得抄的一个设计。同一个复现脚本跑三次：

- 原始代码必须失败
- 打上补丁必须通过
- 完整回滚补丁必须再次失败

第三臂是重点。只验证「打完补丁通过」，无法排除是环境变化或测试改动让结果变绿；把补丁撤掉后 bug 重新出现，才能证明是补丁本身起的作用。

配套的还有两条：

- **不变量修复**：优先修被违反的安全不变量，而不是修这一个具体 bug，让补丁覆盖同类变体
- **强制回归检查**：patching-bugs 必须调用 regression-hunt，补丁和检查走同一条流水线

## 误报下降的代价

regression-hunt 的误报比 baseline 少 25%，但博客主动写了一个 tradeoff：严格的证据要求会让一些已知回归停留在「borderline」——插件识别到了可能的问题，但没收集到足够证据，于是没有确认为回归。

也就是说，误报下降不是免费的，代价是漏报。Trail of Bits 的下一步是改证据收集策略，而不是放宽判定标准。这个取舍值得单独写一段：在安全场景里，漏报和误报的成本不对称，工具设计必须明确站在哪一边。

## 把威胁模型塞进每一步

两个插件都依赖项目自己提供的两份文件：

- **`THREAT_MODEL.md`**：哪些资产被攻陷才算问题、信任边界在哪、支持哪些配置、什么算漏洞、什么算回归、一份有效的 bug 报告需要什么证据
- **`PATCHING_GUIDELINES.md` 或 `AGENTS.md`**：怎么构建和测试、补丁多大、改在哪、怎么呈现变更、回归测试要证明什么

regression-hunt 的做法是把威胁模型作为全局上下文，传给每一个 agentic step，要求每一步在得出结论前对照一遍。这个设计比「在 prompt 里写一句注意安全」具体得多：它把安全假设变成了可引用、可检查的文件。

GPAC 已经按这个格式提交了威胁模型和项目专属的 patching skill；liboqs 和 validator.js 也发布了威胁模型。这些是可以直接点开看的样例。

## 背景：Patch the Planet

这是 Trail of Bits 与 OpenAI 的联合项目，为广泛使用的开源项目共同编写安全补丁，已经合入数百个。两个插件的方法论来自两处：所有已合并补丁的复盘，以及工程师使用 Codex 的数千次会话。

这个背景解释了一个容易被忽略的点：21 个回归是「Trail of Bits 工程师 + Agent」协作产物的回归，不是纯 Agent 的回归。把它当作纯 Agent 基线，会误判人在这条流水线里承担的那部分审查贡献。

## 关键矛盾

1. **16% 是特定项目的样本，不是行业基线**。Patch the Planet 选的是安全敏感的开源项目，补丁复杂度和审查强度都高于平均水平，不能外推到所有 Agent PR
2. **精确率 36% 说明单轮候选噪声大**。Agent 报 58 个、确认 21 个，意味着大量人工筛选。自动化修漏洞的瓶颈正在从「生成补丁」转向「验证补丁」
3. **裁决仍由 Agent 完成**。fresh-context 重放和 three-arm proof 缓解了自评，但没有引入独立的人类或形式化判定。边界案例（borderline）就是这套方法的盲区
4. **误报与漏报的成本不对称**。安全场景下漏报更贵，工具却选择压误报，这个选择需要明确说明适用场景
5. **「没有破坏安全防护」是重要限定**。21 个回归里没有一个是安全防护失效，这句话不能省；省掉就会把「功能回归」误读成「安全回归」
6. **HN 热度低不代表选题弱**。53 分说明它没出圈，但这类「有样本、有对照、有失败案例」的材料，比一条爆款新闻更适合做技术深读

## 创作方向建议

### 方向 A：验证链，而不是通过率（推荐）

以 three-arm proof 为核心，讲 Agent 修 bug 的评估范式从「测试通过」转向「可执行的因果证据」：原始失败、补丁通过、回滚再失败。再往前推一步：为什么 live PoC 比单元测试更难造假，为什么 fresh-context 重放能削弱自评。

落点可以是：**Agent 的可信度不来自它说自己修好了，而来自它能证明「没有它，问题仍然存在」**。这个判断能同时解释 three-arm proof 和 21/58 的噪声。

### 方向 B：误报经济学

25% 的误报下降、14%–38% 的置信区间、borderline 的漏报代价，三个数字撑起一篇关于「Agent 代码审查工具怎么定价」的文章。适合偏工程的读者，但需要补一点统计背景。

### 方向 C：威胁模型作为 Agent 上下文

从 `THREAT_MODEL.md` 切入，讲 Agent 项目应该如何把安全假设外置成文件，而不是塞进系统提示词。可以和 AGENTS.md、Skills 的上下文管理线接上。素材够，但偏工具使用，深度不如 A。

### 方向 D：AI 找漏洞快，修漏洞慢

把 Patch the Planet 和 PHP2Shell 之类的漏洞披露放在一起，讲产能错配：发现端已经被 Agent 加速，修复端仍受限于验证和审查。这个方向需要更多漏洞侧的一手数据，目前只有 Trail of Bits 单方材料。
