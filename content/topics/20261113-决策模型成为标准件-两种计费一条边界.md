## 主线

2026 年 9 月到 11 月，八周时间，这个品类走完了从「一个实验室的产品」到「两家大厂各出一条产品线」的路。

- 9 月 15 日，TypeSafe 发布 Jev，$0.042/百万输入 token，输出不计费，端到端 70–500 毫秒
- 10 月 1 日，AWS 开源 Strands Decider 2B：拆掉 Qwen3.5-2B 的 LM head，换成约 100 万参数的 pointer head，权重、数据、脚本全给
- 11 月 9 日，Amazon 公布生产账：工单打标从 Sonnet 4.6 换成 Decider E4B，每百万张 $22,200 → $500
- 11 月 11 日，Google 发布 Gemini Decision 1 与 Decisions API，$0.10/百万输入 token，输出不计费，一次请求最多 1,000 个问题

四个事件放在一起，能看出三件前两篇没覆盖的事。

**第一，定价单位分裂了。** Jev 和 Gemini 都按输入 token 计价、输出免费；Strands Decider 没有 API，只有权重，成本按实例小时算（`ml.g5.xlarge` $1.408/小时）。同一个能力，三种计费锚点：按判断量、按吞吐、按机器。这不是细节，它决定了这门生意谁能做——API 厂商卖的是「不用自己运维」，开源自托管卖的是「数据不出网」。

**第二，Google 把「一个问题」变成了「一千个问题」。** 单请求最多 1,000 个独立问题、共享 256K 上下文，按输入 token 计费意味着：一次塞满 256K 的请求花 $0.0262，回答 1,000 个问题，摊到每个问题 $0.0000262。同一批问题如果一次一问，输入要重复付一千遍。这个批量化不是模型能力，是接口设计——它把「决策」从按次调用变成了按批调用，成本结构整个换掉。

**第三，边界被厂商自己的基准画出来了。** Google 公布 9 项基准 7 项第一，但输掉的两项里有一项叫 When2Call——判断「这个工具现在该不该调用」，79.9% 对 TypeSafe Jev 1.14 的 82.0%。工具选择是 Agent 里最值钱的那类判断，恰恰是决策模型还没吃下来的。Amazon 那边也给了三条不适用条件：标签需要解释性描述、目录每周变、上下文塞不进几千 token。

所以这条选题真正的落点不是「又快又便宜」，而是：**决策模型已经能商品化「分类」，但还没商品化「判断时机」。** 前者是封闭选项里挑一个，后者要理解状态和动作的关系。这两件事在 Agent 里长得很像，在模型能力上差一个层级。

## 核心事实（已核对一手来源）

### Google：Gemini Decision 1 / Decisions API（2026-11-11）

| 项目 | 数据 |
|------|------|
| 计价 | $0.10 / 百万输入 token，输出 token $0 |
| 单请求问题数 | 1–1,000 个独立问题，三种类型可混合 |
| 输入上限 | 262,144 token，支持文本/图像/音频/视频/PDF |
| 延迟 | 端到端 150–250 ms；≤16K 上下文时模型计算中位 50–100 ms |
| 决策类型 | 是/否（返回概率）、多选（2–255 个选项）、有序标准评分 |
| 成本对比 | 同组基准下约为 Gemini 3.5 Flash-Lite 的 1/5 |
| 基准 | JevBench 92.2%（GPT-6 Luna 90.9%、TypeSafe Jev 1.14 90.0%、Flash-Lite 86.6%） |
| 校准 | Top-1 ECE 0.0250（GPT-6 Luna 0.0721、Jev 1.14 0.0494、Flash-Lite 0.2104） |
| 输掉的项 | When2Call 79.9% vs Jev 1.14 82.0%；Mind2Web Multimodal 86.2% vs 86.8% |

Google 同时披露了四个内部用法：Gemini Notebook 拿它做实时模型路由，日常查询延迟最多降 40%；Stitch 的 Rapid Canvas 用它生成线框流程；Google Labs 的 CC 从 200 多个 emoji 里选反应；Google Search 用它给 MCP 工具做安全检测层。最后一条值得单拎：把「这个工具调用是不是对抗性的」做成一次百毫秒级的概率判断，是这类模型最自然的落点。

### Amazon：Strands Decider 替换 Sonnet 4.6（2026-11-09）

| 指标 | Sonnet 4.6 | Decider E4B | 变化 |
|------|-----------|-------------|------|
| 单次调用平均耗时 | 4,215 ms | 897 ms | -78% |
| 每张工单输入 token | 6,554 | 2,009 | — |
| 每张工单输出 token | 170 | 1 | — |
| 每张工单总 token | 6,724 | 2,010 | -70% |
| 单张工单成本 | $0.0222 | 约 $0.0005 | — |
| 每百万张工单 | 约 $22,200 | 约 $500 | 约 44 倍，-98% |

部署形态：SageMaker `ml.g5.xlarge`（单卡 A10G，24GB），模型占约 19GiB，单请求约 640 毫秒，单实例每小时约 5,600 张工单。官方按满负荷算是 $250/百万张，留出突发余量后按 $500/百万张计。

两个工程细节值得抄：

- **三档灰度开关**：Lambda 每次从 AppConfig 读 `BEDROCK`（只走 Sonnet）、`DUAL`（两边都跑，Sonnet 上线、Decider 只记录）、`DECIDER`（只走 Decider）。回滚是改一次配置，45 秒。
- **JSON 键序会带偏概率**：同样的内容，键序不同，输出概率最多偏 0.19。他们把请求改成固定键序。任何要拿决策模型做 A/B 的人，这一条是硬约束——不锁序列化格式，测出来的差异可能是键序造成的。

还有一个容易被忽略的动机：SageMaker endpoint 的网络是隔离的，容器不能对外访问。Amazon 选自托管不全是图便宜，是工单数据不能出网。

### Strands Decider：这类模型长什么样（2026-10-01）

不是蒸馏，是**把语言模型的输出头拆掉**。底座 Qwen3.5-2B，去掉 LM head，换成约 100 万参数的 pointer head：用每个候选选项位置的隐层状态和 `<answer>` 位置的隐层状态打分，取概率最高项。躯干用 rank-16 LoRA 微调。权重、训练数据、训练脚本全开源。

延迟：RTX 3090 中位约 115 ms，M3 MacBook 约 153 ms。JevBench 公开集上 2B 量级排第 3（33 个模型中），排除略超 2B 的模型后排第 1。

官方适用清单：模型路由、工具选择、评估、护栏、记忆、上下文管理、策略分类。不适用：生成文本、多步推理、解释理由。

## 三种计费锚点，三种生意

把公开发布的价格放在一张表里，能看清这个品类的商业模式已经分叉。

| | TypeSafe Jev | Gemini Decision 1 | Strands Decider |
|---|---|---|---|
| 形态 | 专用 API | 通用 API | 开源自托管 |
| 计价 | $0.042/百万输入 token | $0.10/百万输入 token | $1.408/实例小时 |
| 输出计费 | $0 | $0 | 不适用 |
| 延迟 | 70–500 ms | 150–250 ms | 约 640 ms（g5.xlarge） |
| 上下文 | 未公开 | 256K | 4,096 token |
| 权重 | 闭源 | 闭源 | 开源 |
| 数据出网 | 是 | 是 | 否（网络隔离） |

三种锚点对应三种客户：按判断量付费的，买的是「不想管机器」；按实例小时付费的，买的是「数据不出网」和「单位成本可预测」；闭源专用 API 卖的是「效果最好那一档」。

**一个反直觉的算术**：按 Amazon 每张工单约 2,000 输入 token 的量级估算，同样负载走 Jev 约 $84/百万张，走 Gemini 约 $200/百万张，自托管 Decider 是 $250–500/百万张。也就是说在这个利用率下，云 API 反而比自托管便宜。自托管的价值在隔离和可控，不在单价。这个对比是我按公开列表价算的，不含重试、出口流量和运维人力，只能当量级参考——写正文时要么标清假设，要么别用。

## 关键矛盾

**第一，98% 不是优化出来的，是「不做」省出来的。** 传统降本是在同一条曲线上往左挪：换小模型、量化、缓存、蒸馏。决策模型是把曲线换掉——不生成，就没有输出 token；prompt 从长指令变成短判据，输入也塌了一截。所以拿它和「小模型 + 结构化输出」比价，比出来的不是同一个东西。

**第二，批量接口把单位成本改了一个数量级。** 1,000 个问题共享一次输入，按输入 token 计费，摊到每个问题约 $0.000026。这不是模型更便宜，是计费方式承认了「同一份材料上的多个判断不该重复付输入钱」。这个设计比模型本身更容易被复制，也更可能成为行业默认。

**第三，边界在「时机」上。** Google 自己的 When2Call 输给 Jev，说明「从封闭集合里选一个」已经商品化，「现在该不该动手」还没有。Amazon 的三条不适用条件补上工程侧：标签要解释、目录常变、上下文塞不进 4K，都不适合。把这两组约束合起来，就是一份可用的准入清单。

**第四，自托管不等于便宜。** Amazon 的账之所以好看，是拿自托管和「Sonnet 按 token 计费」比。如果对手换成 $0.042/百万 token 的决策 API，44 倍会缩到个位数甚至反转。真正的理由得回到隔离、可控、可审计——这些不上财务报表，但决定了能不能用。

**第五，基准是厂商自选的。** 「9 项 7 项第一」来自 Google 挑的 9 项、挑的对手，没有第三方复现。能用的部分恰恰是那些输掉的项——厂商主动公布自己输的项，通常说明差距藏不住，或者赛道上有一个必须正视的对手。

## 创作方向建议

### 方向 A：标准件是怎么长出来的（推荐）

以八周四个事件做时间轴，主线放在「品类成熟的三个标志」：定价单位分裂、接口批量化、边界被厂商自己写进基准。Amazon 的账做经济性证据，Google 的 1,000 问题做接口设计证据，When2Call 的失利做边界证据。

落点：一个模型品类成熟的标志，不是它变强了，是它开始知道自己不能干什么。

这条最适合续写系列，也能自然承接前两篇，不需要重复基础概念。

### 方向 B：判断的计价单位

只写钱。三种计费锚点（token / token / 实例小时）如何决定客户结构；1,000 问题批量如何把单位成本压一个数量级；自托管在什么利用率下才比 API 便宜。做一张「什么规模该选哪种」的决策表。

风险是纯算账容易干，需要把「数据出网」这类非价格因素放进表里，否则结论会失真。

### 方向 C：4K 窗口与 0.19 键序——生产准入清单

偏实操。把 Amazon 的三条不适用条件、Decider 的 4,096 窗口、Google 的 256K 上限、JSON 键序偏移、灰度三档开关做成一张检查表。读者收藏率高，但传播弱。

## 数据口径备忘

1. **「98% / 44 倍」是列表价推算，不是账单。** $22,200 按 Sonnet 4.6 在 Bedrock 全球端点 us-east-1 的按需价 $3/$15 每百万 token 和实测 token 数算出；$500 含实例利用率假设（满负荷 $250，留突发余量后 $500），不含 Lambda 成本。
2. **Amazon 的「精度可比」没有数字。** 原文只说 E4B「performed just as well」「beating production Sonnet on a separate set of our tickets」，未给准确率。不能写成「准确率提升 X%」。
3. **每问题 $0.0000262 是算术推导**：262,144 × $0.10/1M ÷ 1,000。前提是单请求塞满 256K 且问题数打满 1,000，实际很难同时满足，只能当理论上限。
4. **跨厂商单位成本对比是我的估算**，按每张工单 2,000 输入 token、公开列表价、不含重试与运维。写正文必须标假设，或者只做量级表述。
5. **「9 项 7 项第一」是 Google 自选基准 + 自选对手**，无第三方复现，引用必须带限定。
6. **ECE 0.0250 与准确率不是一回事**，且不同评测集的 ECE 不可横向比较——前一篇写过的 TrueStandard 数据（0.061–0.067）是另一套题，不要放在同一句里比。
7. **Jev 的 $0.042 单位已核实**：官方原文为 input tokens $0.042/MTok（$42 per billion），输出免费。前一篇也用这个数，保持一致。
8. **Strands Decider 2B 与 E4B 是两个模型。** 案例里用的是 E4B Gemma 4 构建，2B 是最初版本，窗口 4,096 是案例里提到的约束；不要把 2B 的参数和 E4B 的成本混在一句。
9. **三家术语不统一**（decision model / System One / decider），正文选一个主术语，其余首次出现时注明同类。
