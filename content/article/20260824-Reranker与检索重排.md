# Reranker 与检索重排：三家族架构与 LLM 时代的新边界

> **导读**：Rerank 不是简单的"换个模型重排一下"。它背后是三套不同架构在"召回率与精度的算力分配"上做权衡。
>
> Bi-Encoder 把 query 和 doc 各自压成单向量，速度快但看不见交叉信号；Cross-Encoder 联合编码每对 (query, doc)，精度顶到天花板但单条推理贵上百倍；Late Interaction 想在中间找到平衡点。而 2023 年开始，LLM 带着 listwise 范式入场，把这套架构之争推进了第二幕。

---

## 一、为什么 Rerank 不只是"加一层排序"

做 RAG（Retrieval-Augmented Generation，检索增强生成）的人都有过这种体验：明明 embedding 模型用的是 BGE-M3，向量库用的是 Milvus，召回 top-20，看着距离分数也不低，但丢给 LLM 之后回答就是驴唇不对马嘴。

绝大部分时候，问题不出在 embedding 模型的语义能力上，而出在"两段式打分"上。

Bi-Encoder（双塔编码器，下文会详述）在召回阶段只能做"向量相似度"这一种粗粒度判断，它看见的 query 已经被压成 1024 维的稠密向量，看见文档时也是同样处理，二者之间没有任何 token 级的交叉注意力。

语义近似但语境错位、关键词命中但答非所问、领域专有词在向量空间里被错误拉近，这些 embedding 召回阶段的典型问题，Rerank 才是真正的解药。

多个 RAG 项目里的规律是：**加 Rerank 之后，top-3 的命中率提升明显，效果比换一个更好的 embedding 模型更明显。** 原因不复杂——embedding 模型的边际收益已经很小，而 Rerank 是在召回已经"沾边"的候选集上做精细打分，相当于把同一道题从开卷考试换成闭卷考试。

但 Rerank 不是一个模型，而是一类模型。它们的架构差异决定了它们在工程管线里能放在哪个位置、能处理多少候选、能跑多快。围绕它展开的是"三家族"加"LLM 新边界"四件事：Bi-Encoder、Cross-Encoder、Late Interaction 各自的核心权衡，以及 2023 年之后 LLM-based Reranker 怎么把这套体系推到了第二个分水岭。

---

## 二、三家族架构：召回率与精度的算力分配

检索系统的两阶段范式从 2019 年 Nogueira 等人提出 monoBERT（[1901.04085](https://arxiv.org/abs/1901.04085)）开始成型，至今几乎所有生产级 RAG 都在用：第一阶段召回 top-100，第二阶段 Rerank 出 top-10。但三家族模型在"如何把 query 和 doc 喂给神经网络"这个根本问题上分道扬镳。

### 2.1 Bi-Encoder：单向量召回的天花板

Bi-Encoder（双塔编码器）的代表是 DPR（[2004.04906](https://arxiv.org/abs/2004.04906)）和 BGE-embedding 系列。它的思路极其简洁：query 和 doc 各自由一个独立的 BERT（或 XLM-RoBERTa）编码，输出一个固定维度的向量，然后做向量内积或余弦相似度。

伪代码长这样：

```text
# Bi-Encoder 召回
E_q = BiEncoder.encode_query(query)             # query 编码为 1 个向量
E_D = BiEncoder.encode_doc(doc) for doc in corpus  # 每个 doc 离线预编码
scores = E_q @ E_D.T                              # 内积/余弦得到所有 doc 的相似度
top_k = scores.topk(100)                          # 取 top-100
```

这个架构最大的优势是**离线可预计算**。Corpus 里 1000 万篇文档，事先跑一遍 Bi-Encoder 存到向量库，查询时只编码一次 query 就好。ANN（近似最近邻）索引能把检索时间压到毫秒级。

代价是什么？**query 和 doc 之间没有任何交互**。query 的"机器学习"和 doc 的"深度学习算法"在编码时是相互独立的，只有最后那一次内积把它们拼起来。

这意味着 Bi-Encoder 结构上无法捕捉"否定关系"（"不要机器学习"和"机器学习"在向量空间里很近）、"实体替换"（"iPhone 价格"和"华为价格"在向量空间里很近）、"组合语义"（"红苹果"和"苹果公司"在向量空间里很近）。这些是 embedding 检索阶段的结构性盲区，不是"换更好的模型"能解决的。

所以 Bi-Encoder 的定位很明确：**第一阶段召回，负责覆盖率，不负责精度**。中文场景下 BGE-M3 是当下的事实标准，多语言、长文本（8192 token）、稠密+稀疏+多向量三合一检索，跑得通就行。

### 2.2 Cross-Encoder：联合编码的精度天花板

Cross-Encoder（交叉编码器）的代表是 monoBERT、BGE-reranker-v2-m3、Cohere Rerank v4.0。它把 query 和 doc 拼接成一个序列送进同一个 Transformer，让 query 的每个 token 和 doc 的每个 token 做全注意力交互。

伪代码：

```text
# Cross-Encoder 重排
input = "[CLS] " + query + " [SEP] " + doc + " [SEP]"
logit = CrossEncoder(input)[CLS]           # [CLS] 位置接分类头
score = sigmoid(logit)                      # 相关性概率
```

这一下就解决了 Bi-Encoder 在上文列出的那些结构性盲区。query 里的"不要"能跟 doc 里的"机器学习"做注意力，模型能判断这是反例；query 里的"iPhone"能跟 doc 里的"华为"做注意力，模型能判断这是实体替换；query 里的"红"能跟 doc 里的"苹果"做注意力，模型能判断这是修饰关系。

**但代价是天文数字的算力**。一个 (query, doc) 对就要过一次完整 Transformer，100 万对就是 100 万次前向。ColBERT 论文引用的数据显示，BERT 类排序模型比此前的检索模型贵 100–1000 倍（[ColBERT, 2004.12832](https://arxiv.org/abs/2004.12832)），所以 Cross-Encoder 不能放在第一阶段去跑全库，只能放在第二阶段重排 top-100。

加 Rerank 之后效果变好，不是 BGE-reranker 比 BGE-embedding 更聪明，而是**它终于能看见 query 和 doc 之间的交叉信号**，这件事 embedding 模型在结构上做不到。

另一个常被忽略的细节是 **Cross-Encoder 的分数不可跨模型比较**。Cohere 文档里明确说"0.9 不等于 0.45 的两倍相关"，BGE 原始输出是 logits 需要 sigmoid 到 [0,1]。阈值必须在自有语料、特定模型上标定，换模型要重调。这件事写代码时容易翻车。

### 2.3 Late Interaction：折中架构的真实价值

ColBERT（Khattab & Zaharia 2020）要解决的痛点是：Bi-Encoder 太粗糙、Cross-Encoder 太贵，关键在中间是否还有一条路。

它的方法是让 query 和 doc 各自独立编码为 token 级别的向量（不是单向量），然后用一个叫 MaxSim 的算子做细粒度交互：

```text
# ColBERT Late Interaction
E_q = [e_q1, e_q2, ..., e_q|Q|]    # query 每个 token 一个向量
E_d = [e_d1, e_d2, ..., e_d|D|]    # doc 每个 token 一个向量
S(q, d) = Σ_{i ∈ |q|} max_{j ∈ |d|} cos(E_qi, E_dj)  # 每个 query token 找最相似的 doc token，求和
```

这个设计的精妙之处在于：**doc 端的向量可以离线预计算**，跟 Bi-Encoder 一样；query 端编码一次后，跟 doc 端做廉价的 MaxSim（点积 + max），不需要再过 Transformer。ColBERT 论文报告它比 Cross-Encoder 重排快两个数量级、少 4 个数量级 FLOPs，同时效果接近 Cross-Encoder。

但 Late Interaction 也不是没有代价。**存储开销是 Bi-Encoder 的几十倍**——一篇 512 token 的文档要存 512 个 128 维向量，而不是 1 个 1024 维向量。

ColBERTv2（[2112.01488](https://arxiv.org/abs/2112.01488)）用残差压缩 + 去噪监督把存储降了 6–10 倍，PLAID（[2205.09707](https://arxiv.org/abs/2205.09707)）进一步把延迟降到 ColBERTv2 的 1/7（GPU）/ 1/45（CPU）。但即便如此，ColBERT 在工业级 RAG 里的部署复杂度仍然远高于 BGE-reranker。

**所以三家族的真实定位是**：

- Bi-Encoder：覆盖率的兜底，负责"捞到候选"
- Cross-Encoder：精度的天花板，负责"排好候选"
- Late Interaction：折中方案，PLAID 论文实测在 140M passages 语料上 GPU 延迟数十毫秒，是 ColBERT 系支撑大规模检索的效率代表

写代码选型时，先看召回阶段用什么 Bi-Encoder，再看精排用 Cross-Encoder 还是 Late Interaction。ColBERT 既能当第一阶段检索器（不接 ANN，直接暴力 MaxSim）也能当第二阶段重排器，但工程上多数团队会选择更简单的 Bi-Encoder 召回 + Cross-Encoder 重排组合。

## 三、训练目标的范式之争：Pointwise / Pairwise / Listwise

架构之争之外，训练 Rerank 模型时还有一个独立的维度——损失函数怎么设计。它决定了模型学到的是"绝对相关性"还是"相对排序"。

**Pointwise（单文档打分）** 是最朴素的做法：把 (query, doc) 对当成二分类，相关为 1、不相关为 0，用交叉熵训练。monoBERT、BGE-reranker、Cohere Rerank v4.0 都是这个范式。优点是简单、可并行、标注易得；缺点是只学了绝对相关性，对"doc A 比 doc B 更相关"这种相对信息不敏感。RankT5 论文（[2210.10634](https://arxiv.org/abs/2210.10634)）系统对比过，单 pointwise 训练在跨域零样本排序上弱于 listwise。

**Pairwise（A vs B）** 直接建模"谁更相关"，训练时给 (query, doc⁺, doc⁻) 三元组，让模型给 doc⁺ 的分数高于 doc⁻。DuoBERT 是代表。优点是直接优化排序目标，缺点是训练依赖难负例的质量——只喂随机负例会学不动，只喂难负例又容易在简单查询上掉点。

**Listwise（整列表打分）** 把整个候选列表作为输入，让模型输出整个列表的排列。RankT5 在 listwise 微调下表现最强，RankGPT（[2304.09542](https://arxiv.org/abs/2304.09542)）把 listwise 做到了极致——直接让 LLM 用自然语言输出 `[3] > [1] > [5] > [2] > [4]` 这种排列字符串。

listwise 的上限最高，因为它直接对齐 NDCG（Normalized Discounted Cumulative Gain，归一化折损累积增益）这种排序指标；下限也最不稳定，受候选列表长度限制（context window 限制 k≤100），长候选集要用 sliding window，工程上脆弱。

实操选型上，**默认 Pointwise**——BGE-reranker-v2-m3 这类逐对打分的交叉编码器，工业级稳定性最好。Pairwise 适合在自有标注数据上微调。Listwise 是前沿研究的方向，生产环境落地要谨慎。

## 四、工程选型与踩坑记录

理论讲完，看工程。

### 4.1 主流 Rerank 模型怎么选

中文场景闭眼选 BGE-reranker-v2-m3（[HuggingFace](https://huggingface.co/BAAI/bge-reranker-v2-m3)），568M 参数，100+ 语言，Apache-2.0 开源，至今仍是 BAAI 在自部署场景的事实标准。要更高效果或更长 context，主流选项有：

1. **Qwen3 Reranker 8B**（阿里 2025-06-05 发布，32K context，100+ 语言，instruction-aware 重排，[OpenRouter](https://openrouter.ai/qwen/qwen3-reranker-8b) 上输入约 $0.10–0.20/M tokens）
2. **Cohere Rerank v4.0**（2025-12-11 发布，Pro/Fast 两档，32K context（v3.5 为 4K，即 8 倍），100+ 语言，**首个支持 self-learning 的重排器**——可声明内容偏好、定制到自有语料不用标注数据，Fast 档 $0.002/search，[Cohere 官方 changelog](https://docs.cohere.com/changelog/rerank-v4.0)）
3. **Jina Reranker v3**（0.6B listwise，131K context）走极致小模型路线，但要注意它是 cc-by-nc-4.0 协议，不能商用

**经验值：fetch-k 50–150，keep-n 3–10**。Anthropic 在《Contextual Retrieval》工程博客里公开过一组数据：取 top-150 候选重排压到 top-20，配合上下文嵌入与 BM25，把 top-20 召回失败率降了 67%（5.7%→1.9%），并发现 top-20 优于 top-5/top-10（[Anthropic](https://www.anthropic.com/engineering/contextual-retrieval)）。

但 fetch-k 超过 ~100 之后 cross-encoder 对噪声敏感，可能把"看似相关实则错"的段落顶上去。原则是"检索宽取，重排狠压"。

### 4.2 五个最常见的坑

**坑 1：分数拿来直接过滤。** 上面说过，不同模型的分数不可比，同一模型在不同 query 上分数分布也不一样。阈值必须按"特定模型 + 自有语料"标定。

**坑 2：把 Rerank 当召回器用。** 有人想"我用 BGE-reranker 直接对全库打分，效果不是更好吗？"算力不允许。100 万篇文档每篇都过一次 Transformer，单查询延迟按小时算。Rerank 只能重排它看见的候选——**召回漏掉的，它救不回**。先测 `recall@fetch-k`，到 plateau 就停，别盲目拉到 1000。

**坑 3：fetch-k 设 500+。** 候选数翻倍延迟近似翻倍（200 篇 × 10ms = 2s），但效果不会翻倍——top-100 之后大量是噪声，反而污染精排。top-100 是甜蜜区。

**坑 4：Embedding 和 Reranker 语言不匹配。** 用 BGE-embedding 检索中文文档，结果 Reranker 装的是 cross-encoder/ms-marco-MiniLM-L-6-v2（纯英文模型），ihower 博客上实测：英文 Reranker 跑中文库，top-k 增加时命中率反而下降。中文场景优先选 BGE-reranker-v2-m3、Cohere Rerank v4 多语言版或 Qwen3 Reranker 8B。

**坑 5：长文档直接超 max_length 截断。** BGE-reranker-v2-m3 的 FlagReranker 默认 max_length=512，长文档会被截断，丢掉关键信息（模型架构本身支持到 8192 token，BAAI 官方推荐推理时设 max_length=1024）。设大到 1024 或 2048 是常见的优化点，但长度翻倍算力近似翻倍，按文档实际长度调整。如果文档真的长到 8K+，优先选 Cohere Rerank v4（32K context）或 Jina Reranker v3（131K context），不要硬扛小 context 模型。

### 4.3 性能优化清单

性能优化有四个方向：

- **GPU 部署**：`FlagReranker(..., use_fp16=True)`，官方说提速明显且精度损失可忽略
- **CPU/边缘部署**：`optimum-cli` 导出 ONNX 后做 INT8 量化，可显著缩小体积、提速
- **高并发服务化**：用 vLLM 暴露 OpenAI 兼容 `/rerank`（`vllm serve BAAI/bge-reranker-base`），Haystack 和自写客户端都能接
- **批量推理**：`compute_score(pairs, batch_size=64)` 比逐条快 2–3 倍，一定要做

## 五、LLM Reranker：2023 年开启的第二幕

传统 Rerank 到 2023 年是一个节点。2023 年 4 月 Sun 等人放出 RankGPT（[2304.09542](https://arxiv.org/abs/2304.09542)），把"用 GPT-4 做 listwise 重排"这件事跑通了，检索排序的研究范式从此被推向了一个新方向。

### 5.1 RankGPT 的核心洞察

RankGPT 的方法出奇简单：把候选列表和 query 一起塞进 prompt，让 GPT-4 输出一个排列字符串。论文里给了一个典型 prompt：

```text
Search Query: {query}

Passages:
[1] {passage_1}
[2] {passage_2}
...
[20] {passage_20}

Rank the 20 passages above based on their relevance to the search query.
Output the ranking in descending order using identifiers, e.g., [3] > [1] > [5]...
```

GPT-4 居然真能稳定输出这种格式的字符串排序，而且效果在 BEIR 多个数据集上追平甚至超过专门训练的 cross-encoder。论文标题"RankGPT: Is ChatGPT Good at Search?"读起来像挑衅，本质是想说明：**LLM 预训练里吸收的世界知识，让它天然能做相关性判断，甚至不需要为排序任务专门训练。**

但 RankGPT 立刻暴露出三个问题：

- **成本**：GPT-4 按 token 计费，重排 50 篇文档在 H100 上最多要 1 分钟（[2403.10407](https://arxiv.org/abs/2403.10407)），生产环境扛不住。
- **可复现性**：闭源 API 换版本就出行为漂移，科学实验写不出"可复现"四个字。
- **数据污染**：BEIR 是公开数据，GPT-4 在预训练里大概率见过，榜单成绩有水分。

### 5.2 蒸馏路线：把 GPT-4 的排序能力压缩到开源模型

2023 年 9 月 RankVicuna（[2309.15088](https://arxiv.org/abs/2309.15088)）成为首个全开源 listwise reranker，7B 模型，持平 GPT-3.5、略逊 GPT-4。然后是 12 月的 RankZephyr（[2312.02724](https://arxiv.org/abs/2312.02724)），两阶段蒸馏：先用 RankGPT-3.5 在全量数据上生成监督信号，再用 RankGPT-4 对 OpenAI Ada2 首阶段召回的 5K 查询排序做监督，微调 Zephyr-7B，比 RankVicuna 更进一步。

RankZephyr 的关键结论（论文 Table 1）：在 TREC DL19 上，7B 的 RankZephyr 反超了它的老师 RankGPT-4，DL20 上仍略逊（[论文](https://arxiv.org/abs/2312.02724)）；在 NovelEval（沿用 RankGPT 构建的、超出 GPT-4 训练期的抗污染集）上同样占优。这件事的意义在于：开源重排器在 TREC DL 榜单上追平甚至反超了闭源 LLM——当然在部分 BEIR 子集上仍略低于 GPT-4。

到 2025 年，RankLLM 工具链（[2505.19284](https://dl.acm.org/doi/10.1145/3726302.3730331)）被 SIGIR 接收，统一了 pointwise / pairwise / listwise 三种范式的工程实现（[GitHub: castorini/rank_llm](https://github.com/castorini/rank_llm)）。ReasonRank（[2508.07050](https://arxiv.org/abs/2508.07050)）和 Rank-K（[2505.14432](https://arxiv.org/abs/2505.14432)）引入 test-time 推理（CoT）进一步提升 listwise 效果。Self-Calibrated Listwise（[2411.04602](https://arxiv.org/abs/2411.04602)）解决排序自校准问题。

### 5.3 闭源 LLM 做 Rerank 到底值不值

这是个真实工程问题，不是学术问题。

[2403.10407](https://arxiv.org/abs/2403.10407) 给了非常硬的数据：SPLADE-v3 做 first stage，DeBERTa-v3 cross-encoder 重排 k=200、512 token，TREC-COVID 上 nDCG@10 89.2；GPT-4 重排 k=75，nDCG@10 87.5。

GPT-4 Turbo 在 k=100 时反而**不如**标准 GPT-4——更大的 context 并没有带来更好的效果。级联方案 `SPLADE-v3 » DeBERTa-v3(k=200) » GPT-4(k=25)` 在 TREC DL23 上达 63.7 nDCG@10。

这个数据说明三件事：

- GPT-4 的 Rerank 上限确实比 DeBERTa-v3 高，但差距不大（89.2 vs 87.5）。
- GPT-4 贵到不能直接用——重排 50 文档最多 1 分钟，按 token 计费，RAG 业务日均百万查询根本扛不住。
- GPT-4 对截断比 DeBERTa-v3 更鲁棒，79 token 截断后 GPT-4 仍 ~87，DeBERTa-v3 从 89 掉到 80。

生产环境最实用的方案是级联：先用便宜的 cross-encoder 重排到 25–50，再用 GPT-4 精排到 5–10，兼顾成本和效果。

开源 LLM（Yi-34B、LLaMA-70B）目前替代不了——[2403.10407](https://arxiv.org/abs/2403.10407) 测下来输出格式稳定性差、效果远低于 GPT-4，Jina Reranker v3（0.6B listwise，131K context）这类小模型才代表"小模型做 LLM 风格重排"的极小化方向。

### 5.4 可运行的 LLM Reranker 代码

RankLLM 工具链简化了 LLM Rerank 的工程接入，下面这段代码演示如何用 OpenAI 兼容接口做 listwise permutation：

```Python
from rank_llm import RankLLM, get_gen_candidates
from rank_llm.rerank.listwise import listwise_rank

# 1. 准备候选（query + top-100 docs）
query = "What is a rerank model in RAG?"
candidates = [
    {"docid": "d1", "text": "Rerank models score query-doc pairs after first-stage retrieval..."},
    {"docid": "d2", "text": "Quantum computing uses qubits and superposition..."},
    # ... 共 100 个候选
]

# 2. 初始化 LLM（OpenAI 兼容，gpt-4o-mini 即可演示）
agent = RankLLM(model="gpt-4o-mini", context_size=4096, keys=["OPENAI_API_KEY"])

# 3. listwise 重排（sliding window 处理长候选）
reranked = listwise_rank(
    agent=agent,
    candidates=candidates,
    query=query,
    window_size=20,   # 每次 LLM 看到的窗口大小
    stride=10         # 滑动步长
)

# 4. 输出 top-10
for i, cand in enumerate(reranked[:10]):
    print(f"{i+1}. [{cand.docid}] {cand.text[:80]}")
```

代码里的 `window_size` 和 `stride` 是关键参数。LLM 的 context window 是硬限制（GPT-4o-mini 16K，gpt-4 8K），100 个候选一次塞不下，必须用 sliding window：先对 1–20 重排，再对 11–30 重排，依此类推，最后汇总。stride 小（如 5–10）效果更好但 API 调用次数翻倍。

这套代码的本质是：把 Rerank 任务建模成"让 LLM 输出排序字符串"，用工程化的 sliding window 解决 context 限制，用 listwise prompt 解决候选间相对比较问题。它不是用 LLM 做分类或生成答案，而是把 LLM 当成一个"懂语义的排序器"。

### 5.5 2026 年还在持续的几条线

RankZephyr 之后，listwise 范式的研究没有停。一个清晰的方向是效率压缩：**FIRST**（[2406.15657](https://arxiv.org/abs/2406.15657)，Reddy et al. 2024）用首个生成 token 的 logits 直接得出排序，替代逐个生成整段排列字符串，把 LLM 重排的推理延迟砍掉 50%，同时在 BEIR 上维持甚至超过 RankZephyr 的效果。

这类工作把 listwise 的"上限高"和"工程贵"两个特征同时优化——既不放弃 listwise 的全局排序优势，又在推理成本上往 Cross-Encoder 看齐。生产环境里，过去一年的趋势是**先小模型 cross-encoder 粗排 top-200，再用 listwise 小模型或 API 精排 top-10**，单步成本从数分钟压到秒级。

## 六、回到开篇：Rerank 的边界与未来

加 Rerank 之后 RAG 效果变好的原因，不在"Rerank 模型更聪明"，而在**Rerank 模型在结构上能看见 Bi-Encoder 看不见的东西**——query 和 doc 之间的 token 级交叉信号。这种信号是 embedding 召回阶段在结构上付不起的成本，Rerank 是这套结构性限制的补丁，而不是取代。

三家族架构的实质是**召回率与精度的算力分配问题**。Bi-Encoder 把所有算力花在离线预计算上，换来毫秒级召回；Cross-Encoder 把所有算力花在 query-doc 交互上，换来精度天花板；Late Interaction 试图在中间找到平衡。

生产环境里大多数团队最终选的是"Bi-Encoder 召回 + Cross-Encoder 重排"这套组合，因为它最简单、最稳定、最容易调优。

LLM Reranker 把这套体系推到了第二个分水岭。它的最大价值不是"用一个更大的模型做 Rerank"，而是证明了**listwise 范式在候选集够小时能跑出比 pointwise 更高的上限**。

但闭源 LLM 的成本让这条路在生产环境难以走通，开源 7B 模型蒸馏让效果追平了闭源，但 context window 限制让工程化变得复杂。Jina Reranker v3（0.6B listwise）这类小模型和小模型 CoT 推理是这个方向的延续。

下一个真正值得关注的信号不是"更大的 Rerank 模型"，而是**端到端排序器**——把召回和重排合并成一个模型，用一个统一的损失函数联合训练。ColBERT 已经迈出了第一步（既当第一阶段检索器也当重排器）。检索端的 embedding 模型也在往"自带重排能力"演进，部分厂商的榜单数据已经体现了这种信号（如 MTEB Retrieval 子集）。

当一个 embedding 模型本身就带有 rerank 能力，Bi-Encoder 召回 + Cross-Encoder 重排的两段式架构可能不再是必须（前提是端到端模型在跨域、长文档、稀疏查询三类场景都稳定跑过 single-stage）。
