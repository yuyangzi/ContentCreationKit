# LoRA 推理合并：从零开销承诺到千适配器并发的工程现实

> **导读**：LoRA 原论文说推理时可以零开销合并权重，这个承诺在单适配器场景成立，但进入多适配器在线服务就不再成立。本文从合并的机制与精度出发，拆解"为什么不合并"引出多适配器切换的核心矛盾，落到 S-LoRA 如何用统一分页和异构批处理解决这个问题，再看 2025-2026 年的近期工作正在怎样改写这套格局。

2021 年 LoRA 原论文（Hu et al., arXiv:2106.09685）给出了一个简洁的推理公式：`W' = W₀ + (α/r)·B·A`。因为 `W₀` 和 `B·A` 形状相同，可以直接相加，合并后的权重就是一个普通的 `d×k` 矩阵，推理时一次标准矩阵乘法，相对全量微调模型零额外延迟。这个性质让 LoRA 在部署上比较灵活——一个基座模型携带多个适配器，推理时按需切换。

但"按需切换"在多适配器场景会遇到硬约束：合并方案无法跨适配器批处理。当系统需要同时服务 50 个、200 个、甚至 2000 个适配器时，合并往往不再是最优解。

## 合并的机制与精度

合并的操作本身不复杂。对每个应用了 LoRA 的线性层，预计算增量 `ΔW = (α/r)·B·A`，加到原始权重 `W₀` 上，保存合并后的权重，推理时不再需要加载 `A` 和 `B`。HuggingFace PEFT 的 `merge_and_unload()` 做的就是这件事：逐层调用 `get_delta_weight()` 计算 `transpose(B @ A) * scaling`，加到基础权重上，然后卸载适配器权重，返回一个不带 PEFT 包装的标准 transformers 模型。

问题出在精度上。`B·A` 的乘法在 fp16/bf16 下会引入舍入误差，如果基础模型是 4-bit 量化的（QLoRA 场景），合并后的增量会被重新量化回 4-bit，舍入误差更明显。正确的做法是：以 fp16 加载基础模型，合并，保存 fp16，最后才量化。PEFT 的 `merge_and_unload` 在 4-bit 路径下会先调 `dequantize_bnb_weight` 反量化，但这会显著增加显存占用，一个 7B fp16 模型大约 14GB。

另一个细节：CPU 上合并 fp16/bf16 adapter 时，PEFT 会自动 cast 到 fp32 计算再转回，因为部分 CPU 的 bf16/fp16 matmul 很慢。显存不足时，在 CPU 上合并是可靠策略。

合并多个独立训练的 LoRA 更棘手。`B₁A₁ + B₂A₂` 简单相加在任务差异大时性能骤降，因为不同适配器的参数方向可能冲突。TIES-Merging（Yadav et al., arXiv:2306.01708）用三步解决：trim（重置小幅变化参数）→ elect sign（解决符号冲突）→ disperse merge（只合并符号一致的参数）。DARE（Yu et al., arXiv:2311.03099）则随机丢弃 delta 参数的 p% 并重缩放 `1/(1-p)`，可消除 90-99% 冗余 delta。PEFT 的 `add_weighted_adapter()` 封装了 linear、TIES、DARE、ties_svd 等多种组合方式。

不同 rank 的 LoRA 合并时形状不匹配，不能直接相加。LoRA-LEGO（Zhao et al., arXiv:2409.16167）用 rank 聚类，Compress-then-Merge（arXiv:2606.03723）先把各适配器压缩到共享 r 维子空间再合并，保证输出仍是 rank-r。

## 多适配器切换：合并失效的场景

单适配器时合并几乎总是最优的——零额外延迟，推理路径与全量微调模型完全一致。但多适配器时，合并意味着为每个任务维护一份完整模型权重副本，存储开销从 MB 级（单个 adapter）跳到 GB 级（完整模型），而且无法跨适配器批处理。

更关键的是切换成本。假设系统按请求路由到不同适配器，合并方案需要在 GPU 上减去当前 `BA`、加上另一个任务的 `B'A'`。这个操作是内存受限的，整个权重矩阵读一遍再写一遍的开销不小。S-LoRA 的消融实验显示：只有 1 个适配器时合并更快，但超过 2 个后合并方案的性能下降，GPU 被闲置。

所以现代 Serving 系统选择不合并，而是把前向传播拆成两部分：

```
h = xW + xBA
```

`xW` 对所有请求共享，可以批处理；`xBA` 每个请求权重不同，无法与 `xW` 并进同一次 GEMM。因为 `r ≪ d`（典型 r=16，d=4096），`xBA` 的计算量不到 `xW` 的 1%，S-LoRA 在单张 A100 上的实测也印证了这一点：适配器从 5 个增加到 2000 个，吞吐只下降约 5%。如何把 `xBA` 跨适配器批量算完，成了后面所有系统的核心问题。

这个拆分引出了三个工程问题：

1. 适配器权重放哪里？
2. 不同适配器的请求如何批处理？
3. 如何隐藏适配器加载的 I/O 延迟？

## S-LoRA：统一分页与异构批处理

S-LoRA（Sheng et al., MLSys 2024, arXiv:2311.03285）是目前对这三个问题都给出答案的系统。它的核心设计是把 PagedAttention 的内存管理思想推广到适配器权重。

**统一分页**。vLLM 的 PagedAttention 把 KV cache 按固定页大小分页存储，按需分配回收，显著减少内存碎片。S-LoRA 发现适配器权重和 KV cache 有相同的结构特征：都是动态大小、非连续存储、按需加载。它设置页大小为隐藏维度 H，KV cache 的序列长 S 用 S 页，LoRA 权重 rank R 用 R 页，两者交错存储在同一个统一内存池。这种设计让 S-LoRA 在单张 A100 80GB 上服务 2000 个适配器，上限是主存大小而非显存。

**异构批处理**。不同请求使用不同 LoRA（不同 rank、不同权重），直接做 batch GEMM 需要大量 padding，硬件利用率差。S-LoRA 实现了 MBGMM（Multi-size Batched Gather Matrix-Matrix，Triton 实现，用于 prefill）和 MBGMV（Multi-size Batched Gather Matrix-Vector，修改自 Punica 的 kernel，用于 decode），能处理非连续内存、变 rank、变序列长度，无需 padding。

**张量并行策略**。多 GPU 场景下，LoRA 计算的通信成本是 `5(N-1)Br/N`，base 模型是 `2(N-1)Bh/N`（B 为 batch size，h 为隐藏维度）。因为 `r ≪ h`，LoRA 额外通信可忽略。S-LoRA 通过在小中间张量上调度通信、与 base 模型通信融合来实现。

调度层面，S-LoRA 用 adapter clustering 优先批处理同适配器请求，配合 early abort 准入控制保证 SLO。适配器全部存主存，动态预测机制基于等待队列预测下个 batch 需要的适配器并预取，重叠 I/O 与计算。

性能上，服务少量适配器时，S-LoRA 吞吐最高可达 vLLM-packed 的 4 倍、PEFT 的 30 倍。vLLM-packed 是 S-LoRA 论文构造的对照基线：当时的 vLLM 还不支持 LoRA，基线把适配器权重预先合并、在一块卡上并存多个 worker，受权重副本限制只能服务不到 5 个适配器。

代价是，S-LoRA 构建在 LightLLM 之上，定位是研究原型；适配器全部驻留主存，未命中时要经 PCIe 搬运，每次访问都要付一次 kernel 停顿和 host 侧拷贝。后来 PLoRA 对"所有已发表系统都在把适配器从 CPU 主存经 PCIe 搬来搬去"的批评，指向的正是这套机制共享的成本。

## 其他系统的设计选择

S-LoRA 是研究原型，生产系统则给出了另一套答案。

Punica（Chen et al., arXiv:2310.18547）是首个提出 SGMV kernel 的系统，核心创新是把 batch 中请求按 LoRA 模型分组，同组连续排列，kernel 并行化不同请求的特征-权重乘法。它比 S-LoRA 早约 9 天挂上 arXiv，S-LoRA 官方将两者并列为同期工作；Punica 的重心在 kernel 与集群级调度（自报集群吞吐提升 12 倍、每 token 延迟只增 2ms），但适配器权重仍需常驻显存，同时驻留的数量受显存限制，没有做主存分层管理。

LoRAX（Predibase）走生产化路线，核心能力有三项：

- 动态适配器加载：启动只加载 base 模型，适配器按请求 just-in-time 加载，不阻塞并发请求
- 分层权重缓存：GPU/CPU 之间异步预取与卸载
- 异构连续批处理

它的特色是 OpenAI 兼容 API，以及按请求合并多个适配器构造集成模型（ensemble）。

vLLM 的 LoRA 支持（v0.3.0+）用 LoRAManager 管理适配器，LRU cache 缓存到 GPU（`max_loras`）和 CPU（`max_cpu_loras`），LoRA 权重放在与 KV cache 分开管理的独立预分配 buffer（槽位池）。v0.6.1+ 支持运行时通过 REST API 动态加载适配器。关键参数 `max_lora_rank` 应设为实际最大值而非更高，因为 vLLM 按此预分配 buffer，设高浪费显存。

TensorRT-LLM 的约束更严格：如果 LoRA 应用到任一 attention 层（如 Q），engine 必须配置支持所有 attention 层（Q、K、V）的 LoRA。它的 `task_id` 缓存机制首次需要带上 weights+config，之后只需 task_id，cache 满时淘汰最旧 LoRA。

## 2025-2026 年的新变量

多 LoRA 服务的瓶颈正从 kernel 效率转向内存管理与架构解耦，下面四个工作各自动了不同的假设。

PLoRA（arXiv:2608.05483）用 CXL/NVLink 池化内存 + NDP（Near Data Processing）让适配器驻留在内存池，GPU 用 load/store 直接访问，仅返回归约结果。H100 上 1000 适配器平均 decode 延迟比 S-LoRA 低 6.6 倍，设备面积增加不到 3.4%。它证明短上下文下吞吐在链路带宽 32GB/s 时即饱和（CXL 3.1 的 1/4），近数据计算可替代链路带宽。

InfiniLoRA（arXiv:2604.07173）针对 MoE 架构的适配器内存爆炸问题，把 LoRA 执行从 base 推理分离到共享 LoRA Server，用 SLO 驱动的资源配置配合 GPU 主动发起的通信，严格延迟 SLO 下平均服务请求率提升 3.05 倍。

BD-LoRA（arXiv:2510.23346）在训练时给适配器因子施加块对角约束，从而消除张量并行 LoRA 服务的通信开销，8×A100 上 Llama-3.1-70B 端到端最高提速 1.79 倍，训练代码已并入 HuggingFace PEFT。代价是适配器必须按块对角结构训练，存量普通适配器无法直接受益；且 1.79 倍对应参数量压到 0.87 倍的配置，参数量升到 1.74 倍时提速仅 1.23 倍。

FastLibra（arXiv:2505.03756）发现 vLLM 静态划分 HBM（LoRA 占 0.2 比例）导致高达 46.5% 的无效 KV cache，提出依赖感知的 LoRA+KV 统一缓存，TTFT 降 63.4%，TPOT 降 40.1%。

以上数字均为各论文自报实验结果，评测基线与硬件不同，不宜直接横向比较。

## 回到决策

LoRA 推理侧的工程选择，本质上是一系列存储换延迟、内存换吞吐的权衡。单适配器低延迟场景，合并仍然是最优解。多适配器在线服务，保留适配器权重、用专用 kernel 做异构批处理是主流方向。当适配器数量从百级跳到千级，内存管理成为瓶颈，统一分页的思想尚未被生产系统完整采纳——vLLM 用的是与 KV cache 分开管理的独立 buffer 池，而不是与 KV cache 交错存储，S-LoRA 本身也停留在研究原型阶段。中小规模不必自建，直接用 vLLM 的多 LoRA 或 LoRAX 即可。PLoRA 代表的池化内存方向，要等 CXL 池化内存与 NDP 硬件普及（NVLink 在 GPU 服务器内部已是常规配置，真正缺的一环是前者），才可能成为下一个拐点。

前作讲低秩假设如何驱动训练侧的工程创新，那里也接受了原论文的合并承诺，称切换"开销极小"，本文用消融数据修正它。LoRA 的故事从"一个矩阵乘积能替代百万参数"开始，目前写到了"如何让一个基座同时服务数千个矩阵乘积"。训练侧的哲学是把参数做小，推理侧的哲学不再是消除开销，而是管理和摊薄开销。
