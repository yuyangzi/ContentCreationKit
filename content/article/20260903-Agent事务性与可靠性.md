# Agent 事务性：当 checkpoint 靠不住时，如何保证一致性

> **导读**：2026 年 8 月，一篇名为《Resume Means Resume》的论文用形式化方法验证了五个主流 Agent 框架的恢复语义，结果其中没有任意两个给出同样的保证。这不是实现差异，而是概念空白——checkpoint 恢复不等于安全恢复，工具调用不等于原子操作，重试不等于无害操作。这篇文章从框架对比出发，追踪一个正在浮出水面的共识：Agent 需要的是语义级事务保证，而不是存储级状态快照。

2026 年 8 月 4 日上线的 arXiv 论文《Resume Means Resume: A Machine-Checked Conformance Contract for Checkpoint, Interrupt, and Resume Semantics in Workflow Persistence Layers》（arXiv:2608.03836）做了一件看似无聊但影响深远的事。

它定义了检查点恢复应该满足的六条性质，然后用一个确定性的、不依赖 LLM 的测试 harness 实测了五个 pin 住版本的框架——LangGraph 1.2.9、LlamaIndex Workflows 2.22.2、CrewAI 1.15.2、pydantic-graph 1.x 和 AutoGen AgentChat 0.7.5。

LangGraph 同一个 API 在中断恢复时表现为恰好一次（exactly-once），在崩溃恢复时表现为至少一次（at-least-once）。CrewAI 会重新执行已完成的副作用方法。pydantic-graph 节点中途崩溃后干脆无法恢复。

所测的五个框架中，没有两个共享同一幅一致性画像。论文明确声明这一结论不外推到整个生态。

这不是哪个框架写错了，而是一个更根本的问题：Agent 框架的 checkpoint 解决的是崩溃恢复，而 Agent 需要的是语义恢复。这两件事大多数时候重叠，但在生产环境的边界条件下，它们的差距足以让你怀疑人生。

---

## 框架 checkpoint 横评：存储原语不等于可靠保证

先看当前主流 Agent 框架在状态持久化上的实际能力：

| 能力 | LangGraph 1.2+ | CrewAI 1.15+ | MAF（SK+AutoGen 后继） | Google ADK | AWS Strands |
|------|:---:|:---:|:---:|:---:|:---:|
| 每步状态快照 | ✅ superstep 边界 | ⚠️ task replay | ✅ superstep | ✅ SessionService | ❌ 仅会话历史 |
| 节点内写入恢复 | ✅ per-task writes | ❌ | ⚠️ 手动 | ❌ | ❌ |
| 崩溃后自动恢复 | ❌ 需外部编排 | ❌ | ❌ | ❌ 调用方负责 | ❌ |
| 重复执行防护 | ⚠️ 仅中断场景 | ❌ | ❌ | ❌ | ❌ |
| 并发 fencing token | ❌ | ❌ | ❌ | ❌ | ❌ |

表中 superstep 指 Pregel 类执行模型的并行执行单元：同一轮并行运行的节点打包为一个 step，快照就落在这个边界上。

数据来自 Diagrid 2026 年 2–3 月的源码级横评系列（《Still Not Durable》等两篇）、RESUME CONTRACT 的形式化验证，以及 LangGraph 官方 checkpointer 文档（per-task writes 条目）。

看完这张表会发现一个结构性事实：**框架 checkpoint 是存储操作，不是可靠性保证**。

Diagrid 在对比分析里写得很直白：LangGraph、CrewAI、ADK、MAF、Strands 都做了状态保存，但失败检测（watchdog/heartbeat）、自动重启、重复执行防护全部留给开发者自己。

框架负责"记住你在哪"，但不负责"确保你在正确的状态继续"。

源码级分析还发现了更隐蔽的问题：MAF 的恢复需要调用方手动传 `checkpoint_id`，且没有 fencing token（防止多个进程同时续跑同一状态的令牌机制），两个进程可以同时恢复同一 checkpoint；同一 superstep 内若有三个 executor 并行，两个成功、一个失败，三者全部重跑。

ADK 的恢复同样由调用方负责，续跑时要手动找回正确的 `invocation_id`。

## 状态层的两个断层：内部状态与外部状态

先从一个具体的失败场景讲起：一个 Agent 正在执行扣款任务，调用支付 API 后网络超时，但支付实际已成功。Agent 重试，第二次调用再次扣款。

即使不重试，仅 checkpoint 恢复也可能出事：Agent 在步骤 3 崩溃，恢复后从步骤 3 的 checkpoint 继续，但步骤 1 和步骤 2 已经产生的外部副作用（邮件已发、日志已写、webhook 已触达）无法撤回。

《Safe to Resume?》（arXiv:2608.29381，2026-08-29）把这类问题系统化为五种恢复失败模式，落到状态层是两类断层：

**内部状态覆盖不全**：大多数框架只保存消息历史和节点输出。恢复后 Agent "知道自己在哪"，但不知道"为什么在这"。

**外部状态失配**：已执行的副作用（文件写入、API 调用、数据库变更）没有纳入 checkpoint 语义。恢复后这些副作用已完成，但 Agent 不知道它们已完成，可能重做或跳过。

同一论文展示了三个端到端攻击：在 LangGraph 上实现双重支付、在 Cline 上实现未授权邮件转发、在 Hermes 上绕过恶意软件验证。攻击手法都一样——利用 checkpoint 恢复和外部副作用之间的语义间隙。这不只是实验室问题：论文引用的一项 2026 年企业调查显示，79% 的受访者曾回滚 Agent 操作，42% 报告因 Agent 失败造成收入损失（第三方引述）。

## 语义一致性：不只是数据对，是结果对

框架 checkpoint 解决的是"崩溃后能从哪继续"，但 Agent 真正需要的是"继续后结果是对的"。这个差距催生了 2026 年一个重要的理论方向：把事务语义从数据层提升到任务层。

清华数据库组在 2026 年 8 月 14 日发布的《Agentic Transaction: Towards ACID-Compliant Agent Systems》（arXiv:2608.13900）首次系统化地把经典 ACID 重释为四个语义级保证：

> **Semantic Atomicity**（语义原子性）：一次"探索-执行-验证"周期作为事务单元，只有通过验证的效果才提交，失败步骤回滚或补偿。不是每一步都原子，而是"提交边界"原子。
>
> **Semantic Consistency**（语义一致性）：执行轨迹可以非确定（LLM 采样本身就不确定），但提交结果必须满足任务目标、执行约束和可用证据。
>
> **Semantic Isolation**（语义隔离）：并发 Agent 事务不得产生语义无效的相互干扰。冲突不止是读写冲突，还包括 prompt 覆盖、记忆污染、工具预算争夺、中间产物覆盖。
>
> **Semantic Durability**（语义持久性）：提交后的效果、证据和恢复元数据跨故障持久，可以脱离瞬时 LLM 上下文独立重建与审计。

形式化地，一个 agentic transaction 定义为：

```
τ = ⟨r₁, r₂, …, rₙ⟩
每步 rᵢ = (cᵢ, aᵢ, fᵢ)
  cᵢ = LLM 上下文（含可用工具集 T 与技能集 S）
  aᵢ = Agent 动作（调用工具或技能）
  fᵢ = 环境反馈
τ 仅在满足任务条件与语义不变量时提交
```

在 KramaBench 上，ACID-Agent 比 Claude Code 等 SOTA 方案高 10.6%（论文自述为初步结果，验证集中在数据 Agent 场景）。消融实验里，"失败步骤隔离"移除后分数降 11.7%（限 KramaBench 的 Environment 域），说明失败状态污染后续执行是真实问题，不是理论假设。

## 并发隔离：多 Agent 共享资源时锁不住

Semantic Isolation 在单 Agent 场景下可以视作退化成语义一致性，但在多 Agent 协作时它变成了真正的挑战。

上海交大 IPADS（陈海波团队）的 CoAgent（arXiv:2606.15376，2026-06-13）研究了一个典型场景：多个 Agent 同时操作同一个 git 树、同一份文档、同一组 Kubernetes 资源。经典并发控制方案在这里几乎失效。

两阶段锁（2PL）会锁住推理区间，Agent 一次推理可能跨越几分钟，这把锁会阻塞所有触碰重叠状态的 Agent，论文实测每轮试验平均死锁 0.81 次，几乎换不回加速。乐观并发控制（OCC）的冲突回滚代价太高——Agent 已经花了大量 token 生成的代码和文档，回滚意味着这些计算全部作废。

CoAgent 提出的 MTPO 协议（Monotonic Trajectory Pre-Order，单调轨迹预序）做了三件事：启动时固定序列化顺序；运行时允许投机写，冲突发生时由运行时通知相关 Agent 重新判断自己的哪些计划前提受影响；修复用 Saga 风格（长事务的补偿式回滚模式）的逆操作，而非整体回滚。在 bash 操作场景下，pass rate 从 45/71 提升到 63/71。

但 MTPO 有两个前提。一是工具要注册 undo 能力，现实是大多数工具 API 并没有逆操作可注册——一个 `git commit` 可以 `git revert`，但 `rm -rf` 没有逆操作，已发出的邮件也无法撤回。二是它假设 Agent 收到冲突通知后能正确判断哪些在途动作受影响，论文实测 LLM 的误判率约 5%。

《Revisable by Design》（arXiv:2604.23283）提出了一个更基础的理论框架。它原本为流式执行中"用户中途修订"的问题而建，但其可逆性分类同样约束并发补偿：每个 Agent 动作按恢复代价分层：

```
Idempotent ⊂ Reversible ⊂ Compensable ⊂ Irreversible
（幂等）    （可逆）     （可补偿）    （不可逆）
```

核心结论：**Agent 的灵活性受其可逆性边界约束**。冲突的可补偿动作必然产生适应成本；冲突的不可逆动作使得完整规格满足在理论上不可能。这是动作空间的性质，与算法无关。

这条定理的工程推论是：设计 Agent 工作流时，应该先做可逆性分类，再决定哪些动作可以并行、哪些必须串行、哪些之前需要人工审批门。

## 恢复语义的形式化：六个性质，实测无一一致

回到 RESUME CONTRACT。论文定义的六条恢复性质是：

1. **prefix continuation**：恢复后从正确位置继续
2. **effect exactly-once**：副作用恰好执行一次
3. **fork determinism**：从同一 checkpoint 恢复的多次运行结果一致
4. **checkpoint validity**：checkpoint 状态本身可恢复
5. **consume-once**：外部资源只被消耗一次
6. **recovery determinism**：恢复行为可复现

对照这六条性质，五个框架没有给出两份相同的符合性画像。

形式化验证在这条线上不止一家。《Verified Detection and Prevention of Concurrency Anomalies》（arXiv:2606.17182，2026-06-15）用 TLA+（一种面向并发协议的规约与验证语言）形式化了四种并发异常，并复现了 ByteDance deer-flow 的静默丢失更新和 LangGraph ToolNode 的工具效应重排。

前者是真实复现的缺陷，其余异常在论文中为按架构模式构造的验证场景，但都指向框架设计层面的问题，而非偶发 bug。

## 工程上的四层防御

理论正在收敛，但你的 Agent 今天要上线。四层防御是综合上述研究得到的一个务实分层。

**状态层**：checkpoint 粒度到节点内写入而非仅 super-step 边界。LangGraph 的 per-task writes 机制做到了这一点——同一 super-step 内某节点失败时，其他成功节点的写入已持久化，恢复时无需重算。恢复时用 `invoke(None, config)` 加同一 `thread_id`，不要重新传入原 state。

**副作用层**：所有外部写操作走幂等键（为每次操作生成唯一标识，后端保证至多执行一次）。key 从持久状态派生（`{workflowRunId}:{stepId}`），而非 task attempt ID。DB 用唯一约束 + 原子 upsert（存在即忽略或更新，不存在才插入）：`INSERT ... ON CONFLICT (key) DO NOTHING`，冲突则读取缓存结果重放。

**故障层**：重试只针对瞬时错误。LangGraph 默认 `retry_on` 就不重试 `ValueError/TypeError/RuntimeError` 等编程类异常，HTTP 库异常只重试 5xx——自定义策略时保持这个方向即可。

超时用 `run_timeout`（硬墙钟）+ `idle_timeout`（空闲心跳），长任务内显式调用 `runtime.heartbeat()`。

熔断：连续 N 次失败后快速失败，避免对已宕机下游持续重试。

**一致性层**：多步骤副作用用 Saga，补偿注册在步骤执行之前。用状态字段记录"哪些步骤真正完成"，补偿只 undo 实际执行的步骤、按逆序执行。补偿本身必须幂等。

## Durable Execution：运行时接管工作流生命周期

如果四层防御还是太繁琐，有一个更彻底的方案：让运行时接管工作流生命周期。

Durable Execution（持久执行）的核心思想是：运行时自动把工作流每一步 checkpoint 到数据库，进程崩溃/重启/重部署后从最后完成点恢复，已完成的步骤不重复执行。Temporal、DBOS、Restate、Inngest 是这一类的代表。

2025 年末到 2026 年，Durable Execution 从小众方案变成生产 Agent 基础设施的重要选项。Temporal 在 2026 年 2 月完成 3 亿美元 Series D，估值 50 亿美元。

AWS Lambda Durable Functions、Cloudflare Workflows、Vercel Workflow SDK（原名 Workflow DevKit）等厂商也陆续落地同类能力。

Pydantic AI 官方支持 4 种 durable execution（Temporal / DBOS / Prefect / Restate）。DBOS 走了一条更激进的路线——基于 Postgres 的持久执行，不需要新基础设施。

但 Durable Execution 有一个前提条件：LLM 调用必须记录输出而非重放时重算。这是确定性运行的必然要求，也是它和 Agent 非确定性本质的固有张力。工程上的解法是把模型调用、工具调用这类不确定操作卸载到运行时的 activity 层执行，工作流代码只保留确定性的协调逻辑——输出一旦记录，重放就不再多花一分钱。

## 理论还在追，问题已经在发生

Agent 事务性这个领域正在经历一个典型的"工程问题驱动理论建设"周期。2025 年的 SagaLLM（arXiv:2503.11951）和 MAST 失败分类学（arXiv:2503.13657）从工程踩坑中提炼模式。

2026 年的 CoAgent、RESUME CONTRACT、ACID-Agent 开始提供形式化框架。2026 年 7 月的 MCP 规范大改引入 Tasks 扩展（durable handles），把事务性责任部分下放到了协议层。

**checkpoint 在大多数情况下只是保存点，不是事务边界。大多数工具调用不是原子的，只是函数调用。大多数重试不是安全的，只是重复执行。** 认识到这件事，比选择哪个框架更重要——第一步不是换更贵的 checkpointer，而是给每个外部副作用配幂等键、给每段工作流划清提交边界。
