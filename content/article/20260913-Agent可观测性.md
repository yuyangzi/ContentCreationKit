# Agent 可观测性：为什么报错的那一步往往不是根因

> **导读**：多 Agent 系统最贵的 bug，报错点往往不是根因。本文从一次典型的级联失败讲起，拆开可观测性的数据模型、OpenTelemetry GenAI 语义约定、跨 Agent 的上下文传播，以及失败归因这条正在快速成熟的研究线。

多 Agent 系统最难查的失败，通常发生在报错的那一步之外；更麻烦的是，有些失败全程没有任何一步报错。

设想一条三层的研究流水线：orchestrator（编排 Agent）接到任务后拆解，researcher（检索 Agent）负责搜索与整理，writer（成稿 Agent）负责落笔。某天产出的报告里出现了一个错误的数字。writer 没有报错，模型照常生成；researcher 也没有报错，检索和摘要接口都返回了 200。日志里只有一排成功的记录。

单 Agent 时代也有类似的事故，多 Agent 只是把它放大了。Fiddler AI 把这类问题归纳为 **handoff（交接）失败**：Agent A 把不完整或错误的上下文交给 Agent B，B 基于错误前提继续往下走，报错点落在下游，根因留在了上游。你手里的日志能证明每个服务都活着，却证明不了"它为什么走到了这一步"。

结构化 trace 要解决的，就是这个"重建现场"的问题。

---

## 日志和 APM 的失明

传统 APM 和日志系统是给确定性系统设计的。同一个输入产生同一个输出，每次调用走同一条代码路径，于是"请求返回 200"就足以说明请求成功了。Agent 把这几条假设逐条推翻。

1. **非确定性**：同一段 prompt，不同运行可能选出不同的工具序列、不同的推理路径。一次延迟上涨未必是故障，也可能是模型选了更贵但更对的路径。
2. **复合操作**：一次用户请求背后可能是十次 LLM 调用、五次工具执行、两次检索，每次都有自己的延迟、token 和失败模式，而传统 tracing 只抓一跳。
3. **token 成本是运行时变量**：一个本该 3000 token 回答的问题烧掉 50000 token，这既是账单问题，也是行为异常信号。没有 per-span 的 token 记账，它不可见。
4. **静默失败**：Agent 返回了 HTTP 200，结果却是错的。系统视角看起来正常，语义层面已经跑偏。

这四条指向同一个结论：可观测性要回答的不是"有没有报错"，而是"它为什么走到了这一步"。

> 传统监控能告诉你 Agent 服务还活着，Agent 可观测性才能告诉你它有没有调错工具、传错参数、检索到错误的记忆、偏离原始计划。

落到数据结构上，一次 Agent 运行可以拆成四类 span，每一类对应一种典型失败：

- **tool call（工具调用）**：工具名、参数、原始返回、耗时、重试次数、错误状态。抓"幻觉参数"和"静默重试循环"。
- **reasoning（推理步骤）**：模型的计划、选定的动作、观察到的结果、下一步的决策。抓计划漂移和错误分支。
- **state transition（状态转移）**：每一步前后的工作记忆，包括上下文裁剪和 handoff 载荷。抓上下文丢失和摘要漂移。
- **memory operation（记忆操作）**：长期记忆的读写、检索命中的条目、相关度分数、新鲜度。抓陈旧读取、错误实体检索、跨用户记忆泄漏。

这四类 span 拼在一起，才是一份能重建行为的记录。

## 把一次执行拆成一棵可以重建的树

可观测性的基本单位是 **trace（一次完整执行链路）** 和 **span（链路中的一个操作片段）**。span 之间用 parent-child 关系嵌套，构成一棵树。你不需要自己拼父子关系，框架或 instrumentation（埋点/自动插桩）在创建 span 时就把链路搭好了。

对 Agent 来说，这棵树有几个标准节点。OpenTelemetry 的 GenAI 语义约定把 `gen_ai.operation.name` 定义为一组固定取值：`chat`（模型调用）、`invoke_agent`（Agent 运行）、`execute_tool`（工具执行）、`embeddings`（向量化）、`retrieval`（检索），以及较晚加入的 `create_agent`、`invoke_workflow` 等。用 Python 手动埋点，一次带工具调用的 Agent 运行大致长这样：

```Python
from opentelemetry import trace

tracer = trace.get_tracer("agent-runtime")

# 根 span：一次 Agent 运行
with tracer.start_as_current_span(
    "invoke_agent research-agent",
    attributes={
        "gen_ai.operation.name": "invoke_agent",
        "gen_ai.agent.name": "research-agent",
    },
) as agent_span:
    # 子 span：模型规划（start_as_current_span 会自动挂到当前 span 下）
    with tracer.start_as_current_span("chat deepseek-v4.1-flash") as llm_span:
        llm_span.set_attribute("gen_ai.operation.name", "chat")
        llm_span.set_attribute("gen_ai.provider.name", "deepseek")
        llm_span.set_attribute("gen_ai.request.model", "deepseek-v4.1-flash")
        response = client.chat.completions.create(model="deepseek-v4.1-flash", messages=messages)
        # token 记账落在 span 上，成本和行为一起被看见
        llm_span.set_attribute("gen_ai.usage.input_tokens", response.usage.prompt_tokens)
        llm_span.set_attribute("gen_ai.usage.output_tokens", response.usage.completion_tokens)

    # 子 span：工具执行
    with tracer.start_as_current_span("execute_tool web_search") as tool_span:
        tool_span.set_attribute("gen_ai.operation.name", "execute_tool")
        tool_span.set_attribute("gen_ai.tool.name", "web_search")
        result = web_search(query)
```

渲染出来是一棵可以直接扫描的树：

```
invoke_agent research-agent
├── chat deepseek-v4.1-flash           ← 模型决定搜索
├── execute_tool web_search             ← 执行搜索
├── chat deepseek-v4.1-flash           ← 用结果继续推理
├── execute_tool summarize              ← 摘要
└── chat deepseek-v4.1-flash           ← 生成最终答案
```

一眼能看出这个 Agent 调了三次模型、两次工具、哪一步最慢；点开任何一个 span 都能看到完整属性。

## 语义约定：一个还没定稿、却已经值得下注的标准

早期每个 tracer 都发明自己的字段名，同样的模型调用在 A 工具里叫 `model`，在 B 工具里叫 `model_name`，换后端就要重写解析逻辑。OpenTelemetry 的 GenAI 语义约定把这套词汇统一到了 `gen_ai.` 命名空间下。

核心属性包括 `gen_ai.provider.name`（`openai`、`anthropic`、`aws.bedrock` 等）、`gen_ai.request.model`（请求的模型）、`gen_ai.response.model`（实际响应的模型）、`gen_ai.usage.input_tokens` 与 `gen_ai.usage.output_tokens`。provider 和 model 刻意分开，因为同一个模型可以经由不同 provider 提供，而 provider 决定了哪些专属属性该出现。

这个标准还在快速变动。2025 年下半年以来，几乎每次发布都动了 GenAI 部分：

| 版本 | GenAI 相关变化 |
|------|----------------|
| v1.37 | `gen_ai.system` 改为 `gen_ai.provider.name`；多轮对话从"每条消息一个 event"改为聚合属性 `gen_ai.input.messages` / `gen_ai.output.messages` |
| v1.38 | 评测事件、工具定义与调用详情、`invoke_agent` 的 span kind（span 类型）指引 |
| v1.39 | MCP 语义约定，用于接通 Agent 侧与 MCP server 侧断裂的 trace |
| v1.40 | retrieval span、cache token 属性 |
| v1.41 | `execute_tool` span 名必须含工具名、reasoning token、`invoke_workflow`、`invoke_agent` 拆分 CLIENT/INTERNAL |
| v1.42 | GenAI、OpenAI、MCP 三组约定整体迁出主仓库，进入独立的 `semantic-conventions-genai` |

到 2026 年 8 月，GenAI 与 MCP 约定仍处于 Development 状态，没有 stable 时间表。2026 年 5 月这套约定建起独立仓库 `semantic-conventions-genai`，6 月随 v1.42 发布完成迁移，为的是能独立迭代版本。

> OTel GenAI 语义约定还没定稿，但它已经是当前少有的、能让 trace 跨后端迁移的选择。在一个字段名会变的标准上长期建 dashboard 是有风险的，把数据锁死在某个厂商的私有 SDK 里，风险更大。

标准之外，内容捕获是另一个需要提前想清楚的问题。prompt 和 completion 既是调试时最有价值的数据，也是最敏感的数据。规范给了三种模式：

1. 默认不记录
2. 记录在 span attribute 上，方便但有体积和权限问题
3. 外置存储（S3 等），只在 span 上留下引用 URL

生产环境通常走第三种，因为它能独立设置 IAM 和留存策略，也能通过 `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` 之类的开关整体关闭内容捕获。

生态侧也在往这个方向收敛。Datadog 是较早原生支持 v1.37+ 约定的商业平台，Langfuse、Arize Phoenix 等开源后端也对齐了 `gen_ai.*`。2026 年初的两笔整合动作（ClickHouse 在 1 月 16 日宣布收购 Langfuse，Cisco 在 4 月宣布收购、5 月完成交割 Galileo）是可观测性工具并入数据平台的两个信号。对所有选型者来说，直接含义只有一条：埋点尽量贴着标准走，后端随时可以换。

## 多 Agent：报错点不是根因

researcher 在第三轮检索时丢掉了一段原始约束，交给 writer 的 handoff 载荷里没有它，writer 于是基于不完整的前提写出了错误数字。writer 的输出语法正确、逻辑自洽，破绽在于数字。没有跨 Agent 的 trace，负责调试 writer 的人看不到根因在上游。

要接通两个 Agent 的 trace，靠的是 **context propagation（上下文传播）**。W3C Trace Context 定义了一个 `traceparent` 头，里面是 trace ID 和当前 span ID。上游把 context 注入到发给下游的消息里，下游取出后新建的 span 沿用同一个 trace ID、生成新的 span ID，于是跨进程、跨服务的两段执行落进同一棵树。OpenTelemetry 的 `inject` / `extract` 就是干这个的，下游 span 随之成为上游的**子节点**：

```Python
from opentelemetry import trace
from opentelemetry.propagate import inject, extract

# 上游 Agent：把当前 trace context 注入到发给下游的消息头里
def send_to_downstream(payload: dict, downstream_url: str):
    headers = {}
    inject(headers)  # 写入 traceparent / tracestate
    requests.post(downstream_url, json=payload, headers=headers)

# 下游 Agent：从消息头恢复 context，作为子 span 接上同一棵树
def handle_from_upstream(request):
    context = extract(request.headers)
    with tracer.start_as_current_span("invoke_agent writer-agent", context=context):
        ...
```

业务维度的信息（会话 ID、租户 ID、用户 ID）走 **baggage（随链路传播的键值上下文）**。baggage 是一个随 trace 传播的键值存储，但它不会自动变成 span 属性，需要配一个 baggage span processor，按配置的键名匹配规则把匹配的键复制到属性上，否则你在 trace 里看不到它。

```Python
from opentelemetry import baggage

# 上游：把会话 ID 放进 baggage，随 trace 一起传播
baggage.set_baggage("session.id", session_id)

# 下游任意位置：取出同一个会话 ID
session_id = baggage.get_baggage("session.id")
```

MCP（Model Context Protocol）调用是另一处容易断链的地方。Agent 侧和 MCP server 侧各自产生 trace，中间没有传播，看起来就是两段无关的执行。OTel 在 v1.39 补上了 MCP 语义约定，通过 `mcp.method.name`、`mcp.session.id` 等属性，以及把 trace context 放进 JSON-RPC 的元数据，把两侧的 span 连成一棵树。规范还处理了去重：如果外层 GenAI instrumentation 已经记录了工具执行，MCP instrumentation 只补充 MCP 专属属性，不重复建 span。

多 Agent 的 trace 树，会在 handoff 处展开出下游 Agent 的 invoke_agent。父子关系取决于传播方式：下游直接收到上游注入的 context 时，它就是上游 span 的子节点；若 handoff 由 orchestrator 转发，两个子 Agent 都挂在 orchestrator 下，上游到下游的数据依赖改用 span link 记录。下面是一棵 orchestrator 转发的树：

```
invoke_agent orchestrator (trace=t1)
├── chat deepseek-v4.1-flash           ← 决定拆解任务
├── invoke_agent researcher
│   ├── chat deepseek-v4.1-flash
│   ├── execute_tool web_search
│   └── execute_tool summarize
├── invoke_agent writer                 ↳ span link → researcher（handoff 数据依赖）
│   └── chat deepseek-v4.1-flash       ← 收到不完整的 handoff 载荷
└── chat deepseek-v4.1-flash           ← 汇总输出
```

**handoff 应该被当作服务边界来记录**，把交接的输入、输出和时序都落到 span 上，而不是只记一个"移交成功"。**span link（跨度链接）** 用来表达非父子关系，例如 orchestrator 转发 handoff 时 researcher 到 writer 的数据依赖，或两个并行子 Agent 之间的因果引用；当 Agent 出现循环（Agent loop）把 span 树压成一条长链时，link 往往是保住可读性的关键。

## 失败归因：让机器说出"是哪一步错了"

多 Agent 调试的难点不只是看不见，而是看见了也归不了因。一条几十步、多个 Agent 交织的 trajectory（轨迹），人类工程师靠肉眼定位错误步骤的效率和准确率都很有限。2026 年，自动失败归因（failure attribution）的论文产出明显增多。

| 方法 | arXiv | 做法 | 关键数字 |
|------|-------|------|----------|
| Who&When | 2505.00212 | 首次把"定位责任 Agent 与决定性步骤"形式化为研究任务，发布 127 个多 Agent 系统的失败日志数据集 | 最强方法定位责任 Agent 准确率 53.5%，定位错误步骤仅 14.2%；o1、DeepSeek R1 也达不到可用水平 |
| AgentTrace | 2603.14688 | 从执行日志重建因果图，从错误现象反向追溯，调试时不需要跑 LLM | 亚秒级延迟；论文报告定位效果优于启发式和 LLM 基线 |
| AgentDebugX | 2607.18754 | 把调试组织成 Detect-Attribute-Recover-Rerun 闭环，DeepDebug 做多轮根因诊断 | 在 Who&When 基准上严格归因 28.8%（qwen3.5-9b 底座，最强单遍基线 21.7%）；GAIA 上单次重跑修复 13/73 个失败任务，整体准确率 55.8% 提升到 63.6% |
| OAT | 2607.12747 | 只用成功轨迹训练（单类学习 + 神经受控微分方程），推理时给失败轨迹的每一步打异常分 | 比 prompt 基线快 200–5000 倍，域内 F1 提升 20%、域外 7% |
| 综述 | 2606.04990 | 把 execution provenance（执行溯源）定义为 Agent 执行的类型化图，证据追溯是其投影 |  |

同一方向上，FALAT 用依赖图引导搜索来定位 trajectory（轨迹）中的决定性错误步骤（arXiv:2606.00765），可视为这条线在另一组假设下的分支。

定位"哪个 Agent 出问题"明显比"哪一步出问题"容易，但两者离可用都还有距离（14.2% 意味着几乎不可用）。路线也在分化：一条是用更强的模型做提示式诊断（AgentDebugX），另一条是绕开逐步人工标注，用因果结构或成功轨迹的分布来做轻量检测（AgentTrace、OAT）。后者的吸引力在于便宜和快，因为对多数生产团队来说，调试即调用前沿模型的成本难以为继。

这些仍是研究前沿，不是可以直接装上就用的生产工具。工业界目前的主要手段还是"trace 树 + 人工排查 + 评测分数"三件套，自动归因更多是加速，还谈不上替代。

## 让 trace 反哺评测

可观测性和评测常被当成两件事，其实是同一条数据链的两端。线上 trace 记录的是"实际发生了什么"，评测回答的是"这样做算不算好"。中间的桥是把 trace 沉淀成数据集。

OTel 为此定义了 `gen_ai.evaluation.result` 事件，用 `gen_ai.evaluation.score.value` 和 `gen_ai.evaluation.score.label` 承载评分结果。一个相关度评估器可以返回 `score.value=0.85`、`score.label="relevant"`，直接挂到当时那条 trace 上。闭环大致是：

1. 线上 trace 全量采集，异常链路（报错、低分、超阈值）优先保留
2. 把失败 trace 转成评测样例，补上期望输出
3. 用 LLM-as-judge 或人工打分给样例标注
4. 新版本上线前跑这批样例，分数退化就挡住合并

这样做的价值在于，评测集不再是拍脑袋想出来的，而是从真实失败里长出来的。Braintrust 把这条思路概括成"evals 是新的 PRD"，核心并不是口号，而是承认了一件事：Agent 的行为边界，只有从生产 trace 里才看得清。

---

## 五条当下的工程建议

1. **优先 instrument，而不是手写 tracing handler。** OpenAI SDK 的 `opentelemetry-instrumentation-openai-v2` 是目前最成熟的 GenAI instrumentation，OpenLLMetry 覆盖 Anthropic、Bedrock 等，DeepSeek 则可经 OpenAI 兼容接口复用同一套埋点。手写 handler 在并行调用时很容易把 `parent_run_id` 搞混，只在需要业务特有信号时才自定义。
2. **控制 span 粒度和基数。** 每个 LLM 调用、每个工具调用各自成 span 就够了，不要给每个检索 chunk 单独建 span，也不要把用户原始输入塞进 span attribute。基数爆炸会让存储和聚合查询一起失效。
3. **用尾部采样，而不是头部采样。** 深度 Agent 链一次运行会产生几十个 span，头部 1% 采样会丢掉 99% 的失败链路。较稳妥的做法是 100% 保留 ERROR、低分、超延迟或超成本阈值链路，其余 5% 到 20% 均匀采样，逻辑放在 collector 端执行。
4. **内容外置存储，属性只留引用。** prompt 和 completion 放对象存储，span 上只留 URL，权限和留存独立管理；需要临时排查时再按引用拉取，避免敏感内容默认进入 trace 存储。
5. **在埋点的一开始就把 trace 当评测数据源设计。** 从第一天起就带上 `session_id`、`user_id`、`strategy_id` 这类业务标识，后面才可能做"某类工具在某类用户上失败的链路"这种查询，否则 trace 只能一条条看。

---

## 三个反复出现的误区

1. **把 logging 当 tracing。** 日志是平铺的事件流，没有 parent-child 结构，无法重建因果。可观测性的最小要求是一棵可查询的树，不是一堆可搜索的字符串。
2. **只监控 LLM 调用，忽略工具、检索和记忆。** 大部分事故发生在工具层和检索层：参数幻觉、检索到陈旧记忆、上下文在裁剪时丢失。只盯模型调用，等于只监控了一半的执行。
3. **把 evals 和 observability 混为一谈。** 一个是重建执行（发生了什么），一个是打分（做得好不好）。少了任何一个，另一个的价值都会打折：没有 trace 的评测脱离真实分布，没有评测的 trace 无法判断对错。

## 回到那条级联失败的流水线

再回到开篇的事故。在这条链路上，修复它不依赖更聪明的模型，而是三样东西：researcher 到 writer 的 handoff 载荷被完整记录成 span，两个 Agent 的 trace 落在同一棵树上，失败 trace 被沉淀进评测集并在下一次改动时被重跑。数字错误的根因因此变得结构性可定位。

这条路径今天已经可以走通，起步动作也不复杂：先接上 OpenAI SDK 的 instrumentation（自动埋点）拿到标准 span，再用尾部采样控制成本，最后把异常 trace 导出成评测样例。这里的"走通"指人工排查路径，自动失败归因仍待成熟。真正需要判断的，是应不应当在还没 stable 的标准上下注。当 `gen_ai.*` 的属性名随时可能改，厂商私有 SDK 看起来更稳，但它换来的是把数据锁死在一处的长期代价。对一线开发者来说，贴着标准埋点、保持后端可替换，是当前风险更低的一个选择。
