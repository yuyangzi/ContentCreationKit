# 口径文档还是确定性编译器：语义层落地的两条路径

> **导读**：智能问数的主流答案是语义层，但这个词同时指着两样东西：一份塞进 prompt 的口径文档，和一套带编译器的指标建模系统。两者的成本和失败方式完全不同。选错形态，建层的钱大概率白花。

PostHog 在 2026 年 8 月记录过一个场景：拿同一个问题（上个月 MRR 是多少）去问 Claude、Cursor 和自家 PostHog AI，三个入口返回三个查询、三个数字，一个汇总了 Stripe 表，一个找到另一张略有出入的 Stripe 表，还有一个试图从原始事件重构经常性收入，按比例分摊算错了。每个方法、每个数字看上去都合理，但没法判断哪个对。

比数字对不上更麻烦的是第二个症状：语义层上线之后，分析师绕开它继续写裸 SQL。dbt Labs 踩坑文里用了 shadow analytics（影子分析）这个词，它是语义层项目走向失败的标准路径之一，道理也直白，可选的治理等于没有治理。

两个症状指向同一件事：口径没有唯一正典，或者正典没有被强制执行。《智能问数方案》那篇收在分层协作的判断上，语义层具体怎么落地只带过一句。而"语义层"这三个字本身，同时指着两样东西。

---

## 一、两组实验与一条分界线

2026 年 4 月有两组基准几乎同时发布，结论方向一致，但各自的"语义层"指的不是同一样东西，而且两组都是厂商自测，题集和模型集都不同，准确率只能在各自内部前后对比，不能横向相减。

Cube 团队的配对基准（arXiv:2604.25149，2026.04.28）走的是最轻的路线：100 道零售数据分析题，Claude Opus 4.7、Sonnet 4.6、GPT-5.4 各跑两遍，一遍只给数仓 schema，一遍多塞一份 4 KB 的手写 markdown 口径文档，内容是指标公式、维度层级、数据怪癖和歧义消解规则。加文档之后准确率从 45.5%–50.5% 抬到 67.7%–68.7%，配对显著性检验 p≤0.0015。

模型间的对比更能说明问题：有文档时三个模型在统计上分不出高下，没文档时同样分不出。论文的结论是，语义层文档解释了这份基准里几乎全部的显著方差，模型选择解释不了。

dbt Labs 同月发布的基准（2026.04.07）走的是重路线：不是把口径写进 prompt，而是建真实的语义层，由 MetricFlow（dbt 的指标编译引擎）确定性地生成 SQL。补 3 个建模之后，Claude Sonnet 4.6 走语义层 98.2%、走 text-to-SQL 90.0%；GPT-5.3 Codex 语义层 100%、text-to-SQL 84.1%。两组数字要放在一起看才完整：dbt 为了让 text-to-SQL 能跑，把整个 schema 塞进了上下文，这在真实大数据集上并不现实；按 dbt 的解读，90% 和 100% 的差距还是保守估计（厂商口径，若换用带 schema 检索的基线，差距也可能收窄）。同一份基准还测了 16 组模型与推理档位的排列组合：语义层侧的准确率几乎不随推理强度变化，而 GPT 系模型把档位从 high 拉到 xhigh，单次查询从 8 秒涨到 20 秒以上，准确率没动。

> text-to-SQL 的失败看起来像一个貌似合理的错误答案；语义层的失败看起来是一条报错。对任何进董事会材料、审计或公司 KPI 看板的东西，dbt 认为这个区别就是一切。
>
> （dbt Labs《Semantic Layer vs. Text-to-SQL 2026 Benchmark》，2026.04.07）

前一种可称为 context 形态：口径以文档形式进入上下文，约束靠模型自觉。后一种可称为 runtime 形态：口径是可执行的定义，约束由编译器强制。context 一词借自 Cube 论文对实验条件的划分，runtime 侧则对应 dbt 基准里的语义层路径，前者写一份文档的成本接近于零，后者要建模、进 CI、养 owner。dbt 给的建议也不是二选一：ad hoc 分析和小数据集用 text-to-SQL，准确性攸关、数据大而乱的企业场景用语义层。

**在讨论怎么落地之前，先要分清你要哪一种，因为它们的上限、成本和失败方式都不一样。**

## 二、context 形态：启动便宜，约束靠自觉

context 形态的作用机制，用论文自己的话说，是把 schema linking 和业务逻辑误读从开放式推断变成受约束的查找（from open-ended inference into constrained lookup）。模型不再猜"退货率怎么算"，只需要在文档里查。

它的价值有独立数据支撑，启动成本也确实接近零。Sequeda 等人在企业保险 schema 上测得，GPT-4 走知识图谱路径（ontology 加映射，生成 SPARQL）时准确率从 16.7% 升到 54.2%（arXiv:2311.07509，转引自 arXiv:2604.25149）。但论文同时承认了软肋：那份文档不是代码，不被任何运行时强制执行。模型读了文档仍可能选错维度，文档本身写错了也没人拦。

文档写错了、过期了、没人更新，它会安静地失效，不会有人收到报错，因为文档不在系统里。PostHog 在 2026 年 8 月的博客里梳理下来，语义层真正要固化的是三类只存在于部落知识里的信息：

- 指标到底怎么算
- 哪张表是被财务认可可以信的，哪些表要避开
- 数据之间怎么连（比如 Stripe 的 customer ID 要先改格式才能对上 organization 属性）

这些信息不写下来，每一次 Agent 会话都会现场重新发明一遍定义，还发明得每次都不太一样。context 形态的失效是安静的，这恰好是它和 runtime 形态最主要的分歧之一。

但这份便宜有明确的适用面：探索性查询、小数据集、答错成本低的场景，文档形态的性价比依然成立，这正是 dbt 建议里 ad hoc 一侧的本意。

## 三、runtime 形态：确定性是编译出来的

runtime 形态把口径变成可执行定义。MetricFlow 的指标长在 YAML 里，比率型指标的分子分母各自是独立定义的 metric（底层各对应一个聚合 measure），口径改动只改一处：

```yaml
# MetricFlow 指标定义（简化示例）：比率型指标，分子分母引用各自独立定义的 metric
metrics:
  - name: return_rate
    label: 退货率
    type: ratio
    numerator: return_amount_total
    denominator: sales_amount_total
    filter: |
      {{ Dimension('order_status') }} != 'test'
```

LLM 面对的问题也随之改写，它不再生成 SQL，而是生成一份受限的查询描述，大意如下：

```Python
# 语义层查询路径：LLM 的输出空间被指标目录限死，SQL 由确定性引擎编译
query_spec = llm.select(
    metrics=["return_rate"],              # 只能从语义层目录里选
    dimensions=["region", "order_month"],
    filters={"region": ["华东"], "time": "LAST_MONTH"},
)
validate(query_spec, METRIC_CATALOG)      # 目录里不存在的指标/维度直接拒绝
sql = compiler.compile(query_spec)        # join 图、方言、行级权限在这里注入
result = warehouse.execute(sql)           # LLM 全程接触不到物理 SQL
```

编译器按固定顺序做事：

1. 解析请求
2. 定位指标背后的物理表
3. 按 entity（实体）关系拼 join 图
4. 校验时间粒度
5. 生成方言正确的 SQL

表名、列名、join 条件全部来自建模文件，LLM 收到的错误是"这个指标不存在"，而不是一串跑得通但算错了的查询。这套"LLM 出受限描述、编译器出物理 SQL"的分工，和 SMQ 论文（arXiv:2606.31041）的中间表示思路是同一件事，也是《智能问数方案》里那句"幻觉列名被结构性移出解空间"的具体落法。

**runtime 形态的结构性失败（指标不存在、维度非法）在编译期就是 loud 的，这是它相对 text-to-SQL 的核心优势。**

确定性不免费，通常是两个工程问题。

第一个是 fan-out（连接放大）：事实表 join 维度表时行数膨胀，聚合结果跟着翻倍。几种主流解法：

- MetricFlow 用 entity 类型（primary/foreign/unique/natural）约束 join 方向
- Cube 要求事实表以 many_to_one 指向维度表
- Holistics 先在携带度量、join 后会被复制的那一侧聚合去重，再执行 join（官方表述是让 fan-out 根本不发生）

原则只有一条，一个查询要么完整走预聚合，要么完全不走，部分路由出来的总数和明细对不上。

第二个是 pre-aggregation（预聚合）的边界：Cube 的 rollup 匹配要过成员检查、粒度兼容、时区一致几道关，查询一旦带了预聚合里没有的维度，或者统计的是 DISTINCT COUNT 这类不可加指标，匹配失败，回落到现场计算。即便全部命中预聚合，缓存也不是免费的：Cube 用两级缓存（内存热查询加 Cube Store）加后台刷新扛住并发，自建语义层没有这层肌肉，每个 Agent 查询都可能变成一次全量重算。Airbnb 的 Minerva 早期重度依赖预计算，后来把执行引擎从 Druid 换到了 StarRocks，减少对预聚合的依赖（厂商案例口径）。预聚合是缓存，不是地基。

## 四、语义层烂尾的三种方式

大多数语义层项目的死法跟模型无关。

第一种是口径漂移。PostHog 归纳了三种形态：

1. 同一个指标在不同工具里被各自发明
2. 指标从某张看板派生出去，看板被人改了，定义悄悄过期
3. 已批准的定义被编辑之后，仍以正典身份继续服务

他们的对策是给指标加状态机：Agent 产出一律先落在 proposed（提案中）状态，人工批准后状态变为 approved（已批准），approved 且无 drift（漂移）标记的才算 canonical（正典），编辑已批准定义自动降回 proposed，读取时再和来源比对打上 drift 标记。

第二种是前面提到的 shadow analytics。元数据覆盖不足，用户查不到、查不准，信心耗尽之后绕开语义层自建计算，语义层退化成没人信的摆设。dbt Labs 的踩坑总结还补了一层：错误编码的业务逻辑会被放大到该指标的每一个消费者身上，语义层的错误影响面比散落的裸 SQL 更集中。换句话说，指标不存在这类结构性失败是 loud 的，定义写错的语义性失败依然安静，还会借强制执行被放大。

第三种是没人认领的定义问题。Tryolabs 在 2026 年 3 月的复盘里说得很直白，最难的部分不是在 dbt、Cube、Looker 之间做选型，而是让 finance、product 和 engineering 对 churn 达成一致，对齐各方对指标定义的共识，常常比微调一个模型还难；当 MRR 定义打架时，往往要靠高管裁决推进，裁决不来，层就上不了线。他们还点破了一个前置陷阱：很多核心定义压根没被写下来，活在最初建数仓那批人的脑子里、遗留 SQL 脚本和部落知识里，没写下来的含义无法被建模。

## 五、治理的最小可行结构

烂尾的反面有一批可复用的结构，来自 Lyft、Uber、Airbnb 的公开实践。

1. **先盘点，后建层。** 把现有看板里同一指标的所有定义找出来对一遍，多半会发现好几个略有差异的版本。先选正典、记录为什么，再动 YAML。口径没对齐就建层，结果是把混乱上移一层，制造出两个都自称正典的 MRR。

2. **准入看复用度。** Lyft 的 Golden Metrics（黄金指标）标准只有一条：至少有两个不同使用场景的指标才允许进包，太 niche 的指标管理成本大于价值。MVP 从十几个指标起步就够，选那些财务已经在反复争论的。

3. **双 Owner，变更双签。** 综合各家公开实践，比较稳的结构是每个指标配 Business Owner（出业务与 SQL 定义、按节奏复核、收集利益方批准）和 Operational Owner（保底表质量、值班、数据质量检查、backfill），两边都必须是团队而非个人，变更必须双方同时批准。Uber 的 uMetric 走类似路线，口径争议交给跨产品线的 Verification Committee（验证委员会）裁决，再用指标分级区分自助与签核。

4. **版本化像 API 一样。** Airbnb 给配置文件里影响产出的字段做 hash，任何变更触发新的 data version、自动建新数据集并 backfill，配合 Staging 环境做零停机迁移。breaking change 留弃用窗口，重大变更走 canary 发布。还有一种通行做法是在 CI 里跑编译一致性测试：同一个问题走 BI、语义层 API、裸 SQL 三条路，总数必须一致。

Airbnb 的教训单独说一句，它管着 12,000 多个指标、4,000 多个维度、200 多个数据生产者，早期只标准化了表，结果下游管道照样制造出大量重复和分叉的指标。他们的结论是表级标准化不够，用户消费的不是表，是指标、维度和报表，指标级标准化才是可信消费的前提。

国内的指标中台（阿里 OneData 一脉的原子指标、派生指标及三要素构成的规范定义）和这套话语高度同构，Aloudata 的 NL2MQL2SQL、Kyligence 的 NL 到 Metric Query 再到 SQL 这类实现（均为厂商口径），本质上就是 runtime 形态的国内版本，差异更多在产品包装而非机制。

## 六、MCP 成为出口之后的争议

近半年最明显的变化是语义层找到了标准出口。dbt 的 MCP server（Model Context Protocol，模型上下文协议的服务端实现）暴露了一整套语义层工具，`list_metrics`、`get_dimensions`、`query_metrics`，还有 `get_metrics_compiled_sql`，Agent 不但能拿到结果，还能看到编译出来的 SQL 长什么样。其余几家也陆续跟上：

- Cube 的 MCP server 在 2026 年 1 月发布
- Snowflake 的 Cortex Agents 与 MCP servers 在 8 月于 Native Apps 内进入 GA
- Salesforce Data 360 和 Looker 也各自带上了 MCP（当时均为预览版）

Lyft 把自研的 MSL（Metric Semantic Layer，指标语义层）封装成 MCP server 接进 Claude、Cursor 和 Hex，得到的观察是那份 YAML 配置意外成了 AI Agent 最好用的知识库。

配套的交换标准也在收敛。OSI（Open Semantic Interchange，开放语义交换）在 2026 年 1 月发布首个正式规范版本 v0.1，随后捐入 Apache 孵化器更名 Apache Ossie，dbt 解析时会自动生成 osi_document.json。要注意它的边界：Ossie 描述指标，不执行查询，它降的是迁移成本，不是治理成本。

把语义层当 Agent 基建，支持和反对的理由都摆在明面上。Gartner 在 2026 年 5 月的新闻稿里给过一个方向性预测：到 2027 年，在 AI-ready 数据上优先语义的组织，agentic AI 准确率最多提升 80%、成本最多降 60%（Gartner 口径的预测值）。反方同样明确。Redis 指出，让语义层擅长 BI 的三个属性恰好是它服务不了 Agent 的边界：输出的是针对数仓的 SQL、架构围绕查询到结果的往返、每次查询无状态（no session context, conversation history, or memory），而 Agent 在推理的每一步还要文档、会话历史、实时操作数据、工具和权限，连向量检索这种按语义而非精确匹配的查找，SQL 标准本身也不提供。ThoughtSpot 的 Cindi Howson 把话说得更直接，2026 年 8 月接受 AIWire 采访时说，头号错误就是把 BI 语义层当成 agentic 语义层，后者还要 ontology（本体）、上下文、记忆和知识图谱。

两边的分歧其实落在不同层：语义层补的是口径可信，Redis 和 Howson 说的会话历史、记忆、知识图谱是状态与检索层，前者是后者的输入，两者叠加而不是互相替代。

## 七、落地清单

**最佳实践：**

1. 先写那份口径文档（那篇基准里是 4 KB），再决定形态。文档都写不出来的团队说明口径还没对齐，直接上编译器大概率烂尾；写得出来，context 形态至少值回对齐这一步的票价。
2. MVP 从 10 到 20 个高复用指标起步，准入标准前置，Lyft 的"至少两个使用场景"可以直接抄。
3. 双 Owner 是团队、变更必须双签，指标定义进版本控制，CI 里跑编译一致性测试。
4. 让失败保持 loud：语义层答不了就报错，别让它悄悄退回裸 SQL 兜底；text-to-SQL 那条路配执行反馈与结果校验。
5. 预聚合当缓存用：不可加指标和跨事实表指标老老实实现场算，聚合路由不做部分匹配。

**常见误区：**

1. 把语义层当文档。口径文档解决的是对齐问题，不解决执行问题，长期只靠它，分析师绕行只是时间问题。
2. 口径没对齐就建层。建层放大的是现状，包括现状里的矛盾。
3. 相信预计算能包打天下。比率、distinct count、跨事实表指标基本压不进 rollup，这是 Airbnb 用一次引擎迁移换来的教训。

## 八、先有文档，再谈编译器

开场那三个 MRR 说明的不是模型问题。两组独立基准从不同角度指向同一件事：口径缺失时，换模型或加推理档位都补不上。context 形态回答的是让模型知道口径，runtime 形态回答的是让错误无法发生，中间隔着建模、治理和持续维护的成本。

多数团队合理的顺序可能是先有那份文档（选低风险用例、容忍它安静失效），再挑几个吵得最凶的指标送进编译器，其余的探索性查询继续留给 text-to-SQL，这也回到了分层协作的结论。治理这一侧的活没有捷径：

1. 盘点口径
2. 定正典
3. 配双 Owner
4. 进版本控制

每一步都是组织工作多于技术工作，但这些工作的产出恰好是 MCP 时代 Agent 在数据可信这一侧最缺的东西。MCP 把语义层接到越来越多 Agent 上之后，写不准的定义不再只骗一张看板，它会骗一堆 Agent。口径的质量正在变成一个可以开始被计量的生产力问题。
