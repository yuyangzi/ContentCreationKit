# Text-to-Chart 的最后一公里：图表没有唯一正确答案

> **导读**：智能问数的前半程是取数，正在被语义层收敛到唯一结果；后半程是画图，却收敛不了——同一份数据能画出好几张都算合理的图。这篇看的是"最后一公里"的机制：可视化有自己的语法，语义层能给的不只是正确的 SQL，还有一套带类型的视觉编码词汇表。

一份结果表摆在面前：12 个月、5 个区域、一列销售额。有人问"各区域销售额怎么样"，你可以按区域排开画五根柱子，可以按月份拉出五条折线，也可以算占比画一个饼图。三张图都画得出来，也都说得通。柱状图在比大小，折线图在看走势，饼图在讲份额。它们不是同一个答案的三种画法，是三个不同的答案。

这就是最后一公里的麻烦。《智能问数方案》梳理了从 Text-to-SQL 到 Text-to-Metric 的演进，《语义层落地》拆了语义层的两种形态和治理成本。两篇的落点都在同一件事上：把一个模糊的自然语言问题，收敛成一段确定、可执行、结果唯一的查询。可到了画图这一步，"唯一"这个前提突然不成立了。

---

## 一、为什么"正确图表不唯一"是 NL2Vis 独有的问题

先把两件事分开看。Text-to-SQL 有一个天然的裁判：查询执行出来的结果集。哪怕两条 SQL 写法完全不同，只要返回的表一样，就算都对；返回不一样，至少有一个错。当然，两条 SQL 也可能错得一模一样，这个裁判只管对齐、不管对错。

Text-to-Visualization（NL2Vis，自然语言到可视化，即标题所说的 Text-to-Chart）没有这个裁判。可视化不返回一张可以逐格比对的结果表，它返回的是一张图。图的"对"取决于它想表达什么、给谁看、在什么语境里。同一份数据在"区域对比"和"时间趋势"两个意图下，正确答案本来就不同。

歧义在这里被放大成两处。一处是数据层：取哪些列、加什么过滤、按什么分组，这一层和 Text-to-SQL 是共用的，前两篇讲过的 schema linking、口径问题都在这里。另一处是可视化层：数据已经确定之后，映射到哪种图表类型、哪个视觉通道，仍然有多种成立的选择。第二层是 NL2Vis 多出来的失败面。

学术上这个现象被单独建了基准。nvBench 2.0（arXiv:2503.12880，2025.03）是 nvBench（arXiv:2112.12926，SIGMOD 2021）的扩展版，用一条"歧义注入"流水线反向造题：从一个确定的种子可视化出发，逐步注入模糊表达，让同一个查询能够对应到多个合理的可视化，每个模糊查询都能沿一条逐步推理路径回溯到它对应的多个可视化。这套基准含 7,878 条自然语言查询和 24,076 个可视化，覆盖 780 张表、153 个领域。它想度量的，正是这种"一对多"到底有多普遍。

**选错图不像选错 SQL，它通常不会报错。**一段聚合写错的 SQL 有机会被结果分布、被上下游对账拦住；一张画错意图的图会安安静静地展示出来，数字全对，读者却被引向一个错误的方向。这是最后一公里里最容易被低估的风险。

## 二、可视化是一门受语法约束的语言

不是所有图都同等合理，这一点让问题从"主观"回到了"可分析"。可视化研究里有一个持续几十年的判断：图表是数据到视觉通道的映射，而映射有规则。

一张标准图表可以拆成两个部分。数据侧是被展示的字段；视觉侧是承载这些字段的通道，常见的有位置、长度、颜色、形状、大小，再加上分面。Vega-Lite 这类声明式可视化语法把这件事写得很直白：你声明字段到 `x`、`y`、`color`、`size`、`facet` 的映射，以及聚合方式，剩下的刻度、轴、图例由渲染器编译出来。

映射一旦写成通道，规则就浮出来了。字段有自己的类型：定量（quantitative）、时序（temporal）、名义（nominal）、有序（ordinal）。通道也有各自的适应能力：位置和长度擅长表达定量差异，颜色擅长表达分类，分面适合把多组数据并排比较。把时序字段放到 `y` 轴、把定量字段画成饼图的扇区角度，都不是"没人这么干"，而更可能是违反了视觉编码的可读性准则，读起来会失真。

微软研究院的 Flint（配套实现 flint-chart）把这套思路做成了一门面向 AI 的中间语言。它让数据字段先显式声明语义类型（比如 Rank、YearMonth、Delta 这类含义比 `int`、`string` 更具体的标签），再由编译器从这些含义推断解析规则、刻度、轴、格式和配色；上层只需要给出高层的图表规范，包括图表类型，以及字段到 `x`、`y`、`color`、`size`、`facet` 的映射，低层的参数化交给编译器。

这个分工的意义在于，**它把"选图表"从生成一整段自由代码，压缩成了在一个受限空间里做一组选择。**这正是前两篇共有的那种思路——缩小 LLM 的自由度。

## 三、语义层顺带给了图表一份受限词汇表

《语义层落地》里有一段代码，LLM 从指标目录里选 `return_rate`，选 `region` 和 `order_month` 作为维度，再加一个时间过滤，然后由确定性编译器出 SQL。那里的约束来自指标目录：选不出目录里没有的指标。

把这段代码往后再推一步，约束的能力还会多出一层。语义层定义的指标和维度，本身就是带类型的：指标是定量，时间维度是时序，"区域""品类"是名义，"会员等级"是有序。这些类型恰好就是视觉编码需要的输入。换句话说，语义层不只是让 LLM 选对数据，它还顺手给出了一套类型化的、够它选视觉通道的词汇。

于是后半程的流程可以写成和前半程同构的形状：

```Python
# 示意伪代码，非真实 API
# 视觉层查询：LLM 的输出空间被语义层的指标/维度/类型限死，
# 视觉编码和最终 spec 由渲染器补全
visual_spec = llm.map_channels(
    data_spec = query_spec,                              # 沿用上一步确定好的指标与维度
    chart_type = "line",                                 # 从受支持的类型里选
    encodings = {
        "x":     "order_month",                          # 时序维度 → 时间轴
        "y":     "return_rate",                          # 定量指标 → 位置/长度
        "color": "region",                               # 名义维度 → 分类通道
    },
    facet = None,
)
render(visual_spec, data=result_table, theme="nature")    # 刻度、轴、配色、布局交给渲染器
```

这里 LLM 做的选择，和它在 `query_spec` 里选指标是同一类动作：从一份有类型的目录里挑实体，而不是凭空造字段。`order_month` 是时序，所以它能放在 `x` 上做时间轴；`return_rate` 是定量，所以它能放到 `y` 上；`region` 是名义，所以它能进 `color`。这些约束不是渲染器事后校验出来的，是在 LLM 输出之前就成立的。

这也是《智能问数方案》"幻觉列名被结构性地移出了解空间"在视觉层的对应版本：如果 LLM 接触不到物理列名，它也同样造不出一根不存在的数据轴。

这套"语义层类型直通视觉层"的组合，目前没有公开基准数据，本文是机制推演，不是实测结论。

## 四、图表类型这一格，交给规则还是交给模型

数据和通道的映射有类型可依，剩下最棘手的是更靠前的一格：先选哪种图表类型。同一份"区域 + 月度 + 销售额"的数据，折线和柱状都能成立，差别在意图，是看趋势还是比大小。这一步没有类型约束那么硬，争议也最大。

工程上有两条路线。

一条是规则与打分。把图表设计知识写成约束和偏好，给每种候选图表打分再排序。Draco、CompassQL 这类规则打分引擎走的是这条线的现代版本：因为低层参数已被 Flint 这类编译器接管，推荐引擎只需要在高层做选择，也就是图表类型加上通道映射，规则可以写得比过去轻。规则路线的好处是可解释，为什么推荐折线而不是柱状，能说清楚；代价是僵硬，规则覆盖不到的组合就失效。

另一条是学习和端到端。让模型直接从数据加意图生成图表。ncNet（IEEE VIS 2021）用 Transformer 做序列到序列的翻译，把可视化先压成一种扁平语法 Vega-Zero 再生成，还允许用户选一个图表模板来收窄输出。这条路更灵活，能处理规则没覆盖的情形，但答案不再由规则保证，而是由模型的概率分布保证。

图表类型选择之所以两难，是因为它同时受两个东西影响：数据的客观结构（几个维度、什么类型、多少基数）和用户的主观意图（想看趋势还是看占比）。前者适合规则，后者适合模型。一个务实的做法是把两者叠起来，规则负责砍掉结构上不成立的选项，模型负责在剩下的选项里按意图挑。这又回到了前面那个模式：确定性引擎管确定的部分，LLM 管模糊的部分。

## 五、生成什么格式，决定了后面能校验什么

图表类型和通道确定之后，最后要落成一个具体的产物。格式的选择不只是工程偏好，它直接决定了你事后能校验什么。

1. **声明式 spec**（Vega-Lite、Vega 等）：结构化，字段可枚举，能对着 schema 做静态校验，也能在渲染前拦住很多非法组合。
2. **扁平序列**（Vega-Zero）：ncNet 的设计，把层次化的 spec 压成一串 token，专门为序列模型生成而改造，生成完再还原。
3. **绘图代码**（Matplotlib 等）：最灵活，能画大多数图，但生成的是程序不是数据，可校验性最差，一段能跑通的代码也可能画出一张完全错误的图。

前两篇里文本到 SQL 那条线有个反复出现的教训：能执行不等于正确。这里的版本是能跑通不等于画对。声明式 spec 在这件事上占了便宜，它是数据不是代码，校验器可以直接读。

## 六、评测：从"结果对不对"变成"图好不好"

既然没有唯一正确答案，评测的尺度也得换。

Text-to-SQL 用执行准确率（EX，Execution Accuracy）：两条 SQL 的结果集一致就算对。这套指标搬到可视化上直接失效，因为没有可比的"结果集"。VisEval（arXiv:2407.00981，2024.07）提了一套多维度的自动评测，覆盖 2,524 条查询、146 个数据库，从三个角度扫一个问题：有效性（validity，生成的代码能不能跑出图）、合法性（legality，图表类型、数据、排序是否符合查询要求）、可读性（readability，布局、刻度、配色等质量）。这三个维度里，前两个接近客观校验，第三个更主观，论文为此单独搭了一个基于 GPT-4V 的可读性评估器；整体框架由 validity、legality、readability 三个异质检查模块构成。

nvBench 2.0 把难点反过来用：它不回避歧义，而是把歧义建进基准，看系统能不能对同一个模糊查询给出多个合理可视化，并让每个都沿推理路径可追溯。

评测尺度的这次搬家，本身就是最后一公里性质不同的证据。前面那半程，好坏是一道判断题；这后半程，好坏更接近一道评分题。

自动指标与人类偏好相关性是 NL2Vis 领域的核心争议之一，LLM-as-judge 的可靠性问题也尚未有定论。

## 七、给工程师的实操建议

如果你在做智能问数的图表这一段，下面几条来自公开的基准、产品实现和工程判断。

**把可视化当受限空间，不要当自由生成。**优先让模型输出字段到通道的映射加一个图表类型，把低层参数交给渲染器或编译器，这能拦掉很大一类能跑但画错的问题。

**语义层的类型信息要一路传到视觉层。**指标是定量、时间维度是时序、品类是名义，这些类型如果只用来生成 SQL 就浪费了，它们同时是通道映射的依据。建层的时候顺手记住这件事，增量成本很低。

**结构用规则，意图用模型。**规则砍掉类型上不成立的组合，比如名义字段塞进 size、超高基数字段进 color；模型在剩下的组合里按意图挑。别指望单靠一端。

**给用户留一个切换入口。**歧义消不掉，但可以交给用户收敛。让图表类型可切换，是在承认没有唯一正确答案之后，把选择权还回去的工程做法。

**警惕安静的错。**数字全对、图表误导，是这段链路最危险的状态。上线前用结果分布校验加图表规则检查兜一道底。

**常见误区：**

1. 把"能画出图"当成"画对了图"。可执行性和正确性是两回事。
2. 认为图表类型纯主观，于是不做任何约束。主观指的是多个答案都成立，不是所有答案都成立。
3. 评测沿用 EX。图表没有可逐格比对的结果集，需要的是可执行性、合法性、可读性这一组多维指标。

## 八、最后一公里没有终点

回到开头那份数据。三张图都成立，这件事不会因为模型变强而消失。它来自可视化任务的本质：图表的"对"依赖意图，而意图藏在提问者的脑子里，不在数据里。

前两篇都落在分层协作上——治理型查询这半程正在被语义层收敛到唯一结果（同时也被两篇各自划了边界），错误从安静的错误数字变成响亮的报错。图表这半程收不敛到那一步。语义层能保证的是数据来源唯一、指标口径唯一、字段类型明确；它管不了的，是同样正确的数据到底该画成哪张图。可执行的确定性可以编译出来，语义的恰当性编译不出来。

所以这一段的工程目标，可能不是"给对答案"，而是"把输出空间收窄到合理区间"：让它选不出类型上不成立的组合，让用户在少数几个都成立的选择里拍板。**指标那一侧可以被治理，视觉这一侧目前只能被收窄。**这条边界目前看不到移动的迹象，因为它的根在人对图表的意图，而不在模型的能力。
