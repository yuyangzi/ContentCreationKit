# 从"可能合法"到"数学保证"：约束解码的三年进化

> **导读**：你让 LLM 返回 JSON，它在第三个请求突然少了一个必填字段，下游 parser 炸了。你说"用 JSON Mode"，它确实返回了合法 JSON，但 `confidence` 填了 0.99 而 `category` 完全是错的。约束解码（Constrained Decoding）解决的是前一个问题，暴露的是后一个问题——它把"格式错误"从概率问题变成了不可能事件，代价是把模型的概率分布扭曲了。本文沿着技术代际演进，从 2023 年的 FSM 索引法一路推到 2026 年的 XGrammar-2，最后落脚在一个反直觉的结论上：主流引擎优化之后，约束解码的开销通常可以忽略，在 jump-forward 等场景下甚至比不加约束更快，但"更快"和"更好"是两回事。（本文讨论以 JSON/schema 场景为主，代码生成与多模态场景下的结论可能不同。）

---

第一次踩到结构化输出的坑，大概率不是因为技术文章里写的那些深层原因。就是一段 prompt，要求模型"返回 JSON"，在本地跑得好好的，部署到生产环境第三天，一个请求的返回值少了 `required` 字段，下游服务 500 了。

这个问题的解法看起来简单：让模型总是返回合法的 JSON。实现起来，路径分了两条。

一条是**生成后校验**。Instructor、BAML、LangChain 的 output parser 都走这条路——模型自由生成，生成完拿 schema 校验，不合法就重试。这条路通用性最强，任何 API 都能用，但重试的成本是线性的，schema 越复杂、模型越小，重试次数越多。BAML 的 SAP 解析器做了一些容错优化，能修复不完整的 JSON，但本质上是在打补丁：它在接受"模型会犯错"这个前提。

另一条是**生成中约束**。在模型自回归生成每一步，采样之前，直接把不合法 token 的概率置零。模型不可能生成不合法的序列，不是"大概率合法"，是数学保证。（还有第三条训练期路线：微调模型，让它天生输出 schema 合规的内容。它与前两条正交、可以叠加，本文不展开。）

这条路走到今天，技术栈已经迭代了三代。

---

## 第一代：把问题变成查表——Outlines 和 FSM 索引

2023 年 7 月，Normal Computing 的 Willard 和 Louf 在 arXiv 上发表了一篇论文（2307.09702），奠定了约束解码的理论基石。他们的核心思路是把自回归生成重构为一个有限状态机（FSM，Finite State Machine）的状态转移问题。

具体来说：给定一个正则表达式（比如 `[a-z]+@[a-z]+\.[a-z]{2,}` 这种邮箱格式），经典自动机理论可以把它编译成一个确定型有限自动机（DFA）。DFA 有一组状态和一组状态之间的转移。每读入一个字符，状态机前进一步。到达终止态时，整个字符串被接受。

Outlines 的贡献在于：把每个 token 映射为 FSM 上的一段状态转移子序列。一个 token 可能包含多个字符（比如 BPE tokenizer 里 `42` 是一个 token、`.2` 是另一个），所以一个 token 会一次跨越多个字符级的状态转移。

做完这一步，最关键的操作来了：**预计算词汇表索引**。遍历整个词表，为每一个 FSM 状态建一张表 `σ: Q → P(V)`，把状态映射到"从该状态出发合法的所有 token"。

朴素做法是每生成一个 token，遍历整个词表（5 万到 12 万个 token），判断每个 token 是否在当前状态下合法。代价固定 O(N)。索引化之后只剩一次字典查找，O(1)。

生成循环变成：

```
当前状态 q = 初始状态
while 未完成:
    logits = 模型(prompt + 已生成序列)
    mask = states_to_vocab[q]           # 查表，O(1)
    logits = where(mask, logits, -inf)  # 掩码
    token = 采样(softmax(logits))
    q = 转移(q, token)                 # 状态推进
```

这个框架极其干净。正则表达式负责"规定合法输出是什么"，FSM 负责"保证每一步只选合法的"，两者在数学上完全等价。Outlines 的论文后来被广泛引用，不是因为它解决了 JSON 输出问题——那个问题在 2023 年已经有 GPT-4 JSON Mode 的工程解法了。它的贡献在于把约束解码从工程技巧变成了一个可证明正确的形式化框架。

但 FSM 有一个已知的局限：它只能表达正则语言。正则语言不支持递归嵌套。JSON 有嵌套（一个对象的值可以是另一个对象，数组的元素可以是数组），这在自动机理论里对应的是上下文无关文法（CFG），需要更强的计算模型。

## 第二代：当嵌套成为刚需——XGrammar 和上下文无关 token 的洞察

JSON 的深层嵌套需要 CFG，CFG 的执行模型是下推自动机（PDA，Pushdown Automaton）。PDA 比 FSM 多了一个栈，用于处理递归展开。每进入一层嵌套，压栈；每退出一层，弹栈。

XGrammar（arXiv:2411.15100，MLSys 2025，陈天奇团队）是目前影响力最大的约束解码引擎之一，vLLM（V1 中经 `auto` 模式首选）、SGLang、TensorRT-LLM 都把它作为默认后端。它的论文标题叫"Flexible and Efficient Structured Generation Engine"，但真正让人记住的是它提出的那个洞察。

XGrammar 把词表 token 分成了两类：

- **上下文无关 token**：只看解析栈的栈顶状态就能判定合法性。比如 JSON 里 `"key": ` 后面的引号 `"`，不管嵌套深到什么程度，在这个位置上永远是合法的。
- **上下文相关 token**：必须检查栈的完整状态才能判定。比如一个闭合花括号 `}`，嵌套层次决定了它闭合的是哪一层。

实测 Llama-3.1 的 128k 词表在 JSON 文法下，上下文相关 token 只有 1,134 个——不到 1%。再经过 XGrammar 的"上下文扩展"（context expansion）处理，进一步压到只有 120 个。

这意味着：**运行时只需要检查这 120 个 token，其余 127,880 个 token 的合法性在预处理阶段就已经全部算好，存在自适应 token mask 缓存里，运行时直接查表**。

论文给出的性能数字在引述中频繁出现：相对既有方案最高 100x 加速。但引用这个数字时要注意口径——它是纯 mask 计算的加速比，端到端的推理场景里，XGrammar 集成进 SGLang 后，H100 + Llama-3.1-8B 的 TPOT（每输出 token 时间）从 Outlines 的 44.2ms 降到 6.8ms，约 6.5x。

XGrammar 还做了一件事：把文法编译和 GPU 推理重叠执行。CPU 在计算下一个 token 的合法集合，GPU 同时在做当前 step 的前向传播。这个 co-design 思路后来被主流推理引擎普遍采纳。

但 XGrammar 有个痛点：编译慢。guidance-ai 的 MaskBench 基准（JSONSchemaBench 项目的一部分，1.1 万个真实生产的 JSON Schema）显示，XGrammar 编译时间平均 27 秒，p99 是 900 秒（超时）。不过这个口径需要说明：MaskBench 由 LLGuidance 团队维护，且未计入 XGrammar 编译与 prompt 预填充（prefill）的重叠执行，而 JSONSchemaBench 论文正文里复杂 schema 的编译中位数只有 0.11–0.30 秒。复杂 schema 的预编译成本仍可能高到不可接受，尤其是 Agent 场景下每轮对话都可能换 schema 的情况。

## 第三代：不预编译，现场算——LLGuidance 和惰性解析

LLGuidance（guidance-ai 团队）走了一条和 XGrammar 完全相反的路。

它不做预编译。每生成一个 token，现场把"已生成的前缀 + 文法规则"喂给一个高度优化的 Earley 解析器（Earley parser），解析器动态计算出"接下来哪些 token 可以合法续写"，然后对照词表的字节前缀树（token trie）求交集，生成 mask。

这条路启动成本几乎为零——没有 FSM 构建，没有 PDA 编译，没有缓存预热。代价是每步都要算。但 LLGuidance 把这个代价压到了极致：MaskBench 在 128k 词表 + 1 万个真实 Schema 上，平均 mask 计算时间约 50μs，p50 是 46μs。

更值得注意的一个数字是 LLGuidance 的启动时间：约 2ms。对比 XGrammar 在复杂 schema 上编译需要几十秒甚至超时，这个差距在 Agent 场景下是决定性的——Agent 每轮对话可能产生不同的工具调用 schema，预编译的代价是每次都要等几十秒，惰性解析的代价是每 token 多花几十微秒。

LLGuidance 内部用了三个关键优化：

1. **词法器/解析器分离**：外层是基于 Brzozowski 正则导数的 lexer，内层是 Earley parser。只有 0.1% 到 1% 的 token 检查需要进入解析器，其余全被 lexer 在更便宜的路径上解决了。
2. **Token trie 剪枝**：把 tokenizer 的字节序列组织成前缀树。某个字节在当前位置不合法，整棵子树直接被剪掉，不需要逐一检查子树下的每个 token。
3. **Slicer 优化**：对于那些没有约束的上下文（比如 JSON 字符串内部的自由文本），按正则切片预计算 mask。命中切片时直接跳过 trie 遍历，延迟进一步下降。

OpenAI 把 Structured Outputs 的后端引擎切到了 LLGuidance，这是惰性解析路线在生产环境可行性的一个侧面佐证。

两条路线（预计算和惰性解析）走到 2025 年，一个独立基准（SqueezeBits，2025 年 9 月）给出了清晰的结论：**简单重复 schema 场景，XGrammar 的预计算缓存完胜；动态复杂 schema 场景，LLGuidance 的零编译启动完胜**。不是谁替代谁，是场景决定引擎。

## 掩码的隐形成本：你过滤掉的不只是非法 token

约束解码的性能问题基本有了答案。但它引出了一个更深的问题，也就是"可能合法"和"数学保证"之间的那个张力所在。

硬掩码的操作是：非法 token 的 logit 置 `-inf`，softmax 后概率严格为 0。这保证了输出 100% 合法。被置零的那部分概率质量哪也没去，直接消失了。

正常采样时，所有 token 的概率加起来等于 1。掩码之后 softmax 重新归一化，合法 token 的概率之和仍然等于 1，但被砍掉的那部分概率质量携带的信息（模型认为"这些 token 是对的"）完全丢失，没有以任何方式补偿给合法 token。

GAD 论文（Grammar-Aligned Decoding，arXiv:2405.21047，NeurIPS 2024）给出了形式化证明：**硬掩码采样得到的分布不等于 LLM 原分布对文法约束的条件分布**。它叫这个现象"分布扭曲"。

直观上理解：假设模型给首 token `0` 和 `1` 各约 0.5 的概率。在 FSM 约束下，两者都能通向合法完整串，所以第一轮同时放行；一旦选了 `0`，合法续写就只剩 `00000` 这一条路。这个串在模型原分布下的联合概率只有 0.5⁵，但掩码在每一步只做"砍掉非法、重归一化"的局部操作，每一步幸存 token 的概率都被系统性抬高。模型说的是"我不太确定"，但掩码把它的输出强行推到了高置信区间。

这个问题在实际任务中表现为一个现象，不妨称之为**格式税**（format tax）。

两篇独立研究给出了两个角度的量化。Let Me Speak Freely（arXiv:2408.02442）发现，配合 schema 约束时 GPT-3.5 在数学推理任务上显著退化：模型在 JSON 模式下自行把 `answer` 键放在了 `reason` 键前面，先给答案再补推理，字段顺序直接绑架了思考顺序。（该结论存在方法论争议，Outlines 团队的复现研究得到相反结果。）

The Constraint Tax（arXiv:2605.26128）在 Qwen2.5-0.5B/1.5B、SmolLM2-1.7B 等 sub-3B 小模型上做了 15,000 次生成的对照实验，给出了一个更极端的数字：hard schema 把 schema 合规率从 61.5% 提到了 100%，但**答案准确率从 19.7% 掉到了 11.0%**。"格式合法但内容错误"的输出从 49.5% 飙升到 88.9%。论文的 3B 边界检查显示，这个代价在 3B 级别仍然存在；更大模型是否同样受影响，该论文没有覆盖。

DOMINO（arXiv:2403.06988，ICML 2024）从另一个切面揭示了同一个问题。它发现约束如果不与模型的子词边界对齐（比如强制模板导致模型选了 `\t` 而不是正常的双引号 `"`），token 错位（token misalignment）会把模型推向它在训练数据里极少见的 token 路径，直接导致 GSM8K 准确率从 41.5% 暴跌到 30.8%。

另一种观点（JSONSchemaBench 团队）认为此前观察到的大部分退化来自提示设计不当。如果 schema 里把 `reason` 放在 `answer` 前面，给足 few-shot 示例，约束解码不降反升，最多提升 4 个百分点。

两边的结论并不矛盾。约束解码"伤不伤质量"取决于三个变量：
- 字段是否按推理顺序排列（先思考后结论）
- 提示是否针对约束场景做了适配（约束模式下 few-shot 示例的增益比无约束更大）
- 约束的粒度是否给模型留了自由度（lm-format-enforcer 专门不做字段顺序和白空约束，因为这个自由度能降低幻觉）

## 工程落地：什么时候用、用什么、怎么用

目前主流推理引擎已经内置了结构化输出。vLLM 的 guided decoding 默认 `auto` 后端，优先尝试 XGrammar，能力不足时回退到 LLGuidance；Outlines 与 lm-format-enforcer 需要显式指定。SGLang 默认 XGrammar，配合 RadixAttention 做 KV 缓存复用和压缩 FSM 的 jump-forward 解码——在高度结构化的输出上延迟最高降 2 倍、吞吐最高提升 2.5 倍。

闭源 API 的格局是：OpenAI Structured Outputs（2024 年 8 月发布，内部用 CFG 引擎，2025 年 5 月切到 LLGuidance 后端）、Anthropic Claude Structured Outputs（2026 年 2 月 GA，grammar-constrained sampling）、Google Gemini（2025 年 11 月全面支持 JSON Schema）。三家都在向"原生约束"靠拢——不是 prompt 里告诉模型要返回 JSON，而是在 token 采样层做硬约束。

选型可以参考这个决策路径：

- **用闭源 API 且 schema 简单**：直接开 Strict 模式（OpenAI 的 `strict: true` 或等价参数），别用 JSON Mode
- **自托管 vLLM/SGLang**：用默认后端，不需要自己搞约束逻辑。除非遇到动态 schema 变动的 Agent 场景，才考虑显式切换到 llguidance 后端
- **Python 研究/脚本、需要切换模型**：Outlines，简单直观。schema 复杂时留意编译时间
- **Agent 动态工具调用**：XGrammar-2（arXiv:2601.04426）。它的 TagDispatch 可以根据响应协议里的 tag 触发结构切换（自由文本 ↔ 工具调用 JSON ↔ 推理通道），不需要为每一种组合预编译不同的文法

几条被验证过的实践：

1. **"Reason free, constrain late"**。需要推理的任务，先让模型输出自由文本的推理过程，最后一步再用约束提取结构化结论。Constraint Tax 论文正是以 delayed packaging（延迟包装）验证这条实践：先求解，最后再包装进结构化对象，日历工具调用场景下执行准确率损失归零。

2. **字段顺序等于思考顺序**。从左到右生成决定了前面的字段是后面字段的"思考条件"。把 `reason` 放在 `answer` 前面。

3. **约束兜底，提示先行**。约束解码只管结构，语义质量靠 prompt 和 few-shot 示例。约束对 few-shot 示例的依赖比无约束更陡（RANLP 2025）——零样本约束模式下幻觉率接近 100%，一个示例后 Outlines 降至 1.8%、XGrammar 约 10.7%（HuggingFace RAG 研究）。

4. **Cache your schemas**。重复使用的 schema 一定要复用编译产物。Outlines 持有 generator 对象、XGrammar 用 GrammarCompiler、vLLM 做服务级缓存——首请求延迟是隐藏的最大性能坑。

5. **格式合规率不等于业务准确率**。两个指标分开监控。Constraint Tax 的实验数据已经充分说明了只盯合规率的风险。

## 结尾

约束解码这三年走了一条不寻常的技术路线：它解决的问题（格式错误）在 2023 年就已经被 json.loads + retry 工程化解了，但它选择去解决的，是那个更根本的问题——在生成源头保证，而不是生成后修补。

代价是这个保证本身会扭曲它试图规范的那个系统。

这像极了很多基础设施技术的故事。你加了一层保证，这层保证本身引入了以前不存在的新问题。然后你再为这个新问题加一层补偿。约束解码的下一层补偿，在 XGrammar-2 的 TagDispatch 里、在 Harmony 协议的 channel 分离里——"结构"和"自由"不再是二选一，而是同一个输出流的不同阶段。

GAD 论文从理论上已经论证了：掩码式约束必然扭曲模型分布——因为掩码的本质是截断概率分布，精确无偏的采样在一般情形下不可行。但工程上存在足够好的逼近，GAD 提出的 ASAp 算法就是一例。"Reason free, constrain late"这条实践背后的逻辑就是：在模型最需要自由的阶段放手，在最不需要自由的阶段收紧。

结构不会没有代价，只是代价的大小与方向，取决于把它付在哪里。
