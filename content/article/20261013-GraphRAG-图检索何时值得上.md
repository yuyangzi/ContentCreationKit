# GraphRAG：图检索何时值得上

> **导读**：向量 RAG 擅长找到"写了某件事的那一段话"，却很难回答需要跨多份文档串联、或要求概括整个语料的问题。GraphRAG 用 LLM 把文本抽成实体和关系的图，再在图上做社区归纳与遍历。它确实能补上这块短板，但索引成本、图质量和维护负担都明显更高。这篇文章想回答一个更实际的问题：什么样的场景才值得付这个代价，以及在微软 GraphRAG 和 LightRAG 这两条路线之间怎么选。

假设你有一个内部知识库，四百多份项目文档。用户问："A 项目的预算审批人是谁？"答案散落在三份文档里：项目立项书写了 A 项目归属于产品部；组织架构文档写了产品部的预算由张总审批；另一份制度文档写了张总的审批权限上限。向量检索会按语义相似度召回与"预算审批人"最接近的段落，大概率只拿到制度文档那一段，缺少把项目、部门、审批人连起来的那一环。

这类问题的共同特点是答案需要沿着关系走两跳以上。另一类问题更棘手："这批文档里反复出现的主要风险有哪些？"这种问题没有单一答案段落，需要对整个语料做归纳。论文 GraphRAG（arXiv 2404.16130）开头就把这两类问题的失效点说得很直接：RAG 在针对整个语料的全局问题上往往会失败，因为它本质上是面向查询的摘要任务，而不是显式检索任务，而已有的查询导向摘要方法又无法扩展到典型 RAG 系统所索引的文本量。

所以问题不在向量检索本身不好，而在它的检索单位是文本块。下面依次说明图索引的做法、三种检索方式、成本与图质量，最后比较两条替代路线。

---

## 图索引在做什么

GraphRAG 的索引阶段可以拆成几步。文档先切成文本块，每块交给 LLM 抽取实体（名称、类型、描述）、关系（源、目标、描述）和可验证的声明。抽取结果合并成一张图，然后用 Leiden 算法做层次化社区检测，把联系紧密的实体划到同一社区，再为每个社区生成一份报告式摘要，高层社区的摘要由下层摘要递归整合而来。

用伪代码表示大致如下（演示流程，非官方实现）：

```python
def build_graphrag_index(documents):
    chunks = split(documents, size=600, overlap=100)     # 文本块切分
    entities, relations = [], []
    for chunk in chunks:
        e, r = llm_extract(chunk)                        # 每块一次 LLM 调用
        entities += e
        relations += r
    graph = merge_and_dedupe(entities, relations)        # 实体合并是质量关键
    communities = leiden_hierarchical(graph)             # 分层社区
    reports = [llm_summarize(c) for c in communities]    # 每个社区一次 LLM 调用
    return graph, communities, reports
```

这段代码里最容易被忽视的是两处 LLM 调用的数量。抽取是按文本块逐个调用的，社区摘要是按社区逐个调用的，两者的调用次数都随语料规模线性增长。下一节的成本问题就由此而来。

论文中的一次实测可以给出量级感。在约 100 万 token 的播客转录语料上，论文报告索引耗时 281 分钟，运行环境为 16GB 内存的 Xeon 机器，LLM 为 gpt-4-turbo（arXiv 2404.16130，§4.1.3）。

## 三种检索方式：Global、Local 与 DRIFT

图索引建好之后，查询时有三种常见路径，它们对应的问题类型不同。

**Global Search** 面向全局问题。它从指定层级读取社区报告，把报告分批交给 LLM 并行生成中间回答（带重要性评分），再对中间结果过滤、排序，聚合成最终答案。论文的核心实验就在这一模式上：在全局 sensemaking 问题上，以根级社区（C0）生成的答案相对向量 RAG 基线，在 comprehensiveness 上的胜率为 72%，在 diversity 上为 62%；同时 C0 级社区摘要所用的 token 比纯文本 map-reduce 少 97% 以上（arXiv 2404.16130，§5.1、Table 2）。

**Local Search** 面向具体实体的问题。它先把查询向量化，匹配到图中的相关实体，再沿关系取回邻居实体、相关社区报告和原始文本块，排序过滤后拼成上下文。它的优势在于能沿着关系补上向量检索漏掉的那一跳。回到前面的预算审批例子，Local Search 会从 A 项目出发，沿"归属于"走到产品部，再沿"预算审批"走到张总，最后取回制度文档里关于张总权限的原文。

**DRIFT Search** 是微软在论文之后补充的模式，它先用社区信息把查询扩展到相关主题，生成一个较宽的初步回答，同时提出后续追问，再对追问执行 Local 式的细节检索。它适合既需要背景又需要细节的问题，代价是调用次数更多、链路更长。

三者的选择大致如下：

- 问题里有明确实体（某人、某项目、某条制度）：用 Local
- 问题在问整体主题、趋势、共同风险：用 Global
- 问题同时需要背景和细节：考虑 DRIFT，但先确认是否真有必要
- 单跳事实类问题：直接走向量检索，图遍历只会增加延迟和噪声

最后这一条容易被忽略。2025 年的一项统一协议评测（arXiv 2502.11371）得出的结论很清楚：在单跳事实查询上，普通 RAG 表现更好；在多跳推理查询上，GraphRAG 更好；同时 GraphRAG 的构建成本、检索延迟和存储占用都更高，且性能对图的构建质量很敏感。也就是说，图检索是增强通道，不是默认替代品。

## 代价在哪里：索引、更新与成本

GraphRAG 的成本集中在索引阶段，而且结构比较清楚。微软官方文档对索引方法的说明中提到，图抽取大约占索引成本的 75%（GraphRAG 官方文档 docs/index/methods.md）。抽取和社区摘要都是 LLM 调用，所以成本与语料量、实体密度、社区层数直接相关。

社区也有实际报告。官方仓库的 issue #385（2024 年 7 月）中，有用户反馈一篇约 5900 词的文档在 GPT-4-turbo 下索引花费约 3.4 美元，十篇文档一次运行约 35 美元。这类数字随模型、语料和参数变化很大，只能当作量级参考，不能直接套用到自己的预算上。

更新是另一层负担。微软的 GraphRAG 提供两条路径：全量 `index` 会复用未变化文本的 LLM 输出，重算受影响部分；增量 `update` 是追加式的，适合小改动。增量路径的一个关键细节是，文档是否"新增"是按 title 判断的。如果你修改了一份文档的内容但文件名没变，增量流程可能会静默跳过它，图里保留的仍是旧内容。这一点在社区课程和一些实战文章中被反复提到，我没有在官方文档里找到完全对应的说明，因此建议在自己的流程里验证：给每次修改的文档加版本号或内容哈希，让"修改"在 title 层面可见，再定期跑一次全量重建兜底。

这里需要区分两件事：全量重建解决的是图的一致性，增量追加解决的是成本。两者不能互相替代。长期只用增量，实体去重的偏差会逐渐累积，最后表现为同一个实体在图里有好几个节点。

## 图的质量比检索策略更决定结果

很多团队在 GraphRAG 上遇到的第一个问题，不是检索慢，而是答案不对。排查到最后，常常发现问题出在图本身：同一个实体被拆成了两个节点，关系方向抽反了，或者某个过于宽泛的实体把整张图连成了一团。

实体去重是其中最需要花心思的环节。一个分层的做法：

1. 精确匹配（名称完全一致）
2. 嵌入相似度匹配，阈值要设高一些（默认的较低阈值容易把同名但不同指的实体合并到一起）
3. 边界情况下调用 LLM 做判断，判断时要固定 temperature，否则同一对实体在不同批次里可能得出不同结论

验证去重效果时，不要只看实体数量。实体数下降 50% 不一定说明去重成功，可能只是抽取口径不同。更可靠的做法是检查同一个规范实体下是否挂着多个来源 ID。如果挂的来源 ID 都指向同一份文档的不同段落，说明合并是合理的；如果来源来自完全不相关的文档，那就是误合并。

另外要说明的是，GraphRAG 的实体去重和实体链接是两回事。去重只合并图内部的重复节点，不会把实体对齐到 Wikidata 之类的外部知识库。如果你的场景需要外部对齐，那一步要另行建设。

## 另一条路线：LightRAG 与 HippoRAG

微软 GraphRAG 的社区摘要机制有其优势，但它的索引成本和更新成本正是很多团队想绕开的部分。这催生了两条有代表性的后续路线。

**LightRAG**（arXiv 2410.05779，2024 年 10 月，EMNLP 2025）保留了图结构，但去掉了社区检测和社区摘要，改用双层检索：低层检索实体级信息，高层检索主题级信息，再结合图与向量。它的一个重要设计是增量更新，新文档只需要增量地补充实体和关系，不必重建社区。论文在 UltraDomain 基准上用 LLM-as-a-judge 评估，其中在 Legal 数据集上对 NaiveRAG 的总体胜率为 84.8%，对 GraphRAG 也保持优势。需要注意，这个基准并不是标准多跳 QA，评估方式也与 GraphRAG 论文不同，两组数字不能直接比较。

**HippoRAG**（arXiv 2405.14831，2024 年 5 月）的思路更接近神经科学的海马体记忆模型：用 OpenIE 从文本中抽取无模式的知识图，查询时通过 Personalized PageRank 从查询相关的实体出发做一次图上扩散，一步完成多跳检索。它在 2WikiMultiHopQA 等多跳数据集上的召回表现相对向量检索有明显提升。**HippoRAG 2**（arXiv 2502.14802，2025 年 2 月）进一步引入短语节点与段落节点的双节点结构，并加入查询到三元组的链接与识别记忆过滤。论文中，它在 7 个数据集上的平均 F1 为 59.8，高于对照的 NV-Embed-v2 的 57.0。

这两条路线与微软 GraphRAG 的分歧，可以概括为一个权衡：社区摘要擅长回答全局问题，但要为此付出较重的索引成本；LightRAG 和 HippoRAG 把成本压在查询侧或更新侧，代价是全局归纳能力相对弱，且图噪声的影响需要单独治理。LightRAG 的论文在简单 QA 上的表现远低于向量基线，说明结构增强在不需要多跳的问题上会引入噪声，这一点与前面的 2502.11371 结论一致。

从开源实现看，微软官方仓库（microsoft/graphrag，约 3.6 万 star）目前处于维护模式，官方说明不再接收新功能的 PR；LightRAG（HKUDS/LightRAG，约 3.9 万 star）仍然活跃维护；nano-graphrag（约 4 千 star，约 1100 行核心代码）适合阅读源码理解机制，但不适合直接上生产。

## 常见误区

**误区一：把 GraphRAG 当成向量检索的升级版。** 它改变的是检索单位和索引流程，而不是只换了一个更好的 embedding。引入图之后，图的构建质量、更新策略和评测方式都要重新设计。如果只是把向量库换成图库而没有处理这些问题，效果往往比原来还差。

**误区二：默认配置就能上生产。** 官方 README 第一句就提醒索引是昂贵操作。`tokens_per_minute` 等限流参数要同时为 chat 和 embedding 配置，否则在索引时容易触发 429 错误。在用真实语料跑之前，先用一小部分语料估算全量成本，比事后看账单有用得多。

**误区三：用一个总分评估 GraphRAG 的效果。** 全局问题和多跳问题的失败模式不同，合并成一个分数会掩盖问题。更可靠的做法是把问题按类型分组（单跳事实、实体关系、全局主题），分别统计各检索模式的表现，并抽查图本身的实体和关系是否正确。

## 最佳实践

- **先估算、再全量**：用约 5% 的语料跑一遍完整索引，记录 token 消耗，据此推算全量成本，再决定是否继续。
- **分路由而不是全替换**：保留向量检索作为默认通道，只把全局和多跳问题路由到图检索。路由可以先用规则或小模型判断问题类型。
- **文档版本化**：给每份文档加版本号或内容哈希，让修改在增量流程中可见，并定期跑一次全量重建。
- **实体去重分层做**：精确匹配、嵌入相似度（阈值设高）、LLM 判断兜底，LLM 判断时固定 temperature。
- **用固定问题集回归**：准备一批已知答案的问题，按类型分组，每次改图的构建参数或检索策略都跑一遍，并抽查图中的实体和关系。

---

## 结尾

回到开头那个预算审批的问题。它的答案其实并不需要一张完整的知识图谱，只需要三段文档之间的一条关系链。GraphRAG 真正有价值的场景，是答案分散在许多文档之中、需要沿关系走多跳，或者需要对整个语料做归纳的时候。在这些场景之外，一套调好的向量检索加上合理的切块，往往已经够用。

问题在于，多跳和全局问题在知识库里到底占多大比例。这个比例没有通用答案，只能靠把自己的问题日志分类统计出来。统计完之后，图检索该不该上，基本就有了答案。
