# 当 Agent 调用了一个不存在的工具：工具幻觉、动态加载与路由的攻防

> **导读**：Agent 挂的工具越多，工具选择准确率掉得越狠，多步任务里每五次工具调用就接近一次是幻觉。过去我们把这些归咎于模型不够聪明，LiveMCPBench 却给出了相反的结论：近一半的失败发生在工具检索（召回）阶段，而不是使用阶段。本文从三种工具幻觉的分类讲起，拆解根因，翻一遍工具调用的进化史，最后落到一套四层防御架构和一个真实的注册表审计案例。

---

## 工具幻觉的三种面孔

"幻觉"这个词用得多了，容易让人以为它是一件事。学术综述里，幻觉被拆成五大类：推理幻觉、执行幻觉、感知幻觉、记忆幻觉和通信幻觉，其中执行幻觉又细分为工具选择幻觉和工具调用幻觉（《LLM-based Agents Suffer from Hallucinations》，arXiv:2509.18970）。工程上更常用的切法是按可检测性分，tianpan.co 那篇分析给了三个可以分别统计的指标：

1. **Unknown-tool rate（未知工具率）**：模型输出一个注册表里不存在的函数名。最容易检测，事后扫一遍日志就能发现。
2. **Shadow-call rate（影子调用率）**：模型输出的名字和某个真实工具足够接近，模糊匹配把它路由到了错误的工具上。日常埋点检测不到，除非专门为它插桩。
3. **Hallucinated-argument rate（参数幻觉率）**：工具名正确，参数是编的。能通过 schema 校验，在语义层面才暴露。

这里有个倒挂：越容易检测的形态越无害，越隐蔽的形态越危险。参数幻觉能一路通过校验，直到业务侧发现数据错了才暴露。

把这个分类放在一边，先看一个更反常的发现。The Reasoning Trap（arXiv:2510.22977）研究了强化学习对工具幻觉的影响，结论是：逐步增强推理能力，工具幻觉会随任务表现的提升成比例增加。另一篇论文把数字给得更具体（arXiv:2511.10899）：工具增强模型能多拿 19.3 个百分点的答案准确率，推理胜率反而掉了 41.5 个百分点，他们管这叫工具诱导的短视（Tool-Induced Myopia）。模型越是专注于"调用工具完成动作"，越没有余力去核对"这个名字真的存在吗"。

换句话说，我们直觉上认为推理更强的模型会少犯工具错误，数据给出的答案正好相反。

幻觉的基数并不小。Deepchecks 在 2026 年的评测里给出的数字是：多步工具调用链路的幻觉率在 20% 到 40% 之间（第三方引述）。幻觉率这么高，日常使用里却感觉不到，因为单次调用的失败太容易被当成偶发异常，多步流程里的失败又常常被后续步骤掩盖。放进一个二十步的 workflow，这个比例意味着几乎必然有一步是错的。

## 为什么工具越多，幻觉越多

1. **工具数量本身**。一份工具定义的平均长度在 400 到 500 个 token，50 个工具就是两万到两万五千 token。模型要在这堆说明书里找到对的工具，还要记住用户问题的上下文，注意力被摊薄几乎不可避免。EclipseSource 在 2026 年 1 月那篇《MCP and Context Overload》里用了一个很准的比喻：一个组装衣柜的手艺人，理想情况下手边只有说明书和恰好需要的工具；当身边堆满无关的电钻、锯子、焊接设备时，他反而找不到该用哪一把。
2. **说明书质量**。很多工具说明书写得并不合格，工具调用失败里，超过六成出在参数上，而不是工具选错（Presenc AI 2026 基准）。自由文本字段能写的地方偏偏不设枚举，该约束的参数类型没有约束，模型只能靠猜。schema 设计是幻觉的第一来源。
3. **命名冲突**。同一注册表里 `get_user`、`fetch_user`、`retrieve_user_profile` 并存，模型的注意力要花在区分近义词上，影子调用的温床就是这么来的。Jigar Joshi 的注册表审计文章把命名冲突排在七种失败模式的第一位。
4. **精度悬崖**。这是全局性的。Berkeley Function Calling Leaderboard 上有个经常被引用的数据：在日历调度任务上，工具从 4 个扩到 51 个，选择准确率从 43% 掉到 2%。工具越多，模型记住每一个的能力越差，这是上下文分配的物理限制，至少当前不是调参能解决的。

但最值得停下来看的是 LiveMCPBench（arXiv:2508.01780），第一个大规模 MCP Agent 基准。它的结论把矛头从模型转到了系统：**近一半的失败发生在工具检索（召回）环节，而不是推理环节**。模型不是不知道该怎么用工具，是根本没找到该用的那个工具。

这个结论和 Anthropic 观察到的现象吻合：

> 一个常见的错误是，很多工具只是把现有的软件功能或 API 端点包了一层，并没有考虑工具是否适合 Agent 使用。因为 Agent 对工具有着传统软件不具备的"affordance"（可供性）。

把这几条根因放在一起，结论就清楚了：20% 到 40% 的幻觉率，很大程度上不是模型在犯错，而是我们要求模型在极端不友好的条件下工作。

## 从 Toolformer 到 MCP：行业是怎么醒过来的

工具调用问题的历史不长，但演进速度极快。行业对"工具幻觉"的认知是分三个阶段醒过来的。

### 第一阶段：让模型学会用工具

2023 年之前，让模型调用 API 还是一个研究方向。Toolformer（NeurIPS 2023）率先实现自监督的工具使用，模型通过自监督方式学会了判断什么时候该调用 API。这个想法的激进之处在于，工具调用不是后置能力，而是模型自己学会的行为。

随后一年，路线迅速分叉。Gorilla（NeurIPS 2024）走检索感知路线，在 1,645 个 API 上训练，让基于 LLaMA 的模型在 API 调用上超过了 GPT-4。ToolLLM（ICLR 2024）把规模推到 16,000 多个真实 API，用深度优先搜索决策树做多步工具规划。

ToolkenGPT（NeurIPS 2023）换了个思路，把工具变成可嵌入的 token，推理时即插即用。到了 ToolGen（ICLR 2025），每个工具直接成为模型词汇表里的一个 token，规模到了 47,000 个。训练侧的强化学习也在推进，ToolRL 在多个工具使用基准上比 SFT 基线高 15 个百分点。

这个阶段的核心命题是"能不能"：模型能不能学会用工具、能不能用很多工具。幻觉还不是讨论的话题，大家忙着让模型先跑起来。

### 第二阶段：规模带来的双重压力

当工具数量从几十涨到几万，两个问题同时浮出水面：上下文塞不下，准确率往下掉。

EASYTOOL（arXiv:2401.06201）在 ToolBench 上把 token 成本砍掉约 70%，成功率反而更高。它证明了一件反直觉的事：少给模型看工具，模型反而用得更好。

这条思路一路延伸，有两条路径最有代表性：ScaleMCP 做了带自动同步 CRUD 管线的动态工具检索器，ToolScope 自动合并相似工具，一个管"按需给"，一个管"给得少"。它们共享一个共识：工具不能全塞给模型，得按需给。但"按需"的关键，也就是怎么知道该给哪些工具，在很长一段时间里没有标准答案。

### 第三阶段：MCP 时代，发现层成为主线

2024 年 11 月，Anthropic 发布 MCP（Model Context Protocol，模型上下文协议），工具调用从各家自建变成了一项行业协议。之后的时间线推进得很快：

- 2025 年 3 月：MCP 引入 OAuth 2.1，OpenAI 在 Agents SDK 里接入
- 2025 年 4 月：Google 宣布支持 MCP，正式集成随 Gemini SDK 在 5 月 Google I/O 发布
- 2025 年 6 月：引入 Elicitation 特性，MCP server 正式化为 OAuth Resource Server
- 2025 年 9 月：MCP Registry 上线，几个月内涌入约两千个 server
- 2025 年 11 月：2025-11-25 规范发布，Anthropic 前一天推出 Advanced Tool Use
- 2025 年 12 月：MCP 捐给 Linux Foundation 旗下的 Agentic AI Foundation（AAIF），Anthropic、Block、OpenAI 联合发起，AWS、Google、Microsoft、Cloudflare、Bloomberg 支持
- 2026 年 1 月：Claude Code v2.1.7 给 MCP 工具定义加了懒加载
- 2026 年 3 月：2026 路线图发布，企业就绪成为优先项
- 2026 年 7 月 28 日：2026-07-28 最终规范发布，无状态核心、去握手、header 路由、正式扩展框架、带 ttlMs 的缓存工具列表

到 2025 年底，MCP 的月 SDK 下载量已达约 9,700 万，server 数量破万。协议本身的重心，从"传输工具"移到了"管理工具的发现"。

最能说明行业觉醒程度的，是 LiveMCPBench 的结论和协议演进的方向重合：既然近一半失败出在工具检索（召回）环节，那协议层就该解决发现，而不是指望模型变聪明。2026-07-28 规范里的渐进式发现和带 ttlMs 的缓存工具列表，就是协议层对这个问题最直接的回应。

## 四层防御架构

防御不是靠一条防线，而是把幻觉挡在四个不同的层。每一层只做一件简单的事，合起来把 20% 到 40% 的幻觉率往下压。这套架构的总体思路，可以概括成一句话：把"让模型选"改成"替模型筛"。

### 第一层：语义路由器，在模型之前过滤

第一层不碰 LLM。用户请求进来，先过一个语义路由器（semantic router），把候选工具从几百个缩到几个。路由器的好处是它几乎不吃上下文：只转发匹配结果，几十个 token 的事。

这一层的设计空间很大，datarekha.com 归纳了四种生产模式：

1. 向量检索（vector retrieval）：适合千级以下的工具，token 成本最低，延迟 80 到 100 毫秒
2. 层级菜单（hierarchical menus）：适合上万工具，成本低，但每次查找要多一轮对话
3. RAG 加重排序（RAG + re-ranking）：适合异构工具目录，延迟 100 到 150 毫秒
4. 代码模式（code mode）：适合链式多工具任务，规模最大时成本最低，但需要沙箱

Cloudflare 的 Code Mode 把工具定义的 token 开销从约 117 万压到约 1K，省了 99.9%，走的就是代码模式这条路。

### 第二层：渐进式发现，工具按需加载

第二层解决"哪些工具真正进了模型上下文"。渐进式发现（progressive discovery）的思路是，先只给模型工具目录的摘要，等模型明确要某一类工具时，再加载完整定义。Claude Code 的 `defer_loading`、MCP 2026-07-28 规范里的缓存工具列表加 ttlMs 提示，都是这个思路的工程化。

Anthropic 的 Tool Search Tool 给出了一组直接的数据：启用工具搜索后，Opus 4 的工具选择准确率从 49% 提到 74%，Opus 4.5 从 79.5% 提到 88.1%。工具没换，模型没换，只是把"加载哪些工具"从一次性决定改成了按需决定。

社区对"把东西一股脑塞进上下文"的态度已经不耐烦了。developersdigest.tech 上有篇文章说得直白：如果你还在每个会话里粘贴巨型自定义 prompt，你是在 2026 年的环境里用 2025 年的战术。

### 第三层：模型选择，把话说死

第三层回到 LLM 本身，但做的不是增强，是约束。

OpenAI 的 `strict: true` 强制工具参数按 JSON Schema 严格校验；Anthropic 的 Programmatic Tool Calling 把工具调用从自然语言输出改成结构化代码调用，实现约 37% 的 token 削减。两家方向一致：不给模型自由发挥的空间，名字和参数都用结构化约束钉死。

### 第四层：验证与延迟绑定，堵住最后的口子

前三层把幻觉率压下来，第四层负责兜底：无论模型输出什么，执行前都要过一道确定性检查。

schema 校验拦参数幻觉；延迟绑定（delayed binding）在调用真正发出前才解析工具引用，让模糊匹配失效；Hook 机制在工具执行流上插入拦截点，人工审批、预算门控、输出校验都挂在这里。

四层不是排他选项。路由层管规模，发现层管上下文，约束层管准确率，验证层管兜底。大多数生产系统四层都上，只是每一层的深度不同。

## 框架选型：三家方案的取舍

同一套防御思路，三个主流生态给出了三种不同的实现。2026 年 Q1 的 AN Score（Rhumb 的 API agent 友好度评分，加权执行可靠性与访问就绪度）里，各家工具调用的可靠性差距不小：Anthropic 8.4/10，Google 7.9/10，OpenAI 6.3/10。这些差异不只在模型，更多在路由和加载的工程选择上。

### Claude Code：双阶段加载与进程隔离

Claude Code 的 skill 系统是双阶段加载：启动时只读 frontmatter，真正调用时才加载完整的 SKILL.md。工具侧有 `defer_loading`，低频工具可以推迟到首次调用。`context:fork` 让 skill 在隔离子 agent 上下文中执行，子 agent 的 MCP server 列表和主进程互不污染。工具搜索还有个 10% 的自动启用阈值：当 MCP 工具描述超过上下文窗口的 10% 时，自动启用延迟加载，工具定义改由 MCPSearch 按需发现，而不是一次性塞进上下文。

### LangChain：中间件与图路由

LangChain 的答案建立在 LangGraph 的图上。`ToolNode` 负责执行工具，`tools_condition` 决定是否继续调工具的条件边，`llm.bind_tools()` 做绑定，每轮调用前用中间件动态过滤工具列表。灵活度最高，代价是这套组合拳要你自己编排。

### OpenAI：严格模式与工具搜索

OpenAI 走协议路线。`strict: true` 把结构化输出和工具调用绑在一起，`tool_search` 成为标准工具类型，Responses API 把工具选择从模型自由发挥改成先搜再选。相比 Claude 的工程化方案，OpenAI 更依赖 API 层面的约束。

### MCP 原生：协议即防御

MCP 2026-07-28 最终规范把防御写进了协议：无状态核心让 server 不再维护会话状态，`tools/list` 加 `list_changed` 通知让客户端感知工具集合变化，header 路由统一多 server 的发现逻辑。对用 MCP 组织的系统，防御不是写在应用代码里，而是写在协议约定里。

无论哪家方案，一个经验值值得记住：**单个 server 挂 15 个以上的工具，边际收益就开始递减**。这不是某篇论文的结论，是生产环境反复验证出的经验法则。工具该拆就拆，一个 server 管一组内聚的工具，比一个大杂烩 server 挂 50 个工具可靠得多。

路由层的混合模式也在成型：用一个小模型做路由，判断该调哪个工具，把推理重的执行交给前沿模型。路由是模式匹配，用不着大模型，执行才需要真正的推理。这个分工把选择准确率和执行质量同时提了上去。

## 注册表审计：先审工具，再换模型

如果只让我推荐一个排查工具幻觉的起点，不是换模型，是审计工具注册表。

Jigar Joshi 写过一篇很有价值的复盘。他的团队有 47 个工具，工具选错率 22%，一路从修 prompt、加示例，试到准备把模型从 Sonnet 升级到 Opus，账单上每月多 4,200 美元。升级前他们先做了一次注册表清理，结果发现根因根本不在模型：命名冲突、描述臃肿、死工具没人清，注册表本身烂了。

清理之后的结果很干脆：Sonnet 在清理过的注册表上的准确率，超过了 Opus 在臃肿注册表上的准确率。**先审注册表，再换模型。** 这大概是工具幻觉问题里性价比最高的一条经验。

注册表审计要盯七种失败模式：

1. 命名冲突：`get_user`、`fetch_user`、`retrieve_user_profile` 并存
2. 描述臃肿：说明书比代码还长，关键信息被淹没
3. 该用枚举的地方用了自由文本参数
4. 缺少使用时机说明，什么时候该用、什么时候不该用都没写
5. 职责重叠，两个工具做同一件事
6. 死工具：注册了但从没被调用，白占上下文
7. schema 漂移：工具实现改了，描述和参数定义没同步

描述质量是重灾区。2026 年 2 月一份研究抽查了 MCP 生态里的工具描述，97.1% 存在质量问题（arXiv:2602.14878）。gravity.fast 那条经验说得很直白：

> 工具描述里的第三句话是大多数团队跳过的那句。没有它（什么情况下不该用），工具就会被过度使用。

审计不需要多聪明的工具，一个 schema lint 脚本就能抓出大部分问题：

```Python
# 注册表审计：抓命名冲突、描述质量、参数约束问题
from collections import defaultdict

def audit_registry(tools):
    name_counts = defaultdict(int)
    issues = []

    for t in tools:
        name_counts[t["name"]] += 1
        desc = t.get("description", "")
        if len(desc) < 30:
            issues.append(f"{t['name']}: 描述过短")
        if "适用" not in desc and "when to use" not in desc.lower():
            issues.append(f"{t['name']}: 缺少适用场景说明")
        for p in t.get("parameters", []):
            if "type" not in p and "enum" not in p:
                issues.append(f"{t['name']}.{p['name']}: 参数未约束类型或枚举")

    for name, count in name_counts.items():
        if count > 1:
            issues.append(f"{name}: 命名冲突，出现 {count} 次")

    return issues
```

逻辑不复杂，三个检查点写在注释里：描述长度、适用场景、参数约束。死工具用调用日志扫一遍就够了，注册了但三个月没被调用的，先归档再删。这类脚本挂进 CI，每次工具变更自动跑一遍，注册表就不会烂回去。

## 还没解决的问题

四层防御能压住大部分幻觉，但有几类问题，现在的方案还摸不到。

**动态生成工具**。注册表是静态的，工具由人定义。Agent 遇到没见过的新任务时，理想的做法是当场生成一个新工具，用完即弃。ToolGen 把工具塞进词表是这条路的一个雏形，但生成出来的工具怎么验证、怎么防注入，远没有答案。

**技能跨会话持久化**。Claude Code 的 skill 解决的是单会话内的加载效率，技能怎么跨会话积累、昨天的经验怎么变成今天的默认行为，还在很早期的阶段。SkillCraft（arXiv 2026）测出的 80% token 削减说明这层的优化空间大得吓人。

**集体技能学习**。单个 Agent 学到的东西，怎么沉淀成组织级的工具资产？注册表审计目前靠人，理想状态是系统自己观察哪些工具被频繁误用、自动合并相似工具、自动淘汰死工具。ToolScope 的自动合并是第一步，离自我维护的注册表还远。

**量化敏感性**。本地模型上，同样的工具定义，量化前后行为可能差很多。Reddit r/LocalLLaMA 上有个典型案例：在 LM Studio 上注册第二个 MCP server，哪怕从不调用它，解析器处理第一个 server 工具调用的方式都会变。这个现象源于一个具体的解析器 bug，不一定是普遍规律，但它说明本地模型对工具定义的微小变化更敏感，这让用开源小模型做路由的方案在精度上打了折扣。

---

至少在可预见的未来，工具幻觉很难根除。只要 Agent 还在用自然语言和工具打交道，模型就可能记错名字、编错参数。能做的只是让幻觉从静默变成可见，从随机变成可查。如果当时有注册表审计，命名冲突第一周就会被标出来；如果有延迟绑定，模糊匹配根本不会生效；如果有路由层，模型根本不会看到那个名字。
