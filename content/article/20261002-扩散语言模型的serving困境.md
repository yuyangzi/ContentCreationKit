# 扩散语言模型的 serving 困境：双向注意力之后，两条路线怎么分岔

> **导读**：dLLM 的营销叙事是"并行生成、更快"，但朴素实现的计算复杂度是 O(L³)，AR 是 O(L²)。根源在双向注意力：更新任意一个 token，全序列的 K/V 都跟着变，AR 的 KV Cache（键值缓存）精确复用假设直接失效。工程界为此分出了两条路线，把生成 block 化以恢复因果性，或者保留全序列去噪、用近似缓存和运行时旋钮扛住。这篇文章拆开这两条路线的机制与代价。

---

## 一、宣传里的"更快"，和开源实现里的"更慢"

2025 年 2 月，Inception Labs 发布 Mercury Coder（技术报告 6 月上线 arXiv），Mercury Coder Mini 在 H100 上达到 1109 tokens/s，这一数字来自 Artificial Analysis 的独立评测，论文直接引用。到了 2025 年 7 月底，字节的 Seed Diffusion 把数字推到 2146 tokens/s（H20，论文自测）。扩散语言模型（diffusion language model，下称 dLLM）给人的第一印象是：它比自回归（autoregressive，下称 AR）模型快。

问题不在实现，在范式。AR 模型每生成一个 token，要对前面所有 token 做一次 attention，因为有 KV Cache，单步是 O(t)，n 步加起来 O(n²)。dLLM 不一样，它把整条序列当成一块要反复打磨的画布，从全 `[MASK]` 出发，走 T 步去噪，每一步都对整条序列做一次双向 attention。如果 T 和序列长度 L 同量级，总计算量就是 O(L³)（按典型 L 步去噪计）。

> dLLM 的 serving 困境从这个 O(L³) 开始，但根子不在复杂度，在两个与 AR 根本对立的性质。

一个是双向注意力，一个是生成单位。前者让 KV Cache 的精确复用失效，后者让 continuous batching（连续批处理）的调度粒度错位。这两个根因往下又长出一串具体问题。

## 二、根因：双向注意力让 KV Cache 的精确复用失效

AR 的 KV Cache 建立在因果掩码上。因果掩码（causal mask）保证每个 token 只能看到自己和左边的 token，所以第 t 个 token 的 Key 和 Value 一旦算出来，就不会被后续 token 影响。前缀可以缓存，跨请求可以复用，PagedAttention 和 Automatic Prefix Caching 都建立在这个"算完就不变"的假设上。

dLLM 把这个假设抽掉了。

在层 ℓ、去噪步 t，某个 token 的 hidden state 记作 h_{ℓ,t}，投影出 Key 和 Value：

```Python
k_{ℓ,t} = W_K · h_{ℓ,t}
v_{ℓ,t} = W_V · h_{ℓ,t}
```

双向注意力下，位置 i 的输出把整条序列的 Value 聚合进来：

```Python
o_{ℓ,t}[i] = Σ_j softmax(q_{ℓ,t}[i] · k_{ℓ,t}[j] / sqrt(d)) · v_{ℓ,t}[j]
```

那个求和跨了 j = 1..n 全部位置。于是任何一步把一个 `[MASK]` 解码成真实 token，这个 token 的 hidden state 就变了，它的 Key 和 Value 跟着变，所有位置的输出跟着变，所有位置的 hidden state 再变。**一步解码，全序列 K/V 的精确复用即告失效**，已解码的 token 和 prompt 里的 token 都不例外。

dKV-Cache 这篇工作把失效原因归纳成两条：KV Cache 依赖"已生成 token 的 K/V 在后续步保持不变"，AR 靠因果掩码保证，dLLM 的双向注意力不保证；KV Cache 还依赖"固定的从左到右解码顺序"，而 dLLM 每一步可以更新任意位置，解码顺序不确定。

精确复用既然做不到，工程上就转向近似：在 K/V 变化可忽略的窗口内复用，差别只在怎么判断哪些 K/V 还新鲜。

```Python
# dLLM 的去噪循环：T 步，每步对全序列做一次前向
for step in range(T):
    logits = model(x)                  # x 是全序列，双向注意力
    confidence = softmax(logits)       # 每个掩码位置的置信度
    accept = confidence > threshold    # 置信度够高的位置解码
    x[accept] = argmax(logits[accept])
    # x 变了，下一步所有位置的 K/V 都要重算
    # AR 的 KV Cache 在这里失效：没有任何位置的 K/V 是不变的
```

dKV-Cache 观察到 token 的 K/V 在"从 MASK 变 decoded"那一步变化最大，延迟一步再缓存就趋于稳定，靠这个拿到 2 到 10 倍加速。dLLM-Cache 发现 prompt 基本静态、response 只有少数 token 剧烈变化，用 Value 向量的余弦相似度决定哪些要重算，在 LongBench-HotpotQA 上把 FLOPs 最多降到约 1/9.1。EntropyCache 换了个更便宜的信号，用新解码 token 的最大熵判断缓存是否漂移，决策开销只有 O(V)，与上下文长度无关，报告 15.2 到 26.4 倍加速。

这些数字来自各自论文，硬件、batch、生成长度不同，不能直接横比，但共享同一个前提：接受近似。

## 三、两个衍生困境：调度粒度错位，和 prefix caching 跨请求复用失效

serving 层还有两个问题：一个从生成单位的 block 化长出来，一个从 KV Cache 失效长出来。

第一个是调度粒度错位。AR 的 continuous batching 在每个 token 步做抢占和换入换出，因为每个请求每步只前进一个 token，异质性主要来自输出长度不同。dLLM 不是这样：每个请求要跑完整的去噪循环才产出一个 block，而不同请求的收敛速度不同，有的 block 几步就收敛，有的要很多步。同一批里，快的请求在 block 边界已经完成，却因为慢请求占着资源而空转。

BlockServe 把这个现象命名为 convergence heterogeneity（收敛异质性），解决办法是把调度量子从 token 改成 block-cycle，在 block 边界立刻驱逐完成的请求，再用 gather-scatter 索引把处于不同 block 位置的请求塞进同一个 dense tensor。在 Dream 和 LLaDA 上，它的吞吐达到 Fast-dLLM 的 1.9 到 10.6 倍。

TeDiServe 走的是另一个角度，它把 confidence threshold（置信度阈值）当成运行时旋钮。去噪时解码哪些 token、解码多少，本来就是一个速度与质量的权衡，那就按请求剩余的延迟预算动态调整阈值，而不是全局固定一个值。它报告 SLO 达成率最高提升 56.6 个百分点，精度损失不到 1%。

第二个是 prefix caching 的跨请求复用失效。AR serving 里 shared prefix 的缓存命中是吞吐的大头，多轮对话的 system prompt 和历史对话都能复用。但 dLLM 的双向注意力让 prefix 的 K/V 也随任意位置更新而改变，直接复用会污染 attention 上下文。

BiCache 的实验给出了一个数字：把 AR 的 shared prefix caching 直接套到 dLLM 上，准确率崩塌到接近零。它的解法是按层分区，浅层直接复用、深层定期刷新，吞吐提升 36.3% 到 98.3%。

## 四、分岔：block 化，还是近似

面对同一组困境，工程界分出了两条路线。分岔的判据是：**生成范式是否 block 化**。

### 路线一：把生成 block 化，换回因果性

Block Diffusion（块扩散）把序列切成若干 block，block 内部用双向注意力并行去噪，block 之间用因果注意力，也就是自回归。这样一来，block 之间就有了"算完不变"的性质，KV Cache、prefix caching、PagedAttention 这些 AR serving 的成熟机制可以部分恢复。代价是牺牲了全序列的并行度上限：block 内的并行还在，block 之间回到了顺序生成。

这条路线的代表工作不少。Block Diffusion 在 2025 年 3 月提出，支持变长生成和 KV caching；Fast-dLLM v2 用 block diffusion 加互补注意力掩码，把预训练 AR 模型改造成 dLLM，只需要约 1B token 微调，而 Dream 那种全注意力扩散用了 580B token。

```Python
# Block Diffusion：块内双向去噪，块间因果
for block_idx in range(num_blocks):
    canvas = [MASK] * block_size
    for step in range(T_block):
        logits = model(canvas, past_kv)   # 块内双向，块间只读历史 KV
        # 更新 canvas...
    past_kv.append(commit(canvas))        # 提交后写入 KV cache，供后续 block 复用
```

### 路线二：保留全序列去噪，用近似缓存和运行时旋钮

这条路线的选择是不动生成范式，接受全序列双向去噪，然后在缓存和调度上做文章。第二节列的四个缓存工作都属于这条线，Fast-dLLM v1 的 training-free 部分也是，TeDiServe 的运行时旋钮和 BlockServe 的 block-cycle 调度同样归在这一支。它保留了全序列并行的理论优势，代价是缓存始终有损，而且刷新本身要花算力。

两条路线的代价并不对称。路线一牺牲的是理论并行度上限，换来的是 AR 生态的复用，通常还需要训练或微调。路线二保留并行度，代价却是持续性的：每一次去噪步都要判断哪些 K/V 能复用，在反复复用下近似误差会累积，刷新步比普通步更贵。TeDiServe 就专门把这种步级异构成本建模进了调度。

## 五、两条路线在现实里已经混在一起

纯的路线一和纯的路线二都少见，落地时两条线往往缠在一起。

Fast-dLLM 本身是个两栖体：v1 用 block-wise 的近似 KV Cache 和置信度感知的并行解码，属于路线二；v2 加入 block diffusion 后，才同时踩在两条路线上。vLLM 在 2026 年 6 月原生支持 DiffusionGemma，用的是一套清晰的混合：同一套权重跑两种模式，encoder 模式用因果注意力并写入 KV Cache，decoder 模式用双向注意力只读 KV Cache。因为提交阶段的 KV 是按 AR 方式写入的，vLLM 的 automatic prefix caching 开箱即用，不需要 diffusion 专属改动。它复用 speculative decoding 的数据路径，把去噪画布当成一批"要么全接受要么全拒绝"的 draft token，FP8 在单卡 H200、batch=1 下达到 1288 tokens/s。这些吞吐数字硬件、batch、精度口径各异，同样不能直接横比。

SGLang 在 2025 年 12 月支持 LLaDA2.0，思路是把 block diffusion 映射到已有的 Chunked-Prefill 机制上：block 内的双向注意力对应矩形掩码，chunk prefill 的因果掩码对应梯形掩码，只需要改 prefill adder 和 chunked reqs。它一次输出一个 block（比如 32 token）。在"10 种语言实现快速排序"的演示场景里，LLaDA2.0-flash-CAP 在 8 张 H20 上达到 935 tokens/s，对照的 gpt-oss-120B（117B 总参数 / 5.1B 激活）是 263 tokens/s。

再往前看一层，dInfer 把推理管线拆成 model、diffusion iteration manager、decoding strategy、KV-cache manager 四个模块，在 8 张 H800 上把 batch=1 的 HumanEval 推到 1100 tokens/s 以上，比 vLLM 上同量级的 Qwen2.5-3B 快 2 到 3 倍。Sangam 则直接借用 AR serving stack，用 deficit token-budget 调度器处理 dLLM 特有的"重复 prefill 加 block-sized decode"结构。在这些框架集成案例里，路线边界正在被磨平。

## 六、工程上能落地的几条经验，和几个常见误解

部署 dLLM 时，有几点可操作的判断。

1. 架构上优先 block 化，不要硬扛全序列双向去噪。block 间因果能让 KV Cache、prefix caching、PagedAttention 部分恢复，SGLang 和 vLLM 的落地都建立在这个前提上。
2. KV Cache 用近似加刷新，并把刷新成本显式建模进调度。近似误差会累积，刷新步比普通步贵，调度器不知道这一点就会做出错误的准入决策。
3. 把 confidence threshold 当运行时旋钮，而不是全局固定值。这是 dLLM 相对 AR 多出来的一个控制维度，按请求的延迟预算动态调，能在吞吐和延迟之间找到更好的点。
4. 调度粒度用 block，不是 token。dLLM 的异质性来自收敛速度而非输出长度，token 级抢占不适用。
5. shared prefix 不要直接复用 AR 的缓存。要么像 BiCache 那样按层分区，要么用因果 encoder 的架构让 prefix caching 天然成立。

至于误区，有三个流传很广。

**第一个是"dLLM 天生比 AR 快"。** 朴素的全序列 dLLM 是 O(L³)，实际比 AR 慢。前面那些上千 tokens/s 的数字，前提是激进的并行解码，多数实现还叠加了 block 化或缓存优化，不是范式的免费红利。

**第二个是"KV Cache 在 dLLM 里完全不可用"。** 它可用，只是必须近似，或者靠架构改造恢复因果性。dKV-Cache 的一个关键细节是延迟一步再缓存，不延迟会直接崩掉。

**第三个是"并行解码越多越好"。** 同时解码的 token 越多，条件独立假设破坏得越严重，质量下降越明显。Fast-dLLM 把质量下降的根因定位在这个假设上：模型按 p(x_i)·p(x_j) 独立采样两个相互依赖的位置，而真实的联合分布 p(x_i, x_j) 是带依赖项的，于是会产出"high house"这种错误组合。并行度是一个需要阈值控制的旋钮，不是一个越大越好的参数。

## 七、快与慢，都是真的

dLLM 宣传的"快"和开源实现的"慢"都是真的，差别在于有没有把 serving 层的困境一个个解掉。解掉之后，它确实能在低 batch 场景下比 AR 快（dInfer 的 batch=1 结果就是一例），因为它的算术强度更高，正好用上 AR 在低 batch 时浪费掉的算力。前面那些精度数字都是相对各自基线的损失，不代表 dLLM 的绝对质量已与同量级 AR 模型持平。

两条路线各让渡了不同的东西：路线一把 dLLM 往 AR 的形状上拉，路线二守住了并行、代价是缓存始终有损。哪条更划算，取决于任务对延迟、吞吐、质量的相对权重，没有一个通用答案。

当 AR serving 从 KV Cache 到 prefix caching 到 continuous batching 的成熟工具被逐一改造复用后，dLLM 的非顺序生成特征所剩无几。Top 10 Open Challenges 那篇综述把"dLLM 被限制在 AR 遗留设施里"列为十大挑战之一，说的就是这个。block 化让 dLLM 跑进了 AR 的框架，也让它的并行优势收敛到一个 block 的大小。

这条路会走到哪里，是 dLLM 长出自己的 serving 原生范式，还是最终变成 AR 框架里的一种特殊解码模式，2026 年还没给出答案。
