# MoE 容量因子：为静态形状而生，靠静态形状活下来

> **导读**：容量因子（capacity factor）是 MoE 里一个专门用来迁就硬件的超参：张量形状必须在编译期定死，可 token 分到哪个专家要等 router 算完才知道，于是给每个专家预设一批槽位，装不下的 token 跳过专家计算。
>
> 这个补丁在训练侧已经基本被拆掉，DeepSeek-V3 报告明确说不丢 token，Megatron 把它默认设成关闭；但它又以另一种身份回到了部署配置里，决定你的 MoE 层能不能进 CUDA Graph（静态计算图捕获）。
>
> 这篇文章从那个矛盾出发，拆开溢出的机制、代价，以及补丁被拆掉之后钱花去了哪里。

2026 年的主流 MoE 训练栈里，有一组相反的默认值。Megatron Core 的参数表里，`--moe-expert-capacity-factor` 默认是 `None`，也就是不设上限；

DeepSpeed 的 `deepspeed.moe.layer.MoE` 默认 `capacity_factor=1.0`、`drop_tokens=True`，连推理路径的 `eval_capacity_factor` 也停在 1.0。

两边取成了相反的方向。这个分歧不是谁写错了，而是容量因子在两个系统里承担的角色已经不一样了，源头则是它诞生时面对的那个矛盾。

---

## 形状必须在编译期定死，路由要等算完才知道

MoE 层做的是这样一件事：把 token 按 router（路由器，一个轻量线性层，给每个 token 打一组专家分数）的 top-k 结果分组，每组送进对应的专家 FFN。

专家 FFN 是普通的稠密矩阵乘，而稠密 GEMM（通用矩阵乘，这里就是专家那层前馈计算）要求输入矩阵的行数是确定的。问题在于，一个 token 会落到哪个专家，要等 router 把 logits 算完、做完 top-k 排序才知道。

动态的路由结果，静态的矩阵形状，中间隔着一层硬约束。有三种处理方式，历史上都试过：

1. 等路由结果出来再决定形状。语义上最干净，但每次 kernel 启动的形状都不一样，编译器和算子库都不好受
2. 用可变长的 ragged GEMM（变长矩阵乘），让 kernel 自己处理每个专家不同的 token 数。这条路要等 block-sparse（块稀疏）一类的新算子成熟才走得通
3. 预先给每个专家划一批固定的槽位，装得下就装，装不下就丢

第三条路是 GShard 和 Switch Transformer 在 2020 到 2021 年选的，实现成本低，落地最快，代价是它凭空造出了一个新的失败模式。

HuggingFace 的 MoE 博客把这层动机说得很直接：

> Since all tensor shapes are statically determined at compilation time, but we cannot know how many tokens will go to each expert ahead of time, we need to fix the capacity factor.

**容量因子不是为丢 token 设计的，是为静态形状设计的。** 丢 token 是它的副作用，而且这个副作用在当时被判断为可以接受。

## 四套写法，一个通用式

容量（expert capacity）指单个专家这一层最多处理多少个 token。Switch Transformer 的定义最常被引用，论文式 3 写得很清楚：

$$
\text{expert capacity}=\left(\frac{\text{tokens per batch}}{\text{number of experts}}\right)\times \text{capacity factor}
$$

这个式子默认 top-1 路由，capacity factor 就是那个缓冲倍数。换成 top-k，再把容量按“派发次数”而不是“唯一 token 数”来算，就得到可以横跨各家实现的通用式：

$$
C=\left\lceil \frac{k \cdot \text{CF} \cdot T}{E}\right\rceil
$$

通用式里有四个量：

- T 是这一步的 token 数
- E 是专家数
- k 是每个 token 激活的专家数
- CF 是容量因子

容量统计的是派发次数，top-8 的一个 token 会占用 8 次容量，分子里那个 k 就是这么来的。

各家实现的差别，全在它们把 k 和 CF 放在哪个位置。表中 GShard 的 N 是一个 batch 的总 token 数，每组分到 S = N/G 个 token：

| 来源 | 原始写法 | 映射到通用式 |
|---|---|---|
| GShard（arXiv 2006.16668） | 每组每专家 `2N/(G·E)` | k=2 写死，没有 CF 这个超参，式子里的 2 是扇出不是缓冲 |
| Switch（arXiv 2101.03961） | `(T/E) × CF` | k=1，CF 显式 |
| Tutel（arXiv 2206.03382） | `k·f·T/E` | 最接近通用式，f 即 CF |
| Megatron Core | `ceil(T · topk · CF / E)` | k 乘进分子 |
| DeepSpeed（top-2 路径） | `ceil((T/E) · CF · 2)` | ×2 写死即 top-2，k=2 |

最后一行容易踩坑，但坑不在数值本身，而在这个数字脱离路由配置就没有意义。

DeepSpeed 在 top-2 路由时把容量因子直接乘 2，`deepspeed/moe/sharded_moe.py` 里写的是 `_capacity(gates, torch.tensor(capacity_factor * 2), ...)`；Megatron 不这么干，它把 topk 乘进分子。

路由配置相同时，两边都设 `capacity_factor=1.0` 算出来的槽位其实一样，都是 2·T/E。差别出在路由配置上：DeepSpeed 的 top-2 把 ×2 写死在代码里，Megatron 的 topk 是自己配的。搬配置时照抄 `capacity_factor` 而没跟着改路由，会得到一个谁也没预期的缓冲量。

拿一组具体数字走一遍。T=4096、E=64、top-8、CF=1.25：

```
每专家派发数（CF=1）  = 4096 × 8 / 64 = 512
每专家容量（CF=1.25） = ceil(512 × 1.25) = 640
总槽位                = 640 × 64 = 40,960
实际派发次数          = 4096 × 8 = 32,768
```

多出来的 8,192 个槽位就是缓冲区，占实际工作量的 25%。路由完全均匀时它们全空着，路由不均衡时它们被填上一部分，剩下的仍然空着。这部分算力是真金白银花掉的，因为 GEMM 不区分真实 token 和空槽位。

容量算完之后，丢弃的动作长这样：

```Python
import math
import torch

def expert_capacity(num_tokens, num_experts, topk, capacity_factor):
    # 容量按“派发次数”计，topk 必须乘进分子
    return max(math.ceil(num_tokens * topk * capacity_factor / num_experts), 1)

def apply_token_dropping(topk_ids, topk_probs, capacity, num_experts):
    """probs 策略：每个专家只保留路由概率最高的 capacity 个 token"""
    flat_ids = topk_ids.view(-1)          # 形状 [tokens * topk]
    flat_probs = topk_probs.view(-1)
    keep = torch.zeros_like(flat_ids, dtype=torch.bool)

    for expert in range(num_experts):
        hits = (flat_ids == expert).nonzero(as_tuple=True)[0]
        if hits.numel() > capacity:
            _, top = flat_probs[hits].topk(capacity)   # 超容量时砍掉低概率的
            hits = hits[top]
        keep[hits] = True

    # 未保留的位置权重置 0，专家输出为 0，该层退化成恒等映射
    kept_probs = flat_probs * keep
    return flat_ids.view_as(topk_ids), kept_probs.view_as(topk_probs), keep
```

`probs` 是 Megatron 的默认策略，实现上就是对每个专家的候选 token 取概率 top-k。另一条路 `position` 按位置截断，谁排在前面谁留下，看起来更“公平”，实际会系统性地牺牲序列后段的 token。

## 溢出之后，token 走的是残差

被丢的 token 并没有从序列里消失。GShard 论文 §2.2 的原话是，两个专家都超容量时，gating 输出「退化为零向量」，token 的表示 `x_s` 经由残差连接送到下一层。Switch 的措辞一样：计算被跳过，token 表示直接穿过残差进入下一层。

写成式子更清楚。对一个正常路由的 token：

$$
y_t = x_t + \sum_{i \in \text{top-}k} g_{i,t}\,\text{FFN}_i(x_t)
$$

被丢弃时，求和项为 0：

$$
y_t = x_t
$$

它仍然参与后续所有层，只是少了这一层专家提供的非线性变换，连带这一层对它的 router 也没有梯度。丢的不是数据，是更新。

同一块容量缓冲里其实有两种方向相反的动作。丢弃砍掉的是被路由过来的真 token，而 `pad_to_capacity` 补上的是没人要的空槽位。

麻烦在于丢谁不由内容决定。OpenMoE（arXiv 2402.01739）把这件事列进了三个主要发现之一，命名叫 Drop-towards-the-End：在 decoder-only 结构里，序列靠后的 token 更容易撞上已经被填满的专家。他们给的例子很具体，如果某个专家偏好换行符，序列开头一堆换行符就能把它填满，后面本该路由到它的 token 全被丢掉。

这份工作还有两个相关发现。OpenMoE 观察到路由决策主要由 token ID 决定，与上下文的关联很弱，而且 token 到专家的对应关系在预训练早期就基本定型。一个在预训练语料里成型的偏好，会一路带到对话任务里。指令数据的分布不在那个偏好覆盖的范围内，丢弃率自然就高。

这解释了为什么平均丢弃率很低和局部任务受损可以同时成立：丢弃集中在特定位置和特定分布上，平均值掩盖了分布。

## 丢多少算多

Switch Transformer 报告的数字是：整个实验过程中，被丢弃的 token 通常低于 1%，而且这个比例与专家数量无关。他们配了足够强的负载均衡损失，把不均衡压在了这个量级。

但靠调大容量因子去换更低的丢弃率，账算不过来。同一篇论文的 Table 1 给了很直接的一组对比：Switch-Base 在容量因子 2.0、1.25、1.0 三档下的吞吐分别是 860、910、1000 examples/sec，达到质量阈值的时间是 72.8、65.0、62.8 小时。

容量因子越小，反而越快也越好。论文 §2.3 的结论写得很干脆：Switch 在低容量因子（1.0、1.25）下表现更好。

那个“丢 token 会伤质量”的直觉，在 ST-MoE（arXiv 2202.08906）这里被限定了。他们做微调实验（Table 5），把容量因子压到 0.75，丢弃率升到 10.6%，SuperGLUE 是 86.5±0.21；容量因子 1.25、丢弃率 0.3% 的那组是 86.7。

原文的结论是，丢掉 10–15% 的 token 和丢掉不到 1% 的 token，表现大约相当。脚注里甚至猜了一句，token dropping 可能是一种正则化。

同一张表还暴露了另一层关系。关掉均衡损失、容量因子 1.25 时丢弃率是 2.9%，开着均衡损失时是 0.3%。容量因子决定上限，均衡损失决定你离上限有多近。

也不是所有实验都这么宽容。MegaBlocks（arXiv 2211.15841）在小规模对比里发现，容量因子 1 的 MoE 比稠密 Transformer 的验证损失低 0.15，完全不丢 token 的那版低了 0.26，是前者的 1.73 倍。

为了让收益充分兑现，MoE 层的数学运算量增加了两倍以上。同一篇论文还引了 Tutel 的结论：有些 MoE 要把容量因子开到 11 才能做到不丢 token。

ST-MoE 和 MegaBlocks 的结论并不矛盾：丢弃率与质量的关系是非线性的，低丢弃率区间里质量对丢弃不敏感；而容量因子与成本的关系接近线性，调大一档就多花一档算力。

ST-MoE 的 Table 9 把这个成本随模型规模放大的过程量出来了。容量因子从 1.25 提到 2.0，10 亿参数的 ST-MoE-L 每步慢 7%，320 亿参数的 ST-MoE-32B 慢 14%。模型越大，同样的缓冲倍数越贵。所以 ST-MoE 在 32B 那档上选择了 1.25，而不是 GLaM 等工作常用的 2.0。

## 均衡损失的代价，和一条绕开它的路

不均衡是丢弃的根因，均衡损失（auxiliary load balancing loss）是最早的解法。Switch 的写法是让实际分配比例和路由概率均值对齐：

$$
\mathcal{L}_{\text{balance}} = \alpha \cdot E \sum_{i=1}^{E} f_i P_i
$$

f 是实际派给专家 i 的 token 比例，P 是路由概率里分给 i 的份额，α 是乘子，Switch 用 1e-2。均匀时这个乘积最小。

问题在于这个损失项会挤占模型本来该学的信号。Tutel 论文（MLSys 2023 版）的 Table 1 标题直接叫「严苛的负载均衡伤害 MoE 精度」：在 ImageNet-22K 上训 SwinV2-S、32 专家、top-1、容量因子设为无限，均衡损失权重 0.001 时 Acc@1 是 37.32，0.01 时最高到 37.78，1.0 时掉到 34.71。

从峰值算起，掉了三个多点的精度，换来的是一个本可以靠别的手段达成的均衡。

DeepSeek 换了个思路。V3 技术报告（arXiv 2412.19437）§2.1.2 里，他们给每个专家挂一个偏置项 b，只在选 top-k 的时候加到亲和分数上：

$$
g'_{i,t}=\begin{cases}s_{i,t}, & s_{i,t}+b_i \in \operatorname{TopK}(\{s_{j,t}+b_j\},\,K_r)\\ 0, & \text{otherwise}\end{cases}
$$

关键在于 b 只参与“选谁”，不参与“给多少权重”。门控值仍然来自原始亲和分数，所以偏置不改变被选中 token 的加权方式，也不会像均衡损失那样往模型里灌一个额外目标。训练时每一步结束统计各专家的负载，过载的减 γ，欠载的加 γ，γ 是偏置更新速率。

这套做法让 V3 在整段训练里保持了不错的均衡，报告里因此有一句很干脆的话：

> DeepSeek-V3 does not drop any tokens during training.

还有一条更彻底的路。Expert Choice（arXiv 2202.09368）把选择方向翻过来，让每个专家自己去挑固定数量的 token，桶大小按 `k = n·c/e` 定，均衡由构造保证，连均衡损失都不需要。代价是每个 token 被几个专家选中变得不确定，而这件事在工程上不好并行。

训练侧靠丢 token 控制不均衡的做法，已经退居边缘。

## 拆掉补丁要付的钱

不丢 token 不等于没有代价，只等于代价换了形式。

MegaBlocks 的做法是把 MoE 计算重写成 block-sparse 矩阵乘，用新写的 GPU kernel 处理动态路由，它在 README 里说自己把 `capacity_factor` 这个超参整个去掉了。

但它的 kernel 有一个硬要求：每个专家分到的 token 数必须是 block size 的整数倍，所以 permutation（重排）阶段还得 pad 到最近的倍数。丢弃换成了补齐，形状问题并没有消失。

推理框架走的是同一条路。vLLM 的 `moe_align_block_size` 文档原文是 "Aligns the token distribution across experts to be compatible with block size for matrix multiplication"，对齐，补齐，不是丢弃；

在专家并行下它把不属于当前 rank 的专家 ID 标成 -1，让矩阵乘直接跳过那些 block。

补齐之外还有三笔账：

1. 通信从定长变成变长。dispatch 和 combine 的 all-to-all 数据量随路由波动，静态规划失效，需要专门的原语
2. straggler（掉队者）。最忙的那个专家决定整层延迟，其余专家空等，负载越偏浪费越大
3. 编译期优化受限。形状动态，很多需要静态图的技术用不上

第三点解释了容量因子为什么没被彻底移除。Megatron Core 的文档里写得很明确：当 `--moe-expert-capacity-factor` 和 `--moe-pad-expert-input-to-capacity` 没有同时设置时，MoE 层是动态形状，**无法被 CUDA Graph 捕获**；

这种情况下可以退一步，只对 attention 层开 `--cuda-graph-modules=attn`。

于是容量因子完成了一次身份转换。它不再是“训练时要不要丢 token”的取舍，而变成“这一层要不要为了静态形状放弃 CUDA Graph”的开关。名字没变，语义变了。

### 折成配置是四条

把前面这些压到实际配置上，大概剩四件事：

1. **默认不开。** Megatron 把它设成 `None` 是有道理的，训练侧不丢 token 已经是主流做法，先让形状动态，只在确实需要静态图时再打开。
2. **要开就把 pad 一起开。** 单独设容量因子只会得到一个被截断的动态形状，MoE 层照样进不了 CUDA Graph，等于白付了丢弃的代价。
3. **先压不均衡，再谈容量。** 均衡损失系数从 Switch 用的 1e-2 量级起步，别指望靠调大容量去解决路由倾斜。Tutel 那张表说明，均衡损失压过头，精度掉得比丢 token 更快。
4. **非要丢就选 `probs`。** `position` 策略系统性地牺牲序列后段，正好撞在 OpenMoE 观察到的位置偏差上。

还有一条换框架时的换算提醒：`capacity_factor` 这个数字不能脱离路由配置单独看，换框架前按「四套写法」那节的通用式重算一遍。

## 推理侧的分岔

训练侧的账算得很清楚，推理侧却分成了三条路。

DeepSpeed 保留了原来的语义。`MoE` 层构造函数的默认值和开头那组一致，训练和推理都默认按容量截断。要关掉得显式加 `--disable-moe-token-dropping`，官方教程还特地注明这个开关更适合推理或评估阶段使用。

推理阶段没有梯度可以稀释伤害，默认丢弃路径的质量代价需要单独评估。关掉之后，容量不再由超参决定，而是取当前 batch 里最忙那个专家的实际 token 数，并在专家并行组内做一次 MAX all-reduce。

vLLM 走的是补齐那条路，不设容量上限，按实际路由做 all-to-all 加 grouped GEMM，再把每个专家的 token 数补到 block 的倍数。

DeepSeek 走的是第三条路，既不丢也不补，而是搬。V3 的结构里，每层有 1 个共享专家加 256 个路由专家，每个 token 激活其中 8 个，并且被限制最多送到 4 个节点。

这套结构在部署时会遇到一个新问题：不均衡不再表现为丢 token，而表现为某些 GPU 上专家挤爆、另一些 GPU 上专家闲置。他们的解法是 EPLB（专家并行负载均衡器），把高负载专家复制成冗余副本，再把这些副本重新打包到各张 GPU 上，让每张卡的负载大致持平。

V3 技术报告给的具体数字是：预填充阶段设置 32 个冗余专家，每张 GPU 原本承载 8 个专家，再加 1 个冗余专家；解码阶段的配置不同，每张 GPU 只承载 1 个专家，另有 64 张 GPU 负责冗余专家和共享专家。

高负载专家的集合根据线上统计每隔一段时间（报告举例 10 分钟）重新计算一次。这套算法开源在 `deepseek-ai/eplb`（据仓库 README），vLLM 也把它做成了 `--enable-eplb` 开关。

代价是冗余副本常驻显存，重打包本身有迁移开销；10 分钟级的重算粒度意味着突发流量下会有滞后。

**不均衡一直存在，只是被挪到了一个更愿意承担它的地方：从「丢掉 token」挪到「多占显存」。**

三条路的差别，本质上是三种目标函数：

- DeepSpeed 那类推理栈要的是形状和显存可预测，容量因子顺便充当了显存上限
- vLLM 那样按实际路由补齐的引擎要的是吞吐，宁可多占显存也不能让请求的形状随机波动
- DeepSeek 的 EPLB 要的是节点间负载持平，代价是冗余副本常驻显存

训练阶段的目标函数另算：要的是梯度和质量，丢几个 token 只要不破坏收敛就可以接受。

---

回到开头那组相反的默认值。它们并不冲突，因为它们回答的已经不是同一个问题了。

容量因子的原始动机是让矩阵的形状在编译期就能确定下来。这个动机在今天依然成立，稠密 GEMM 依然要求行数固定，CUDA Graph 依然要求形状静态，推理侧的显存预算同样要求每层占用可预测，变长 all-to-all 依然比定长贵。真正被拆掉的是它的副作用部分：在主流训练栈里，靠丢弃来控制不均衡的做法，已经大致被均衡损失和偏置控制器压到可以忽略，残余的不均衡则由部署侧的冗余专家处理。

所以它现在的处境有点像编译器里的一个开关。平时没人想起它，直到你想把某个 kernel 抓进计算图，或者显存算得太紧，于是翻回配置里把它打开，顺手把 pad 也打开。打开之后会发生什么，取决于你用的是哪个框架：Megatron 里打开它会同时引入丢弃和静态形状，DeepSpeed 里它从诞生起就绑定丢弃语义。

一个为静态形状而生的补丁，最后以静态形状的名义活了下来。
