# 63 万行证明对 110 行规格：形式化验证把信任边界缩到了哪里

> **导读**：2026 年 10 月，Anthropic 让 Claude 为 123 个开源库、239 个入口点写出形式化证明，证明它们在 64 MB 以内的任意输入下都不会崩溃。产出的证明约 1.8 亿行，没有人能逐行读完。这篇文章不讨论「AI 会不会证定理」，而是沿着一条定理往回退四层，看每一层还剩什么需要人信：定理陈述、语义模型、证明检查器、硬件。退到最后，能审的东西确实少了，但少掉的部分没有消失，只是从「更多代码」变成了少数几个具体假设和部件。

一个 391 行的 C 解析器入口，最后配了 63 万行证明。而这一批证明的规格，中位数是 110 行。

这三个数字的方向是反的。程序最短，证明最长，而最靠近人类意图的那一端，比程序还短。

2026 年 10 月 22 日，Anthropic 的 Frontier Red Team 与 Theorem 联合发布一项实验，让 Claude 为 239 个入口点、123 个 OSS-Fuzz 库生成形式化证明（formal verification，用数学推导而非测试来确认程序性质）。OSS-Fuzz 是谷歌维护的持续模糊测试服务，用随机变异输入去撞程序的崩溃。整个过程「数周」，产出约 1.8 亿行 Rocq（Rocq 原名 Coq，一个交互式定理证明器）。

Hacker News 上这条讨论拿到 475 分、312 条评论（2026-11-03 计），争的不是证明对不对，而是「证明的是不是你想要的东西」。

## 先把定理摆正

「零崩溃」不等于「没有漏洞」，两者差在证的对象上。

证明对象不是源码，是编译后的 RISC-V 二进制（一种开放指令集架构的机器码）。整套实验实际上证了三条定理：

1. ASan（AddressSanitizer，运行时检测内存越界的工具）版本与普通版本都不会遇到故障、不会 abort、不会出现模型外的行为；
2. 两个版本产生相同的读写序列、相同的退出方式、相同的文件系统终态；
3. 普通版本自己也不崩。

第二条容易被跳过，但它才是这件事有意义的前提。fuzzer 跑的是插了 ASan 的版本，用户跑的是普通版本，不证两者等价，第一条就只是关于测试二进制的孤立结论。

「崩」不只指段错误，还包括断言失败，以及语义模型里没有定义的任何行为：

```text
# Anthropic 对「崩溃」的定义，三件事都算
def is_crash(run):
    return run.fault        # 访问未映射内存
        or run.abort        # assert 失败
        or run.unmodeled    # 语义模型里没写这个 syscall

# 要证的定理（伪代码）
Theorem no_crash(prog):
    forall input, layout:
        len(input) < 64 * 1024 * 1024 and layout in modeled_layouts  # 输入上限 64 MiB
        -> not is_crash(run(prog, input, layout))
```

「未建模行为算崩溃」这一条是保守设计。模型没写到的系统调用，一律按不安全处理，宁可证不出来，也不放过。代价是证明规模会因为模型的覆盖不足而膨胀：模型每漏一个系统调用，要么补语义，要么改定理，两边都会让规模涨。

范围限定写在正文里：

- 单线程、静态链接
- RISC-V 与 Linux
- 固定内存预算，输入上限 64 MB（附录口径为 64 MiB）

这批 bug 的触发条件都很刁钻：一个解压器里的计数器下溢导致越界写，只在约 20 MB、且内存布局极特殊的输入上触发；一个图像解码器的越界读需要 64 MB 输入和超过 2 GB 内存。Anthropic 在正文里点明了 fuzzer 为什么碰不到：它变异的输入通常被限制在 1 MB 以内。

而定向 fuzz 的一项实测（FuzzGuard，USENIX Security 2020）显示，超过 91.7% 的生成输入根本到不了目标代码。

所以两种手段的差别不在谁更聪明，在搜索空间：fuzz 证的是「跑过的都没崩」，证明证的是「跑不到的也不崩」。

## 为什么这件事在 2026 年才划算

形式化验证不是新东西。seL4（一个经过完整形式化验证的操作系统内核）的验证 2009 年就完成了，CompCert（一个经过形式化验证的 C 编译器）的正确性证明也在同期落地。它们没有普及，一个主要障碍是账算不过来。

先看旧的账。seL4 的 C 实现只花了 2 人月，加上 Haskell 原型共 2.2 人年；证明本身约 20 人年，其中 9 人年投在可复用的语言框架和证明工具上，seL4 专属的部分是 11 人年。CompCert 是 10 万行 Coq、6 人年。这笔投入只有空客航电这类场景付得起。

新的成本是数周时间，一份证明可耗数亿 token。Anthropic 没有公布总数，只写了「proofs can take hundreds of millions of tokens to produce」（网传的效率数字仅来自 36 个缩小版任务的模型间比较，不代表全量证明的成本）。

两者证的性质不在一个量级，这里只比单位成本的变化趋势，不构成等价对比。

同一篇里还有一组对照，说明这笔投入买到了什么。Claude 用 Rust 重写了一个 Python 大子集的解释器，用 Verus（一个面向 Rust 的验证器）证明它符合论文里的 CPython 语义，在超过 170 万个（大部分随机生成的）Python 程序上做了经验对比，行为一致率为 99.95%；但真正说明问题的是注入实验：往解释器里注入 7 个 bug，随机测试只发现其中 2 个，另外 5 个躲了过去，而证明把 7 个全部拦下了。

成本降下来只是必要条件；真正让它在 2026 年划算的，是另一头的账变了：待审的代码比待证的涨得更快。

人审代码本身也是一条链。这是一个刻意简化的模型：设链路长度 n 是必须读的代码行数，单行读到位的概率是 p，整份代码被真正读通的概率就是 p 的 n 次方；0.95 和 20 步只是一组示例参数，代进去是 35.8%，这个乘法结构在《95% 的自信走 20 步只剩 36%》里算过。它不是说人会逐行读，而是说关键路径上必须由人拍板的判断点越多，整份代码被真正把握的概率按乘法衰减。代码规模越大，这条路越先到极限。

AI 把代码产量继续推高，这条链先到极限的就不会是产出，而是审阅带宽。形式化验证做的事情，是把 n 从「代码行数」换成一个固定项。

**不是证明变便宜了，是人审变贵了。**

这次实验的价值，在于它让「固定项」和被验证代码规模之间的脱钩变得足够明显：证明产能和待审代码量同时被 AI 推高，中间那道人工审阅的窄门才显得可以绕开。

## 往回退一层：定理陈述凭什么算数

定理不是从天上掉下来的，它需要一个陈述。这个陈述就是规格（spec）。

形式化验证通常最卡在这里。写规格要求有人先把「这个程序该做什么」说清楚，而这件事往往比写代码难。这次实验绕开它的办法是：不写规格，把原有的 fuzz test 机械转换成规格。

做法是把「这个测试套件永远通过」这句话编码成一条定理。工具把 ELF 文件（可执行文件格式）转成内存镜像，接上 Theorem 提供的 RISC-V 与 Linux 进程语义，再加上「不崩」这个目标性质，由这三样机械地生成规格。原来的 fuzz test 从「跑一遍看崩不崩」变成了「对所有输入证明不崩」。

规格因此非常小。附录给的中位数是 110 行，而被证程序的中位数是 86 KB，证明覆盖的是 fuzz driver 实际走到的 20% 到 50% 代码。

小是优点，也是天花板。

优点在于 110 行是人能读完的。天花板在于，读完只能确认「这份规格确实表达了原测试那句话」，没法确认「原测试那句话覆盖了这个库值得保证的全部行为」。前一个问题有机器答案，后一个没有。

测试领域对这件事有个名字，叫 oracle problem：给定一个输入，怎么判断输出是对的。Barr 等人在 2015 年的综述里写得很清楚，当已有的自动化判定方法没有一种完全够用时，最后的 oracle 只能是人。把测试转成规格，等于宣布原来的测试就是 oracle。这个宣布本身没有经过证明。

它也不是 Anthropic 的发明。2026 年的一项工作（FVSpec: Real-World Property-Based Tests as Lean Challenges，arXiv 2606.01008）把真实 Python 仓库里的 property-based test（基于性质的测试）自动翻译成 9,415 条 Lean 规格（Lean 是另一个主流定理证明器），这些规格带 `sorry` 占位符，属于待完成的挑战样本。同样的转换，在学术上已经是已知范式。

CACM 2025 那篇评论的标题更直接：《It's the Specification, Stupid!》。里面有一节就叫「规格缺口」（The Specification Gap），原文的说法是，即便最精确的规格，最多也只是墙上的影子。

2026 年 10 月还有一条旁证：OpenAI 证伪指数时间假设后用 Lean 做了形式化，但从公开的 Lean 目录看，机检的是弱一档的界，论文头条更紧的界没有进入机检；数学侧把可机检的陈述压得比对外宣称的结论弱一档，代码侧把规格压得比程序该保证的行为窄一档，两边是同一类缺口。

Anthropic 自己在限制章节写了这句话：证明检查器没法告诉你，你的规格是否与现实相符。

所以这一层剩下的是：**规格是可读的，但不是可证的。**

## 再退一层：语义模型凭什么可信

这条定理甚至不是关于 C 代码的。它是关于「RISC-V 指令在 Linux 进程模型下如何执行」，而这个模型由 Theorem 提供。

模型也是产物，也会错。

同一篇里的 zlib 实验是个好例子。Claude 先为 RFC 1950 写形式规格，再证明 Linux 内核里的 zlib 实现符合它，而且不在 RISC-V 上绕，直接在 x86 二进制上做，用的是 Claude 自己生成并大量测试过的 x86 语义。生成这套语义的过程中，它在官方参考手册里找出数百处错误，还找出硬件本身的少数几个 bug。

一个由 AI 写的语义模型，一边用来证明别人的代码，一边顺手纠正了芯片手册。这件事说明语义模型这一层不是给定的地基，是一份需要被审查、也会被修订的文档。

seL4 的假设清单是最好的对照，官方把它逐条列在网站上：

- 约 340 行 ARM 汇编，假定正确
- 约 1,200 行启动代码不在证明范围内
- 假定 CPU 和 MMU（内存管理单元）是唯一直接访问内存的设备，DMA 设备（能直接读写内存的外设）要么不存在，要么不捣乱
- 虚拟内存那一部分，官方原话是「证明并不强制我们做到完整」（按常规形式化验证标准，这一部分通常不算作假设，只是保障度更低），存在人为遗漏的空间
- 时序侧信道不在保密性证明的覆盖范围，官方原话是「我们知道这个假设不成立」

seL4 团队这样定位这份清单：

> 能清晰列出穷尽的假设，意味着完全信任一个系统所需的工作，从查看几千行代码缩减为查看少数几个小而具体的部件。

CompCert 那边有一篇专门计算可信基（trusted computing base, TCB）的论文（Monniaux & Boulmé, ESOP 2022），结论是 bug 全部落在未证部分，但可信基「可能并不像我们天真以为的那么小」。它举了一个具体例子：CompCert 假定 malloc 永不失败、永不返回空指针，作者自己的评价是「这看起来站不住脚」。

## 再退一层：检查器凭什么不出错

假设规格写对了、语义模型也没问题，还剩最后一环：检查证明的那个程序。

现代定理证明器靠一个很小的内核（kernel）保证这一点，学术上叫 de Bruijn 判据：内核只负责判定一份推导是否合法，所有花哨的自动化策略都在内核外面跑，跑错了也造不出假定理。Rocq 的内核约 4 万行 OCaml（2019 年的文献口径为 2 万行），HOL Light（另一个定理证明器）的内核只有约 400 行。

小不等于没有 bug。

一篇讲类型检查器正确性的论文（JACM 2025）里有一句话：平均每年，Coq（今 Rocq）里会发现一个 critical bug。官方仓库的 `critical-bugs.md` 截至 2026 年 11 月仍挂着标「fixed in: NONE」的条目。

2026 年 7 月，Lean 的内核也出了事。一个恶意元程序可以让内核接受 `False` 的证明，绕过了类型检查器。有人据此发布了一份没有 `sorry` 的 Collatz 反证，内核接受，连独立的第三方检查器 nanoda 都放行了。原因是 nanoda 自己也有一个不相关的 bug，两个独立的 bug 叠在一起，假的才通过。

这条记录说明两件事：检查器可错；独立检查器能降低风险，但不能消除风险。Lean 团队事后又找出一批内核实现错误，均被 nanoda 捕获并已修复。

不过这一层出错的机会仍然很低。CompCert 那篇论文的说法是，靠碰运气撞上检查器 bug 的机会很小（该判断早于 2026 年的 Lean 事件，针对的是随机撞上的概率）。

## 最后一层：硬件、操作系统、编译器

Anthropic 的正文列了三样需要信任的东西：RISC-V 与 Linux 进程的形式模型、被证明的定理陈述本身、Rocq 检查器。脚注补了一句：严格说还要信任运行检查器的硬件、操作系统和 OCaml 编译器。

退到硬件与运行环境，这一层没法再往下拆了。

这一层最有力的证据不是推理，是 seL4 的时间记录。功能正确性证明 2009 年完成，到 2026 年，已证代码没有出现过功能缺陷。同期，每一类未验证代码都发现过小缺陷：硬件假设、编译器假设、未验证的启动代码。

> 缺陷没有消失，它们搬到了边界上。

证明不生产确定性，它搬运确定性：把散落在几万行代码里的信任，压缩到几个可以单独审视、单独争论、单独出事的部件上。

## AI 自己修，自己证

实验中，Claude 发现 bug 之后直接打补丁、重新生成规格、继续证明。

效率很高，风险也很清楚。证明保证的是补丁之后的代码符合规格，不是补丁本身是正确修法。规格来自原来的 fuzz test，如果补丁顺手改变了别的行为，证明不一定拦得住。

Anthropic 的处理是：惩罚打补丁，对「证明这个补丁只改变了哪些输入」给额外奖励，所有补丁记录并审计。这是一个把「改动面」变成定理的思路。更根本的限制在于，规格、证明、补丁若出自同一个模型，共享的盲区不会自己暴露；审计补丁记录是对的，但审计者仍需要独立于这个模型的判断。

它和十月 Trail of Bits 的实测接得上（2026-10-21）：那批 130 多个已合并的 Agent PR 里，确认了 21 个回归。修好一个 bug 和证明没有改坏别的东西，是两件事。

区别在证据强度。Trail of Bits 靠可执行的 PoC（能复现问题的样例代码）和三角验证，Anthropic 靠「改动面最小」的定理。后者更硬，但只覆盖被规格框住的那部分行为。补丁改动了规格之外的东西，定理不会说话。

## 三个误区

**一、把 1.8 亿行当成能力的度量。** 附录里写的是另一组数：Claude 前后一共写了约 10 亿行 Rocq，最终约 1.8 亿行通过检查器、真正满足规格，按这两个数推算，存活率约 18%。长度也不全是推理：附录举的 cJSON（一个 C 语言的 JSON 解析器）例子是 391 行入口点、63 万行证明，其中只有约十分之一与 cJSON 有关，其余是 C 启动、malloc、printf、ASan 运行时和 fuzz driver，而每条证明都要把这些从零重证一遍，不能 import。照这个例子看，证明长度目前更多反映工具链有多少现成部件可复用，而不是模型的推理能力。

**二、认为拿测试当规格等于作弊。** Hacker News 上有一条原话：「他们又作弊了，拿覆盖率可能很糟的现成测试套件当规格。」这个批评对了一半。规格确实弱，但如果没有这次转换，连弱规格都写不出来。缺口没有被绕过，只是从「写不出」变成了「写得不对」。前一个问题工具能解，后一个不能。

**三、觉得直接跑完 64 MB 以内的输入更便宜。** 输入空间不是一个数，是输入、内存布局、系统调用响应三者的组合，测不过来。而且这次要证的代码规模本身是被 AI 推上去的，真要逐条路径跑一遍，要跑的时间也会跟着规模涨。规模问题靠换手段，而不是加机器。

还有一条不在误区里，更接近免责：**「已证」不等于「安全」**。Anthropic 自己列了三条限定：

- ASan 不检测所有内存安全 bug；
- 没有验证每个库的所有入口点；
- 真实程序还可能误用这个库。

仓库 README 写得更直白：证明没有说这个库是正确的，sanitizer 查不出的错误，比如结果算错、内存泄漏，不在排除范围内。

还有一层选择上的偏差：这批库本就是 fuzz 生态里测试最全的一批，换一批没有现成测试的库，110 行这个规格规模未必成立。证明可以由任何人拿公开仓库复跑检查器；语义模型与规格，目前未见公开的独立审读记录。

## 团队要不要上，怎么上

- **从入口点入手，不从库入手**。这次证的是入口点，死代码和调用方误用都不在范围内。把「已证」理解成整库安全，是最常见的误读。
- **把规格当评审对象**。110 行是能读完的，读的时候要问的是「这个 fuzz test 代表了哪一部分行为」，不是「这条规格写得对不对」。
- **挑复用率高的基础库**。证明可以复用，但今天每条证明仍要从零重证运行时，复用价值还没有兑现。基础库、协议实现、解析器是合适的起点。
- **给 Agent 留证据链**。补丁要能回答「改了哪些输入」，而不只是「测试过了」。前者是可审计的，后者是自证的。
- **对外表述留一寸**。写「在模型与假设下不崩」，不写「没有漏洞」。这两句话之间隔着一整套假设清单。

## 结尾

回到开头那三个数字。391 行的程序，63 万行的证明，110 行的规格。

如果只记一个，记 110。63 万行的证明会随工具成熟而缩短，391 行的程序取决于库本身，而只要「哪份测试算数、覆盖哪部分行为」的判断仍要人来做，110 这个量级就很难跟着缩，它标记的是人的位置。

人能读的东西确实在变少。以前读代码，后来读测试覆盖率，现在读规格。每一步都更短，但每一步都更需要判断，判断的不是「写得对不对」，是「这够不够」。

证明能替你排除跑得到和跑不到的路，但它没法替你决定，这条路该通向哪里。这件事至少目前没有被自动化过。
