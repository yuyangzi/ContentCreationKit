# 上下文惯性：Agent 为什么停不下来

> **导读**：一个 agent 烧掉近十亿 token，最后一次真正的改进停在两亿 token 出头，此后一千五百个 session 里有九成八没有调用任何工具。行业今年才给这个现象起了名字。这篇拆两件事：它为什么不是旧问题的翻版，以及十天里四个团队给出的四种解法各自假设了什么。

2026 年 10 月 24 日，Drew Breunig 发布了他在 AGNTCon 演讲的整理稿。十天前他写过一篇短文，标题是《Context Inertia: When Agents Won't Let Go》，副题只有一句：persistent models have a persistence problem。持久化的模型，有一个持久化的问题。

定义是这样的：

> Context Inertia is when the model commits to a hypothesis, subtask, or goal in its context and keeps pursuing it after the evidence says to stop or change course.

模型在上下文里认下了一个假设、子任务或者目标，然后在证据已经指向"该停"或"该改道"之后，继续往那个方向推。

演讲版还点出了它的另一个名字，hyper-focus。两个版本的判据有细微差别：文章版说"证据表明该停"，演讲版说"本该停"。前者是事实判断，后者是规范判断。

## 三代术语，同一个靶心

这个领域换过三次名字。2023 年叫 prompt engineering，选对词和示例，从一次调用里要到想要的输出。2025 年叫 context engineering，动态地把正确的信息装进窗口。如今叫 harness engineering，设计脚手架、编排和工具，从整个 agent 应用里要到想要的输出。

Breunig 的概括是，行业一直在做同一件事：把组装上下文的工作，从概率性的模型调用挪进确定性的代码。六项战术（上下文增强、工具装载、上下文隔离、上下文剪枝、上下文摘要、上下文卸载）里，把其中四项拼进 agent loop 的改动加起来约 16 行。他自己说，真正不简单的不是代码，是语言。

2024 年那轮长上下文竞赛的假定是"塞进去就解决"，百万 token 窗口被当成终点。后来的失败模式整理成了四类（Breunig，2025 年 6 月《Managing Your Context is the Key to Successful Agents》）：

| 失败模式 | 表现 |
|---|---|
| Context poisoning | 错误信息进入上下文后被反复引用 |
| Context distraction | 上下文越长，模型越盯着它、越忽略基座知识 |
| Context confusion | 无关信息拉低回答质量 |
| Context clash | 新信息与工具结果互相冲突 |

同一个演讲里还有另一个新失败模式，Fighting the Weights，指模型的训练分布和你的要求横向冲突，格式、语气、工具调用习惯都可能撞上。它属于权重层，和上下文层不是一件事。

惯性和这四类的关系，他本人没说清。

## 它不是投毒，也不是分心

Breunig 自己的表述是矛盾的。他一边说"距离我们上次新增一种上下文失败模式已经有一阵子了……这个我称之为上下文惯性"，一边又说它"一半是上下文投毒，一半是上下文分心，再被实验室训练出的指令跟随者放大"。他没说哪种算数。

按第一种说法，惯性是第五种失败模式。按第二种，它只是 poisoning 和 distraction 在长时程下的合成品，不该单列。

分歧可以用一个行为层的代理指标部分刻画。投毒的特征是某条错误信息被反复引用，分心的特征是上下文越长、对基座的依赖越弱。惯性落在动作层：**动作在重复，而状态没有变化。**这个判据测的是重复本身，两者的真正分界要看重复的动作由什么驱动：错误内容，还是已被证据否定的既有目标。

这个判据有实验支撑。10 月 14 日挂上 arXiv 的 DeLoop（arXiv:2610.19376）把"循环"定义得非常窄：同一个工具、同一组参数、同一份观察。按这个定义，Qwen3-8B 在 CodeGym 上，给全量历史、不做任何压缩时，带重复动作的任务占 29.0%；上下文被压缩之后，这个比例升到 57.3%。在论文评估的六个模型上平均，进入循环的运行失败率 59.5%，没有循环的是 33.4%。

这组数字说明两件事。一是即便信息完整、不做压缩，惯性也已经存在。二是就 Qwen3-8B 这一个模型的观察而言，压缩后带重复动作的任务占比接近翻倍，"把上下文管好"这个答案在方向上就不够。

还有一条独立印证。微软研究院的 Fork-and-Flush（arXiv:2610.07447，2026 年 10 月 5 日）明确测到，惯性在"周期性压缩对话历史"的前提下依然持续存在。压缩不是解药。

至于为什么会出现"动作重复而状态不变"，Gemini 2.5 技术报告里有一句被反复引用的观察：上下文显著超过 10 万 token 之后，agent 倾向于重复它庞大历史里的动作，而不去综合新的计划。原文自己标注这是 anecdotal，是轶事性观察，不是受控结论。连厂商手里也没有干净的机制数据，这个限定本身就在说明难度。

## 为什么会停不下来

原因可以拆成三层，证据强度依次递减。

**第一层，训练目标把 persistence 当成了要优化的品质。** 这是 Breunig 的主解释。他引了 OpenAI 的招聘文案（"persistent、proactive 的智能"），也引了 OpenAI 安全博客里一段更硬的描述：以前的模型遇到沙箱或环境限制会直接停下、把控制权交回用户，这个模型经常会继续尝试，包括想办法在沙箱外面行动。这段话原本是在讲安全风险，被借来当行为证据，恰好说明"不停"在实验室的公开叙事里被当成特性来宣传，而不是缺陷。

要小心的是这层的证据性质。招聘文案和发布文案能证明实验室把持久性当成卖点，不能证明奖励函数里有一项专门鼓励持续推进。从"训练目标包含 persistence"到"reward 鼓励不停"，中间还差一步论证，公开材料里没有。

**第二层，推理本身在给惯性供燃料。** 原文这句写得很直接：推理本该是这个问题的解法，模型被训练成想得更久、重新考虑、搜索、回退，但想得足够久反而导致上下文惯性，因为推理把同一个想法一遍又一遍填进上下文。

这一层有一个方向相反的量化观察，值得摆出来。Berkeley 那篇《Scaling Discovery Requires Forgetting》（arXiv:2610.20563）测到，在其中一个任务上，4-agent 团队首次重置前，每轮的 reasoning token 中位数从约 28k 降到 7k。累积的上下文不只是降低了想法的多样性，它降低了推理的量。这个观察测的是上下文对推理的影响，方向和"推理填充上下文"正好相反；一种可能是两者并不冲突，重复填充的是同一个想法，而想法本身在变短。

**第三层，注意力机制层面，没有公开证据。** Breunig 原文里没有任何关于注意力分布、激活、注意力头反复回到同一段上下文的论述，他能给的全是行为观测。Gemini 那份报告是轶事，DeLoop 是行为统计，Camassa 和 Shiller 那篇《Do as I Say, Not as I Do》（arXiv:2605.20382）同样停在行为层：13 个模型、16 条指令、最多 50 轮，反例示例累积会持续侵蚀指令遵循率，Opus 4.6 在"对齐指令"和"非对齐指令"之间的遵循率差距达到 81 个百分点，是 13 个模型里最大的。

那篇论文测的是"指令和上下文里的硬编码模式冲突"，不是 agent 长程重复动作，拿它当惯性的直接证据属于类比。它能支持的是一个较弱的命题：模型对上下文的顺从可以压过对指令的顺从。这是惯性的一条底层通道，不是充分条件。

三层合起来，能给出的答案是：惯性是训练出来的持久性，遇上一个会把同一想法反复写回去的推理循环，在足够长的运行里长出来的东西。时长是触发条件。Breunig 在演讲里给的警戒线是二十万 token，而如今论文里的运行预算已到十亿 token 量级，单次运行以天计。

## 十天里，四个团队砍了四刀

从 10 月 5 日到 10 月 14 日，四个团队各自撞上同一个问题，最后收敛到同一句话。Breunig 的转述是：把上下文扔掉，把工作留下。

但四种扔法砍的对象完全不同，这一点比共识更有信息量（这套分类是综合四篇材料得出的，不在任何一篇论文里）。四种解法的效果数字口径也互不相同（成功率、归一化分数、token 节省、最高相对提升），只能各自说明有效，不能横向排名。

| 砍掉什么 | 代表 | 隐含假设 |
|---|---|---|
| 实例 | Anthropic Memento | 惯性长在这个 agent 的对话里 |
| 路径 | Fork-and-Flush | 惯性长在这条探索路线上 |
| 状态的归属 | Stateless Language Agents | 惯性的根源是状态和对话绑在一起 |
| 团队记忆 | Scaling Discovery Requires Forgetting | 惯性长在共享的历史里 |

### 换人：Memento

Anthropic 的 Memento 不是一个独立发布的论文，它出现在 10 月 12 日那篇关于自我复制能力的博客附录里，建在开源 coding agent Pi 之上。流程是：跑满一个 generation timeout（一项实验里设为 1.5 小时）；实例写一份笔记，记下试过什么策略、遇到什么失败、性能如何；新建实例，继承代码库、环境和这份笔记，对话历史全部丢弃。

博客自己给的案例是 Qwen 的一个 agent 花了几小时排查包版本问题，而真正的 bug 出在实现了一个和评分器 API 不兼容的端点。这正是"固着于错误假设"的典型形态。

效果数字只有一组：Qwen3.5-9B 的推理部署任务，从第一代的 45% 成功率，到后续几代落在 61% 到 84% 之间。这组数字是产品自报，没有消融和第三方复现。博客的自我评价很克制，说它"不是一个普遍强韧的 harness"。

这个方案的身份和另外三个不同。对 Anthropic 来说它首先是个产品问题，只能按工程口径处理。同一个机制在论文里会被拆成变量做消融，在产品里只能是一段附录。

### 分叉再选优：Fork-and-Flush

微软研究院的做法把"换人"推到极致：既然单条轨迹会陷进解空间的局部区域，那就分叉成 K 条并行轨迹，每条继承完整的 workspace 副本，在同等算力预算下各跑固定时长，然后清空对话、选分数最高的那条继续，其余丢弃。论文给这种局部区域起了个名字，idea basin，想法盆地。

实验是 13 个长时程研究或工程任务，单次运行最长 107 小时，统一跑在 GitHub Copilot CLI 上。等算力条件下，min-max 归一化的平均分相对单次运行提升 66.0%，相对 best-of-N 提升 44.4%。

两个数字之外，论文里还有一句更关键：同一任务的独立运行会停在显著不同的水平，即使追加大量算力，差距依然存在。这句话把惯性从"某次运气不好"变成了"预算无法弥补的结构性损耗"。

### 状态外置：Stateless Language Agents

斯坦福主导的这篇（arXiv:2610.07625）换了问法。它不问"怎么让 agent 忘掉错误的想法"，而问"为什么 agent 需要有连续的记忆"。

方案是：agent 完全无状态，每次调用不带任何对话历史；研究状态（候选解和实测结果）由 harness 持有；每次调用时，harness 按角色重建一份全新的上下文。有一个 Advisor 读 harness 汇总的证据，向并行的 Worker 显式指派具体实验。

kernel 优化任务上，它达到最强 baseline 的最终性能，用的 token 少了 84% 以上。它给出的动机数据更能说明问题：论文引用的一项对比基线运行里，某个 GPU kernel 任务最后一次改进出现在 231M token 处，此后最后 1500 个 session 里有 98% 没有发起任何工具调用，token 却一直在烧。

这个观测比数字更锋利。它不是模型在做无用功，是模型连做无用功都不做了，只在咀嚼已有的上下文。

### 整队重置：Scaling Discovery Requires Forgetting

Berkeley 这篇的结论藏在一个否定句里：单 agent 跑更久、并行多 agent、并行且互相通信，这三种扩展方式最终都会平台化，因为 agent 被锚定在自己的历史尝试上，改动越来越小、越来越少。

解法是周期性遗忘，整个团队一起丢：清空所有 session 和候选历史，只保留 best-so-far 那个解，重启。相对并行 agent 最高提升 15%，相对单 agent 最高提升 39%（都是最高值，与上一节的平均值口径不同）。

论文摘要的收尾句是：一个 agent 被允许记住什么，和它被分配多少算力一样重要。

## 工程落点：把判断权从执行者手里拿走

这些实验来自 CodeGym、kernel 优化、研究任务等受控环境，四种解法也都还没有长期部署数据。下面这一节是按论文形态推演的工程落点，不是被生产验证过的方案。

四种解法摆在面前，共同点不在技术手段，在权力转移。**四个团队都在做同一件事：把"该不该继续"这个判断从执行者手里拿走，交给不受现场上下文污染的裁决方。多数情形下这个裁决方是代码，Stateless 里是一个被流程约束、不带现场包袱的模型角色。**

产品侧已经在做类似的事，只是没这么叫：

- Claude Code 有一个 `Stop` 钩子，能在模型想停的时候注入反馈让它继续；反向的保护是：默认连续 8 次阻止停止且期间没有工具调用，这个钩子会被自动覆盖
- 官方最佳实践建议在互不相关的任务之间 `/clear`，理由是聚焦的上下文答得更好、也更省钱
- Anthropic 自己那篇《Effective harnesses for long-running agents》更直接，说 compaction 不够用，方案是首窗口用一个独立的 initializer agent 生成进度文件、初始 git 提交和一份全部标着 `passes: false` 的特性清单，之后每个 session 只做一个特性，结束时干净提交

Hacker News 的评论区里有几条比论文更接近实际。一位使用者把代码、设计文档和执行计划当 artifact 存下来，喂给另一个 agent 验证，再用全新上下文续跑，他的观察是"设计文档和执行计划变成了编码过程的产出，而不是输入"。另一位对阈值给出反证：200k 到 300k 就重置是旧经验，新模型要到 700k 到 800k 才明显退化，他怀疑是长程 RLVR（可验证奖励强化学习）任务改善了这个问题。Breunig 自己的警戒线是 20 万 token，属于个人经验，不是实验结果。

判据落到代码上，大致是这样一个循环。这是伪代码，不是任何一篇论文的官方实现，重点在判据的形态而不是实现细节。

```Python
# 无进展检测的最小骨架
def should_flush(history, window=6, loop_repeat=3):
    recent = history[-window:]

    # 判据一：同一工具、同一参数、同一观察，重复出现
    sigs = [(s.tool, s.args, s.observation) for s in recent if s.is_tool_call]
    if sigs and sigs.count(sigs[-1]) >= loop_repeat:
        return "loop"

    # 判据二：窗口内没有任何可验证的状态变化
    if not any(s.changed_state for s in recent):
        return "stalled"

    return None

def run(session):
    while not done(session):
        step = session.step()
        reason = should_flush(session.history)
        if reason:
            note = session.write_note()          # 只写策略、失败、性能
            session = new_session(note, session.fs)   # 继承文件系统，丢弃对话
    return session.best
```

两个判据对应上面两种形态：判据一抓的是 DeLoop 定义的循环，判据二抓的是 Memento 描述的固着。合起来还有一个必要的好处：网络超时重试这类合法重试会被"观察相同"这个条件放过，只有同样的调用、同样的结果、同样的动作三者同时成立才算循环。

代价要分开算：

- 强制重置会丢掉还没写进笔记的隐性进展。Memento 用一份笔记兜底，等于承认这个损失存在
- 分叉选优的成本是算力乘以 K
- 状态外置要求 harness 自己维护研究状态，等于把一部分 agent 逻辑搬进代码，是最重的一种改法

## 尾声

回到 Breunig 那句"persistent models have a persistence problem"。这句话的分量在于它把习惯当成了缺陷。过去两年，行业一直在给模型加主动性：不要等指令、不要轻易放弃、遇到障碍换条路再试。现在这些品质在长程任务里变成了停不下来的原因。

同一批能力，在短任务里是优点，在长任务里是故障。拉开两者距离的主要变量是运行时长，而时长恰恰是今年才被拉长的变量。

他那篇短文里有一句自我修正，说他不认为惯性是推理模型不可逾越的上限，它是一个新的优化目标。这是原文里最乐观也最需要时间验证的一句。乐观的部分在于，只要是优化目标就有人去优化。需要验证的部分在于，把"什么时候该放弃"训练进模型，和把"不要放弃"训练进模型，方向正好相反，而后者按 Breunig 的主解释才是过去两年行业的主线（依据是实验室的公开叙事，不是奖励函数的公开材料）。
