# 判断也是接口：快决策模型接入 agent 的工程模式

> **导读**：agent 循环里的大部分判断，只需要在几个选项里挑一个，却被交给自回归模型逐字写出来，写完再解析回结构。2026 年下半年被做成通用 API 的一类非自回归决策模型，把输出空间收窄到几个选项，一次并行前向返回概率。它更快也更便宜，但决定集成效果的往往不是模型本身，而是判断怎么拆、闸门怎么设、回退怎么接。

一封客户邮件进来，agent 要判断它该进哪个队列、客户是否要求退款、有没有流失倾向。交给聊天模型，返回的是一段话：分析、理由、结论，末尾附一个 JSON。代码要做的第一件事不是决策，是解析。解析失败就重试，重试再带来一次延迟和一次费用。

真正被代码消费的，可能只有“退款”和“基础设施”这两个词。

单次调用看不出浪费。放进一个每秒十次的 agent 循环，一天是八十六万次调用，每一次都在为一个不需要读给人看的判断支付生成成本。

## 被砍掉的那一段叫 Decode

自回归模型的推理分两段。Prefill 读输入，把文字压进隐状态；Decode（逐字解码）则一个 token 一个 token 地往外吐，产物是给人读的语言。

两段的成本结构完全不同。Prefill 是一次大矩阵乘法，算力能吃满；Decode 每吐一个 token 都要对全部前缀做一次注意力计算，KV Cache（键值缓存）把算过的键值存下来避免重算，但每一步仍然只产出一个 token 的向量，算力利用率很低。序列越长，缓存越大，瓶颈从计算转到显存带宽。一段三百字的解释，就是三百次这样的前向。

人类语言的带宽很窄。工单里的隐含诉求、对话里的语气、图里的光影，写成文字都会有损耗。让模型把已经理解的东西翻译成文字，再让代码把文字解析回结构，中间多了两次有损转换。

快决策模型的做法是把这一步摘掉：保留 Prefill，跳过 Decode，直接在隐空间里对着预先定义的输出空间算概率。TypeSafe 的 Jev 就是这类实现，公布的数字是：端到端延迟 70 到 500 毫秒；同一份材料引用的 Artificial Analysis 延迟榜（含最高推理档）显示，前沿模型端到端从 3 秒到 329 秒。输入计价 0.042 美元每百万 token，输出不计费。

需要说明的是，Jev 的架构、权重和训练方法都没有公开。上面这套 Prefill/Decode 的切分，是官方口径加上外部复现者的推断，36氪的复现访谈里也提到这一点。

快的原因可以拆成三层：

1. 跳过逐字解码
2. 候选范围从十几万词表收窄到几个选项
3. 候选之间没有先后依赖，可以并行

三层叠在一起，省下的不只是时间，还有最贵的那部分算力。

输出空间被收窄之后，能问的文本问题也收敛成三种：

| 原语 | 回答什么 | 返回什么 |
|---|---|---|
| `choice` | 从固定选项里选一个 | 选中项 + 全选项概率 + confidence（置信度） |
| `score` | 落在有序等级的哪一档 | 分数 + 各档概率 + confidence |
| `noul` | 一个是非判断 | 0 到 1 的概率 |

`noul` 指的是伯努利式的是非判断，只返回一个概率：越接近 1 越像 yes。

`score` 返回的不是整数档位，而是期望值。在 0/1/2 三档上给出 (0, 0.57, 0.43) 的概率分布，分数就是 1.43：`0 × 0 + 1 × 0.57 + 2 × 0.43`。这个数可以直接排序、直接比阈值，但它不是“1.43 档”，是分布的重心；档位之间的刻度和真实数值对不齐，插值出来的具体数不可信。

`choice` 的 confidence 只看最高概率：`(p_max − 1/n) / (1 − 1/n)`。三个选项时，0.6 的最高概率换算成 0.4 的 confidence。这意味着 `(0.6, 0.3, 0.1)` 和 `(0.6, 0.2, 0.2)` 拿到同一个分数，尽管后者的不确定性明显更高。公式压缩了分布的形状，第二名、第三名离得多远，它不管。

## 判断的粒度决定集成难度

文档里给的判据是：一个好问题应该是“一个有知识的人看一秒就能答”的那种判断。“这封邮件是否要求退款”合格；“分析这封邮件并决定下一步”不合格，后者需要展开推理，是拆分的信号，不是提示词的信号。

举一个具体的拆法。一封投诉邮件，不拆的版本是“判断这封邮件该怎么处理”，拆开可以是四问：

1. 是否明确要求退款
2. 是否提到已经联系过客服
3. 语气是否构成威胁
4. 涉及金额是否超过某个阈值

前三个是语义判断，第四个是算术，应该在代码里从结构化字段读。

拆开之后，三件事同时发生：

1. 每个问题有独立的对错，可以单独标注、单独测
2. 问题之间没有依赖，可以并行，一次前向全部出结果
3. 权重回到代码里，业务调整改系数，不改提示词

组合评分是 Jev 这类模型最自然的用法：简历筛选拆成 Python 深度、团队领导力、系统设计、通识四个 `score`，资深工程师和工程经理用两套权重，前一套是 `0.40` 的 Python 深度加 `0.10` 的团队领导力，后一套把领导力提到 `0.40`。要调整偏好，改的是权重表里的数字，不是重写一段自然语言。尺度由代码持有，不随措辞漂移；换一版模型，业务逻辑也不会跟着重写。

拆解还有两个容易忽略的细节。

**选项顺序会影响答案。** TypeSafe 自己在已知缺陷页上承认了这一点。上线前把选项打乱重跑一遍，答案不跟着变，才算通过一致性检查。

**“以上都不是”不一定好用。** 选项上限是 255 个，加一个 `other` 看似安全，但官方文档的结论是它在许多场景下都不好用，理由没有展开。更稳的做法是配一个 `noul`，先判断“这段话有没有命中任何一个选项”，命中再读 `choice`。

还有一个约束：一次请求里的问题互相隔离，一个问题的答案不会进入另一个问题的上下文。这既是优点也是限制。需要“A 的结论决定 B 怎么问”的场合，只能拆成两次请求，或者把两种可能都问出来，在代码里选。投机性提问，本质上就是为了绕开这个限制。

## 一次 fan-out（扇出），把五次串行压成一次

Jev 的 API 支持一次请求带多个问题，并行评估。加问题几乎不改响应时间，只增加输入 token。

工单分流是一个典型场景。五个问题里有三个是“投机性”的：严重程度只对故障类有意义，退款意向和流失意向只对账单类有意义。与其先分类再追问，不如一次全问，代码决定用哪几个。

```python
# 一次请求带五个问题，多余的答案在代码里丢掉
state = {
    "subject": "重复扣款",
    "messages": [{"from": "customer", "text": "这个月被扣了两次，请退一笔。"}],
    "order": {"id": "A-104", "charges": [49, 49]},
}

questions = {
    "queue": {"type": "choice", "instructions": "该工单归哪个队列？",
              "criteria": {"infra": "服务中断、网络、数据库故障",
                           "billing": "退款、账单争议、扣款异常",
                           "support": "一般咨询"}},
    "refund": {"type": "noul", "instructions": "客户是否明确要求退款？"},
    "severity": {"type": "score", "instructions": "问题严重程度？",
                 "criteria": ["咨询", "功能受损但有绕行", "服务中断且无绕行"]},
    "churn": {"type": "noul", "instructions": "客户是否表达取消或流失意向？"},
    "legal": {"type": "noul", "instructions": "是否提及法律或监管投诉？"},
}

answers = decide(state, questions)
queue = answers["queue"]

if answers["legal"].noul > 0.6:
    route_to_legal(state)
elif queue.choice == "billing" and answers["refund"].noul > 0.7:
    route_to_billing(state, refund_likely=True)
elif queue.choice == "billing" and answers["churn"].noul > 0.7:
    route_to_billing(state, retention=True)
elif queue.choice == "infra" and answers["severity"].score > 1.5:
    escalate_to_oncall(state)
```

这段代码里，`severity` 只在 `infra` 分支被读，`refund` 和 `churn` 只在 `billing` 分支被读。它们仍然花了 token。五个问题串行要五次调用，按“先分类再追问”的两次调用算，一次并行省下一次往返；真正多出来的是三个本来不会问的信号，它们的成本只是 token，不是往返。

把分支留在代码里还有一层收益：可观测。每次调用的 state 摘要、问题版本、概率分布、走的分支都能落进日志，自动处置率、人工改写率、置信度分布的漂移可以进同一张看板。自由生成的文本没有稳定字段，做同样的聚合，成本和误差都高得多。

往返次数在 agent 里是复利计算的。把五个问题逐个串行问，每次约 1.5 秒，光延迟就 7.5 秒；每次还有失败概率，单次成功率 99%，五次串起来只剩 95%。一次并行前向把这个结构压成一次，失败面也跟着收窄。

上下文有两个上限：单请求 64k，单问题 32k。带上专门的请求头可以开到 262k，但厂商明说长上下文更慢、更不准，只对确实需要的请求开。这和 fan-out 是同一个约束的两面：并行省的是往返，不省 token，塞得越多，账越贵。

## 闸门能不能用，先看概率是不是真的

Jev 最容易被误读的一句话是“不会幻觉”。它成立的部分是类型安全：输出空间在请求时就定死，模型不可能返回 schema 之外的值，这一点是数学保证，不是实测结果。判断对不对是另一件事，两件事经常被读成一件。

概率可不可信，要看校准。ECE（Expected Calibration Error，期望校准误差）衡量的是：所有报了 0.8 的预测里，实际有多少比例成立。

第三方评测机构 TrueStandard 用 108 条声明做过一次对照，六个领域、四档难度，三个模型的 ECE 分别是 0.066、0.061、0.067（Jev 这一项是 1.13 的数据）。差距不到一个百分点，在 108 个样本上基本分不开。真正拉开差距的是最难那一档：0.917 对 0.833 和 0.806。

它赢在难题上的判断质量，不在概率的校准质量。

更细的一层来自 TrueStandard 对相邻两个小版本的复核。新版本把 Brier 分数（概率预测的均方误差）从 0.033 降到 0.026 到 0.028，看起来更准；同一批题目的 ECE 却从 0.066 升到 0.078 到 0.088，看起来更不准。

两件事同时发生，因为新版在一个错例上给出的置信度从 0.76 降到 0.57，Brier 因此变好，整体分布偏移又让 ECE 变差。不过对同一批样本重采样后，Brier 的改善幅度小到可能是偶然，ECE 的上升则更稳定。

> 更准和更校准不是同一个方向。校准指标适合做诊断，不适合单独当验收标准。

这也是 2024 年一篇讨论后验概率评估的论文（Ferrer 与 Ramos，arXiv:2408.02841）的核心主张：应该用 proper scoring rule（恰当评分规则）评估概率质量，ECE 只反映其中一个侧面，会忽略判别能力。

工程上的结论很直接：文档里的阈值只能当起点，不能照抄。用自己的标注集跑一遍，同时看 Brier 和覆盖率，才能定出适合本业务的数。

## 三档闸门与一条回退链

文档给出的示例阈值从 0.5 到 0.9 不等，取决于动作的代价。只读操作（查余额）在置信度 0.5 以上可以执行；破坏性操作（转账）要 0.9 以上，否则先确认；低于地板值的一律不猜。

落到代码里是三档：

1. 高置信：直接执行，不打扰人
2. 中等置信：确认、复核、补一次检索，或者交给慢模型
3. 低置信：不行动，转人工

`noul` 没有独立的 confidence，概率本身就是信号。要和其他原语统一尺度，用 `|2p − 1|`，0.5 映射到 0，0 和 1 映射到 1。起始阈值 0.7 和 0.3 是文档给的默认值，实际落点仍要自己标。

```python
# 两个判断分别设闸门：退款不确定就转人工，队列足够确定就自动分流
refund_conf = abs(2 * answers["refund"].noul - 1)
queue_conf = answers["queue"].confidence

if refund_conf <= 0.4:              # 概率落在 0.3 到 0.7 之间
    handoff_to_human(state)
elif queue_conf > 0.85:             # 路由的代价低于转账，0.85 足够
    auto_route(state, answers["queue"].choice)
else:
    # 中等置信：让慢模型带着快模型的判断做一次复核
    review_with_llm(state, draft=answers)
```

回退链的收益有公开基线可查。级联方案 FrugalGPT 在匹配最强单模型性能的前提下，最高把成本降了 98%，或者在同等成本下把准确率提升 4%（arXiv:2305.05176）。

RouteLLM 用偏好数据训练路由器，在某些场景下把成本压到一半以下而不牺牲质量（arXiv:2406.18665）；按查询难度分流的 Hybrid LLM，最多减少 40% 的大模型调用而不掉质量（arXiv:2404.14618）。三者省的东西并不相同，前两个算的是总成本，第三个算的是调用次数，不能横向叠加。

这三组数字都建立在一个前提上：系统能识别哪些请求是简单的，或者判断当前答案可不可靠。识别器判错，收益就反过来变成质量损失。

级联的经典结构有两块：一个打分函数判断当前答案可不可靠，一个路由器决定下一个问谁。打分函数可以是小模型的自评分、多次采样的一致性，也可以是独立验证器。FrugalGPT 的实验里，这套结构在多个数据集上都能贴近成本与质量的帕累托前沿，前提是打分函数本身就校准得不错。

校准不够可靠时，还有一个更笨但更稳的信号：重复采样的一致性。同一批问题跑多次，看标签翻不翻。翻，说明这条判断落在分布的边缘，不该自动处置。这个信号不依赖概率的绝对值，只依赖排序，对校准误差的容忍度更高。

回退链还要配预算，否则会变成无限升级。三个约束值得先定：

1. 单次请求的超时
2. 每条链路允许的回退次数
3. 一次用户操作的总成本上限

回退到慢模型时还得保证幂等，避免快模型已经执行了动作，慢模型又执行一遍。

顺序也有讲究：中等置信先换模型，低置信直接换人。人工往往是最后一道能处理新情况的层，也是最贵的一层，不该被当成默认兜底。

## 阈值是测出来的，不是拍出来的

TypeSafe 的文档里有一组自洽性实验：8 个 `choice` 问题各跑 15 次，原始标签一致率 90.8%，几个对照的聊天模型在 87.5% 到 100% 之间。加上“最高概率低于 0.60 就判为不确定”的规则之后，一致率升到 99.2%，代价是 25.8% 的答案转人工，自动处置覆盖率 74.2%。

这组数字比单点准确率更有用，因为它同时给出了收益和代价。只看一致率会误以为模型很稳，加上覆盖率才知道稳是怎么换来的。区间上端那个 100% 来自一个关掉采样的对照模型，它在同一规则下一次都不弃答：稳定，但不提供“不确定”这个信号。

方法上这是选择性分类的老问题：给定风险上限，让分类器自己决定什么时候拒答。Geifman 和 El-Yaniv 在 2017 年给出了构造方法，ImageNet top-5 上可以在 99.9% 置信度下保证 2% 的错误率，代价是覆盖率降到六成左右（arXiv:1705.08500）。

快决策模型的闸门本质上是同一条 risk-coverage（覆盖率与风险）曲线，只是把选择依据换成了 confidence。

回归集的建法比规模重要。从线上日志分层抽样，每个分支、每个难度档都要有样本，多语言业务再加语言维度；标注至少两人独立做，分歧的样本单独存一份，那批往往就落在阈值附近的灰色地带。评估时不要只看准确率，画一条 risk-coverage 曲线，看每提高一个百分点的自动处置率要付出多少错误率。

还有一条必须写进流程的检查：模型升级后的回归。TrueStandard 在同一批 108 条声明上对比相邻两个小版本，准确率两次持平、一次低 0.9 个百分点，错的还是那四道题。版本号动了不等于判断变了，回归集是目前最靠谱的提前发现手段。

上线顺序建议是先旁路再灰度。旁路阶段只记录判断、不执行动作，拿人审结果对比，攒够样本再开第一个低风险分支。

旁路阶段要对比的不是“模型对不对”，而是“如果当时自动执行，会错在哪”。把快模型的判断和人工最终处理结果对齐，分成四格：

| 模型 vs 人 | 人判对 | 人判错 |
|---|---|---|
| 模型与人一致 | 一致且正确：可直接自动化的样本 | 一致但错误：通常指向标注或流程本身有问题 |
| 模型与人分歧 | 分歧但人判对：快模型漏掉的场景 | 分歧但模型判对：阈值可以放松的地方 |

## 它不擅长的活，文档自己列了清单

TypeSafe 的已知缺陷页列了九类，这里挑对集成影响最大的几条：

| 失败模式 | 工程处理 |
|---|---|
| 算术、计数 | 留在代码里，只让模型做语义判断 |
| 日期时间比较 | 抽出字段，在代码里比 |
| 多跳指代 | 减少跳数，或直接把相关段落指给它 |
| 大段无关上下文 | 先过滤，只发这个问题需要的部分 |
| 对抗性内容 | 写死判定条件，上线前测边界样例 |
| 需要生成 | 换回生成模型 |

缺陷页之外还有一条限制：语言。Jev 的训练以英文为主，中文、日文、韩文可以输入，但准确率偏低。中文业务不能直接套英文场景的阈值，得用中文标注集重新标一遍。

表格里“对抗性内容”这一条，在 state 含用户可控文本时具体化为提示注入。输出空间有限，注入能造成的破坏比自由生成小，但依然可以诱导分类。上线前用一批注入样例测一遍，尤其是“忽略以上指令”这类直接写在 state 里的句子。

还有一条关于定位的说明：文档说它不生成文本、不写代码，也不自己选择下一步动作。它是 if 语句的模糊版，不是 agent。快慢分工里它承担判断，不承担规划。

## 账要按调用次数算，不是按单价算

单次成本就是输入 token 乘单价，输出不计费。400 token 的 state 加 60 token 的问题，一次大约 0.000019 美元。同样内容交给一个每百万输入 1 美元、输出 5 美元的聊天模型，400 入 40 出是 0.0006 美元，差三十倍上下。

压成本和压延迟要分开看：

- **降成本**：减小 state，只发相关问题需要的字段。这同时会提升准确率。
- **降延迟**：合并请求，一次带满问题。省的是往返，不是 token；问题带得越多，输入反而越贵。

按调用频次铺开更直观：

| 场景 | 日调用量 | 单次差额 | 一年差额 |
|---|---|---|---|
| 内部工具 | 1 万 | 约 0.0006 美元 | 约 2000 美元 |
| 在线客服 | 50 万 | 约 0.0006 美元 | 约 11 万美元 |
| 高频 agent 循环 | 86 万 | 约 0.0006 美元 | 约 19 万美元 |

但单价不是重点，次数才是。

TypeSafe 宣称的“最高便宜 445 倍”来自工作流评测，对手是前沿模型；而 TrueStandard 在 108 条声明的核查任务上测出的 8 到 27 倍，对手是两个廉价聊天模型，输出很短。两者都是端到端成本，差距主要来自模型档位和任务形态。写预算时用后者。

真正的大账是错误动作的代价乘错误率乘调用量。同样一天一万次调用，token 上省下的差额只有六美元；假设这一万次都是退款判断、错误都是误退款，一次误退款 50 美元、错误率 2%，期望损失是一万美元，差三个数量级。这也是闸门值得反复标定的原因。

## 落地清单

六条实践，按落地顺序：

1. 先画决策树，再写问题。每个分支节点对应一个问题，节点之间不重叠。
2. 一次请求带满可能需要的问题，投机性的也带上，代码里裁剪。
3. 阈值按动作风险分档，中间地带不猜，交给慢模型或人。
4. 每条失败用例进回归集，模型升级后重跑，比较错的是不是同一批。
5. 先旁路跑一段时间，再灰度开低风险分支，最后才碰有副作用的动作。
6. 把问题定义、阈值和 SDK 调用封在自己的一层里，请求里写死版本号而不是 alias，否则换版会静默改掉线上判断。

三个误区：

1. 把 confidence 当“答对的概率”。它衡量的是分布的形状，`(0.6, 0.3, 0.1)` 和 `(0.6, 0.2, 0.2)` 一个分。
2. 把“不会幻觉”当“不会错”。类型安全保证的是输出不越界，不保证判断正确。
3. 拿它做多步推理和算术。官方缺陷页写着它不会数数，误差随被数对象变大。

---

回到开头那次调用。判断拆开之后，集成的重心从“选哪个模型”移到了“哪几个判断值得被显式化”。

一个判断被写成 typed question（带类型的判断问题）的那一刻，它就有了输入、输出、概率、阈值和测试用例，也就第一次能被当作软件组件维护。模型会换代，阈值会漂移，至少当前这套接口把判断变成了可以被版本管理和回归测试的对象。

快决策模型改变的未必是成本曲线，而是判断在系统里的位置：从提示词里的一段期望，变成代码里的一个分支。
