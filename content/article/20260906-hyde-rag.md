# HyDE：让 LLM 替你写一道"假答案"，然后用它去找真答案

> 稠密检索在大多数场景下工作得很好。但有一类 query，它明明和知识库里的某段文档高度相关，检索器却死活匹配不上——问题不在编码器，而在查询和文档在嵌入空间里根本不住在同一个街区。HyDE 的解法是用 LLM 把查询翻译成一篇"假设文档"，让检索变成"文档匹配文档"。

---

从一次看起来不该失败的检索说起。

你的知识库里有这样一段话："Berlin 是德国首都，市区人口约 391 万，是欧盟人口最多的城市。"用户输入的查询是"德国首都有多少人"。语义上，这个问题和那段文档的相关性几乎一目了然。但稠密检索器可能匹配不上——不是因为编码器太差，而是因为"德国首都有多少人"这句话的向量，和"Berlin 是德国首都，市区人口约 391 万"的向量，在嵌入空间里的距离远得超出你的直觉。

HyDE（Hypothetical Document Embeddings，假设文档嵌入）的原论文正是从这类错配出发。2022 年 12 月，卡内基梅隆大学的 Luyu Gao、Jamie Callan 和滑铁卢大学的 Xueguang Ma、Jimmy Lin 在 ACL 2023 发表的论文 *Precise Zero-Shot Dense Retrieval without Relevance Labels* 中把问题的根源形式化了：零样本稠密检索要把查询和文档两个独立编码器学进同一个语义空间，而查询与文档之间的相似度从来没有被训练直接建模（arXiv:2212.10496）。

这篇论文的核心洞察不是"让 LLM 帮忙理解查询"，而是一个更底层的东西：**查询和文档的嵌入向量天然分布在空间的不同区域，直接比较它们，信号往往就是弱的。**

---

## 一、查询和文档为什么不住在同一个街区

理解这个问题有两层，一层比一层深。

**第一层是表面不匹配。** 查询通常很短，三五个词，语气是疑问或祈使。文档通常很长，几百个词，语气是陈述或说明。它们的词汇密度不同、句法结构不同、语域（register）也不同。把"The impact of climate change on crop yields"和一篇关于气候变化对农作物产量影响的研究摘要扔进同一个编码器，生成的向量在结构上就有差异——不是语义上的差异，是"形状"上的差异。

**第二层是结构性错配，这一层更关键。** 稠密检索器（比如 Contriever、BGE、OpenAI Embedding）的训练目标，无论是掩码语言建模还是对比学习，本质上都在学习"文本和文本之间的相似度"。训练数据里，正样本对通常是语义相近的文本片段——文档和文档、段落和段落。很少有训练目标会专门告诉你"这个问题的答案应该是那篇文档"。

换句话说，编码器学会的是"两段文本是否在说同一件事"，不是"这个问题的答案是哪段文本"。问题向量和答案向量在嵌入空间里占据不同区域，是训练目标的自然结果，不是哪个特定模型的缺陷。这意味着：**即使查询和文档语义高度相关，它们的向量也可能离得很远，因为编码器从来没学过"问题和答案应该靠近"这件事。**

HyDE 的思路就是从这里切入的——既然"问题 vs 答案"的信号天然弱，那就别比了，把问题变成答案，让比较双方都是答案。

---

## 二、颠倒顺序，发生了什么

标准稠密检索的流程是线性的：

```
查询 q → 编码器 enc_q → 查询向量 v_q
文档 d → 编码器 enc_d → 文档向量 v_d
检索 → 计算 ⟨v_q, v_d⟩ → 排序
```

HyDE 把这个流程拆成了两步，并且颠倒了"生成"和"编码"的顺序：

```
查询 q → LLM（带指令）→ 假设文档 d̂
假设文档 d̂ → 无监督编码器 f → 文档向量 v_d̂
检索 → 计算 ⟨v_d̂, v_d⟩ → 排序
```

变化在于：**查询向量不再是查询本身的编码，而是一段 LLM 生成的"假设答案"的编码。** 假设文档和真实文档走的是同一个编码器 f，检索变成了"文档匹配文档"——这正是编码器被训练去做的事情。

用公式表达。设 LLM 在指令 inst 下生成假设文档的概率分布为 g(q, inst)，从中采样 N 个假设文档 d̂₁ ... d̂_N。查询向量的估计为（原论文 Eq. 6–7）：

```
v̂_q = (1/N) · Σ_{k=1..N} f(d̂_k)
```

实践中也可以把原始查询本身也作为一个"假设"加入平均（Eq. 8）：

```
v̂_q = (1/(N+1)) · [Σ_{k=1..N} f(d̂_k) + f(q)]
```

然后对 v̂_q 和语料库所有文档向量做内积，取最相似者。

一个值得注意的细节：**检索过程不再显式计算查询和文档的相似度。** 整个检索被重构为两个子任务——一个 NLG 任务（LLM 生成假设文档）和一个 NLU 任务（编码器把假设文档映射到语义空间）。这个重构与"生成更多查询来对比"的查询扩展路线不同：HyDE 是直接把查询替换成一段假设文档。

## 三、假设文档可以是错的——这是设计，不是 bug

HyDE 的一个反直觉发现是：**生成的事实不正确的假设文档，依然可以有效检索到正确的真实文档。**

举个例子。查询是"柏林人口"，LLM 生成的假设文档写了"柏林是德国首都，人口约 400 万"——这个数字是错的，实际是 391 万。但检索器用这段假设文档的向量，成功找到了包含真实数字 391 万的那篇文档。

起作用的机制是编码器的稠密瓶颈（dense bottleneck），它充当了一个"有损压缩器"。假设文档里的"400 万"这个错误细节，在经过编码器压缩成固定维度的向量时，被更强势的正确语义信号淹没了——"柏林""德国首都""人口"这些核心概念主导了向量的方向。编码器的维度有限，它被迫做取舍，而取舍的结果就是：保留相关性模式，丢弃细节精确性。

原论文把第二步描述为"接地"（ground）：第一步，LLM 负责生成假设文档，捕捉"什么样的文档和查询相关"这个模式；第二步，编码器负责把假设文档压缩成向量，在这个过程中过滤掉幻觉细节，把向量锚定到真实语料的语义空间里。

两步之间有一个微妙的分工：LLM 提供"方向感"，编码器提供"着陆精度"。LLM 不需要知道真实答案是什么，它只需要想象一个"看起来像答案的东西"——形状对了就够了，事实对不对没那么重要。这个设计哲学和多数人对"LLM 生成内容用于检索"的直觉恰好相反：他们担心幻觉污染检索，HyDE 的设计恰恰利用了幻觉在压缩过程中的自我消解。

## 四、工程落地：怎么做，花多少钱

**采样策略。** 实践中通常采样 N=5 个假设文档（Haystack 的 HyDE 文档原文是"in practice, this is done five times"），temperature 0.7（原论文实验的默认设置），取嵌入平均。多次采样的目的是降低单次生成的方差——一个假设文档可能偏了，五个取平均之后方向更稳。

**Prompt 设计。** 原论文附录 A.1 给出了 8 组按任务定制的指令模板。核心结构统一为：

```
Please write a passage to answer the question
Question: [QUESTION]
Passage:
```

不同任务的差异主要在领域限定词。比如 SciFact 任务写成"Please write a scientific paper passage to support/refute the claim"。中文场景下，等效写法可以是"请写一段话回答以下问题"或根据领域加上"请以技术文档的风格"。

```python
from langchain_classic.chains import HypotheticalDocumentEmbedder, LLMChain
from langchain_core.prompts import PromptTemplate

prompt = PromptTemplate(
    input_variables=["question"],
    template="Please write a passage to answer the question\nQuestion: {question}\nPassage:"
)
llm_chain = LLMChain(llm=llm, prompt=prompt)
embeddings = HypotheticalDocumentEmbedder(
    llm_chain=llm_chain,
    base_embeddings=base_embeddings
)
```

注意 LangChain 1.x 中 HyDE 相关组件位于单独安装的 `langchain-classic` 包，上面的 `LLMChain` 已被官方标记为废弃，新项目建议用 LCEL 风格改写。

**延迟成本。** HyDE 给每次检索新增一次 LLM 调用。arXiv:2506.21568 在小模型（Gemma 1B/4B）的个人助理场景实测，HyDE 的响应时间比不带假设文档生成的普通 RAG 基线慢七成以上。

这个数字需要和召回率提升放在一起看。原论文的 TREC DL19 数据集上，HyDE 的 nDCG@10 达到 61.3，对比无监督 Contriever 的 44.5 和 BM25 的 50.6。在 BEIR 的低资源任务上（Contriever → HyDE）：

- SciFact：64.9 → 69.1
- Arguana：37.9 → 46.6
- DBPedia：29.2 → 36.8

**串联 BM25 和 reranker。** HyDE 不排斥混合检索。一个典型的两段式管线是：HyDE 生成假设文档向量做稠密召回，同时 BM25 做关键词召回，两者用 RRF 融合，再送进 cross-encoder reranker 精排。HyDE 负责把"语义相关但词汇不匹配"的文档捞回来，BM25 负责把"词汇精确匹配但语义距离远"的文档锚定住，reranker 负责最终排序精度。三者的增益来源是正交的。

一个架构性的硬性要求：**假设文档绝不泄漏进最终生成的上下文。** 假设文档只用于检索阶段的向量生成，最终喂给 LLM 生成答案的，必须是检索到的真实文档。如果假设文档混入生成上下文，LLM 生成的答案里就会出现"400 万"这种数字——因为假设文档里就是这么写的。这个隔离不是锦上添花，是底线。

## 五、什么时候该用，什么时候不该用

HyDE 的适用边界比大多数人以为的要窄。

**适合的场景：**

- 查询和文档之间存在明显的词汇鸿沟——用户用通俗语言提问，文档用专业术语回答。HyDE 的 LLM 在这时充当了"翻译"，把通俗查询翻译成专业语域的假设文档
- 查询很短但信息密度极高——两三个词的概念性查询，直接嵌入信号太弱，LLM 的展开能补全语义
- 知识库内容和查询之间的语义距离远、词汇重叠少——这是 HyDE 最自然的主场

**不适合的场景：**

- 精确标识符查询。比如"错误代码 E4392"，这类查询的关键词本身就是全部信息。HyDE 生成的假设文档只会引入无关概念、稀释精确关键词的嵌入信号。arXiv:2604.01733 在金融文本和表格基准上的实验也确认了这一点：对精确数值/实体查询，HyDE 增益有限甚至有害
- LLM 不熟悉的领域。这是 HyDE 最脆弱的假设——它要求 LLM 能"想象出正确答案的形状"。如果你的知识库是公司内部政策文档、未公开的产品规格、专业领域的私人数据，LLM 没见过这些内容，它会自信地编一个"看起来对"的假设文档，把检索引向完全错误的方向。arXiv:2506.21568 在个人数据检索上的实验显示，这类场景下 HyDE 的幻觉率不可忽略
- 延迟或成本敏感场景。每次查询多一次 LLM 调用，在语音 Agent 或亚秒级检索预算下可能不可接受

**一个实用的路由策略**：按查询特征分流。概念性、语义模糊的查询走 HyDE，精确标识符查询走标准检索，不确定的两者都跑 + reranker 融合。这个路由决策本身的价值，可能比"全量加 HyDE"更大。

## 六、最新进展：把成本从查询时挪走

HyDE 的工程化演进集中在同一个痛点上：**查询时的 LLM 调用延迟**。

**HyPE**（Hypothetical Prompt Embeddings，arXiv:2607.29402，2026-07）把假设内容的生成从查询时搬到了索引阶段。具体做法是：为每个 chunk 预计算 k 个假设问题（比如这段文档能回答哪些问题），嵌入这些假设问题而不是嵌入 chunk 文本本身，每个假设问题的向量都关联回原 chunk，检索时用户的问题直接和预计算的问题匹配，命中后返回对应的 chunk——把"问题-文档"检索变成了"问题-问题"匹配。效果是零查询时 LLM 调用、零额外延迟。论文报告在 6 个数据集上检索上下文精度最高提升 42 个百分点，claim recall 最高提升 45 个百分点。

**CoHyDE**（arXiv:2605.29271，2026-05）走了另一个方向：不消除查询时调用，而是让 LLM 重写器和稠密编码器迭代协同训练（InfoNCE 训练编码器 + DPO 对齐重写器），三轮迭代后在 ToolBench 的约 1 万工具子集上比最强单组件基线提升 2.5pp NDCG@5（标准查询）、6.3pp（模糊查询）。

**ReDE-RF**（arXiv:2410.21242，2024-10）的做法更激进：让 LLM 不生成完整文档，只输出单个 token 判断候选文档是否相关，平均延迟比 HyDE 低 3.8 倍。

还有一个趋势：两篇 2026 年的研究从两侧给出了互补的结论。arXiv:2606.28367 在强 reranker 存在时的系统评测发现，多数检索增强技术不再带来稳定的端到端收益，只有少数查询侧方法（含 HyDE 在内的 query expansion 是其中之一）仍有可靠增益——这说明 HyDE 的价值更多体现在"把正确文档拉进候选池"，而非"提升最终排序精度"；arXiv:2603.02153 的工业部署经验则印证了后半句：融合类技术带来的原始召回优势，经 rerank 和截断后被大量中和。

---

HyDE 做的事情本质上很简单：它不试图让编码器学会"问题和答案应该靠近"，而是用 LLM 把问题翻译成编码器已经学会处理的形式。这个思路的代价是每次查询多一次 LLM 调用，收益是在词汇鸿沟最深处架一座桥——桥的两端，分别是用户说的问题和文档里写的答案。
