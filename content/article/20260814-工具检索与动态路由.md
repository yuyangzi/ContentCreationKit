# 把工具找对，比让模型变聪明更重要：工具检索与动态路由的工程实现

> **导读**：在 Agent 工具调用的失败里，模型"找不到"比"不会用"更常见。LiveMCPBench 在 70 个 server、527 个工具的基准上得出结论：近一半的失败发生在工具检索环节（不是推理环节）。
>
> 本文从"为什么工具多了模型反而选不对"开始，逐层展开四种检索模式（向量检索、层级菜单、RAG 加重排序、Code Mode）的原理与权衡，再深入到按需发现的五种机制（Claude Code defer_loading、Anthropic Tool Search Tool、LangChain 中间件、EASYTOOL、MCP 2026-07-28 规范）。
>
> 最后讨论协议层怎么把"工具发现"从应用层问题变成原语。

---

## 一半的失败，发生在找工具这一步

2025 年 8 月，中科院软件所发布的 LiveMCPBench 是第一个大规模 MCP Agent 基准。它把 12 个 LLM 放在 70 个 server、527 个工具、95 个任务上跑，结论里有一条值得停下来看：

> 检索错误占全部失败近一半，工具组合能力与任务成功强相关。

在最常见的工具调用失败里，**模型不是不知道该怎么用工具，是根本没找到该用的那个工具**。这条结论把矛头从模型转到了系统，转到了工具在被塞进上下文之前的那段路。

过去一年关于"工具幻觉"的论文，主流观点大多把失败归到模型能力上。要么说模型推理不够强，要么说强化学习反而诱导短视，要么说工具说明书没写好。LiveMCPBench 给出的相反结论是：很多问题模型无能为力，因为工具压根没到它手里。

本文要回答的问题是：当工具库从几十涨到几百甚至几万，我们怎么把"对的那 3-10 个工具"找出来，送到模型面前。这件事在工业上叫**工具检索**（tool retrieval），跟它绑在一起的是**动态路由**（dynamic routing），决定哪些工具在什么时机被加载、哪个模型来执行、什么时候触发一次重新发现。

## 工具多了，为什么模型就选不对

第一个直觉反应是"工具描述不够清楚"。Berkeley Function Calling Leaderboard 上有个经常被引用的数据（第三方引述）：在日历调度任务上，工具从 4 个扩到 51 个，选择准确率从 43% 掉到 2%。这不是渐变，是悬崖。

根因要分三层看。

第一层是**注意力分配**。一份工具定义的平均长度在 400 到 500 个 token，50 个工具就是两万到两万五千 token。模型要在这堆说明书里找到对的工具，还要记住用户问题的上下文，注意力被摊薄几乎不可避免。

EclipseSource 在 2026 年 1 月那篇《MCP and Context Overload》里用了一个很准的比喻：一个组装衣柜的手艺人，理想情况下手边只有说明书和恰好需要的工具；当身边堆满无关的电钻、锯子、焊接设备时，他反而找不到该用哪一把。

第二层是**说明书质量**。工具调用失败里，相当一部分出在参数上，而不是工具选错。自由文本字段能写的地方偏偏不设枚举，该约束的参数类型没有约束，模型只能靠猜。schema 设计是工具检索质量的隐藏变量，它在"找"之前就决定了"找不找得到"。

第三层是**命名冲突**。同一注册表里 `get_user`、`fetch_user`、`retrieve_user_profile` 并存，模型的注意力要花在区分近义词上，影子调用（shadow invocation，名字相近的工具被模糊匹配路由错）的温床就是这么来的。命名冲突只是表面，更深的问题是语义等价但接口不同的工具被同时暴露。

把这三层放在一起看，**20% 到 40% 的工具调用失败，相当一部分发生在"工具被送进上下文之前"**（这是工业综合估算，与 LiveMCPBench 的"检索错误占近一半"口径不同但方向一致）。换句话说，不是模型推理能力的问题，是系统在极端不友好的条件下工作。

这是后面所有方案的论证起点：模型能力的天花板短期内很难大幅突破，但"送进上下文的工具"这件事我们能改。

## 四种检索模式：原理、算法与代价

工具检索不是一个被广泛讨论的子领域，但工业上已经形成四种相对成熟的模式。理解它们的原理和代价，是选型的第一步。

### 向量检索：把工具描述嵌入，再做最近邻

最常见的做法是**把工具描述嵌入成稠密向量**，用户查询也嵌入成向量，做余弦相似度最近邻。

ScaleMCP 论文（arXiv:2505.06416）给出的加权嵌入公式 TDWA（Tool Document Weighted Average）是目前最明确的方案：

```
z = Σᵢ wᵢ·Embed(cᵢ) / ‖Σᵢ wᵢ·Embed(cᵢ)‖₂    （Σwᵢ = 1）
```

cᵢ 是工具文档组件：工具名、描述、参数 schema、S 个合成问题。论文测了两组权重，**合成问题（SQ）的权重最高（40% 到 50%），参数 schema 的权重可以为零**。原因在于：用户查询是自然语言，与"合成问题"的语义空间最接近，而参数 schema 是结构化文本，权重过高反而干扰匹配。

嵌入模型选型上，ScaleMCP 对比了 OpenAI text-embedding-3-large/small/ada-002、Amazon titan、Vertex text-embedding-005，结果差异不大。

在 gnosis-mcp 基准里，23M 参数的 embedder 与 335M 参数的模型在开发文档语料上 nDCG@10 完全相同（0.8702），小模型索引还快 13 到 32 倍。**embedder 大小不是工具检索的瓶颈**，但合成问题的质量是。

代价是延迟。向量检索在千级工具下的延迟是 80 到 100 毫秒，跨语言场景更慢。最关键的硬限制是 API 单请求工具数有上限（OpenAI 128 个，Anthropic 无硬性数量限制但 deferred 工具上限 10,000 个/请求，Gemini 官方文档为 128 个），这是后面"按需发现"机制的工程动因。

一个常见的实现是 Anthropic cookbook 里的语义检索片段：

```Python
def search_tools(query: str, top_k: int = 5) -> list[dict]:
    # 查询嵌入（SentenceTransformer 返回归一化向量，点积=余弦）
    query_embedding = embedding_model.encode(query, convert_to_numpy=True)
    # 批量点积计算相似度
    similarities = np.dot(tool_embeddings, query_embedding)
    # 取 top-k
    top_indices = np.argsort(similarities)[-top_k:][::-1]
    return [{"tool": TOOL_LIBRARY[i], "score": float(similarities[i])}
            for i in top_indices]
```

向量检索不是银弹。ScaleMCP 的数据指出，**dense retrieval（即向量检索）在工具检索上 MAP 卡在 0.50 附近**：单向量无法同时捕捉多个工具的意图，多步工作流里的"先调 A，再调 B"场景是它的天花板。

### 层级菜单（hierarchical menu）：用一次额外往返换 token

把工具组织成树：顶层只暴露分类名（billing、identity、scheduling 等等），agent 先选分类，再加载该分支的工具。Zapier 是最大规模案例，MCP 采用动态发现模式，暴露 14 个静态元工具（discover/enable/execute 系列），30,000 多个 action 可搜索但不预加载。

ToolMenuBench（arXiv:2606.15508）给出一组数据：工具注册表分 25/100/250 三档规模，全暴露时 token 56,062、成功率 32.1%；用 CMTF（Causal Minimal Tool Filter，因果最小工具过滤）后 token 1,125、成功率 85.7%。**token 下降 98%，成功率提升 53 个百分点**。

代价是多一轮 LLM 往返。层级菜单的延迟陷阱是"深嵌套目录中，找到工具的总延迟可以媲美使用工具的延迟"（datarekha 博客）。另一个常见误区是把"语义相关"等同于"因果必要"：日历任务里 search、create、update、delete 事件工具都相关，但当前状态只允许一个正确动作，纯语义分类的层级菜单会过早暴露工具。

层级菜单的适用边界是 1K 到 30K 工具、目录相对稳定、分类可以人工维护的场景。

### RAG 加重排序：双阶段，先召回再精排

向量检索的 topK 召回后，再加一个 cross-encoder 精排，是 RAG 时代的标准范式。BGE 官方的推荐是"bge embedding 检索 top-100，bge-reranker 重排得到 top-3"。

收益有多大？ScaleMCP 论文测了三种 reranker：Cohere Rerank v3 把 NDCG 从 0.634 提到 0.642（+1.3%，相对纯向量检索基线），LLM reranker（Claude 3.7）提到 0.672（+6%）。

enquire-mcp 基准里 BGE-reranker-base 相对混合 RRF 提升 24.7 个 MRR 点、15.5 个 NDCG@10 点，但端到端延迟从约 400 毫秒升至约 1,030 毫秒（Apple Silicon 实测）。

**但有一个常被忽略的反例**。gnosis-mcp 双实验证明：MS-MARCO 训练的 reranker 在技术文档语料上，nDCG 从 0.84 掉到 0.57，延迟从 7 毫秒涨到约 2,920 毫秒。原因是 cross-encoder 的训练分布与工具描述分布根本性错配。**在工具检索场景，reranker 必须与工具描述分布匹配，否则宁可不加**。

候选池大小也影响结果。SemEval-2026 Task 8（MTRAGEval 多轮 RAG 任务）参赛系统 Caraman 的消融实验扫描了 k∈{30, 50, 100, 250, 500}，发现 3/4 的模型在 k=30 就达峰，BGE-v2-m3 这类强模型能用到 k=50，但 k=500 全部退化。**更大的候选池不是免费的午餐，是噪声注入**。

### Code Mode：让模型写代码，不是写工具调用

Cloudflare 提出的方案在思路上换了轨道：把 MCP 工具转成 TypeScript API，让 LLM 写代码调用，而不是直接工具调用。核心理据是：LLM 训练数据里有海量真实 TypeScript，但只有少量人造 tool-calling 示例。"让莎士比亚学一个月普通话再写剧本，不是他的最佳作品。"

2026 年 2 月发布的 Code Mode MCP server 把整个 Cloudflare API（2,500 多个端点）压缩为两个工具：

```json
[
  {"name": "search", "description": "Search the Cloudflare OpenAPI spec.",
   "inputSchema": {"properties": {"code": {"type": "string"}}, "required": ["code"]}},
  {"name": "execute", "description": "Execute JavaScript code against the Cloudflare API.",
   "inputSchema": {"properties": {"code": {"type": "string"}}, "required": ["code"]}}
]
```

Cloudflare 公开的 tiktoken 测量数据（200K 上下文窗口）：传统 MCP 完整 schema 1,170,523 tokens，Code Mode ~1,100 tokens，**削减 99.9%**。

GitLab MCP server（34 个工具）从 15,000 tokens 降到 ~1,100 tokens，削减约 93%。压缩率取决于 API 表面大小，99.9% 是个端点很多的极值。

但 Code Mode 不只是 token 优化，还有两个收益：

1. **跳过中间结果回传**。传统方式每个工具调用的输出必须回到 LLM 神经网络再复制到下一个调用输入，代码模式下中间结果只在沙箱内传递，模型只读回最终需要的数据。
2. **利用模型对代码的掌握**。LLM 对 TypeScript 的掌握远好于工具调用格式，沙箱执行可以串多个工具调用而不需要每一步都让模型决定。

沙箱是前提，不是可选项。代码在 Cloudflare 的 V8 isolate 中执行，无文件系统、无环境变量（防 prompt injection 泄露）、外部 fetch 默认禁用，出站请求通过显式 outbound fetch handler 控制。没有沙箱的 Code Mode 是任意代码执行漏洞。

Code Mode 的适用边界是超大 API 面（数千端点）、需要多步编排与数据变换的 agent 工作流。代价是依赖 LLM 的代码能力，对弱代码模型效果未知；调试和可观测性也还没有标准。

### 选型：四种模式怎么挑

datarekha 总结的边界经验值是：

- **少于 30 个工具**：直接塞进 prompt，不值得上检索
- **少于 1K 工具**：向量检索最划算
- **1K 到 10K**：层级菜单或 RAG 加重排序
- **10K+ 异构目录**：RAG 加重排序
- **链式多工具任务 + 大 API 面**：Code Mode

但这些都是综合 datarekha 等多方来源归纳的经验值，真实选型要看你愿意为多一轮往返付多少延迟、模型代码能力有多强、工具描述质量有多参差。

## 按需发现：把"找工具"从一次性决定改成持续过程

四种检索模式解决的是"怎么找"，按需发现解决的是"什么时候把找到的工具送进模型上下文"。这件事在 2025 年底到 2026 年上半年变得重要，因为 OpenAI、Google 的 API 对单请求的工具数设了硬上限（OpenAI 是 128 个，Gemini 官方文档为 128 个），Anthropic 虽无硬性数量限制，但 deferred 工具上限是 10,000 个/请求。

一个朴素的想法是"先少塞点，模型需要时再补"。难点在于补的时机、补的内容、缓存的粒度都需要协议和工程层面的支持。

### Claude Code defer_loading：10% 阈值触发的懒加载

Claude Code v2.1.7（2026-01-14）起默认开启 MCP tool search auto 模式。规则很简单：**当 MCP 工具描述超过上下文窗口的 10% 时，所有可延迟工具被标记 defer_loading，前缀里只留下一个 MCPSearch 工具（~500 tokens）**。

模型需要能力时用关键词调用搜索工具，命中 3 到 5 个工具（~3K tokens）展开为完整定义。

10% 阈值既是 token 数，也是占上下文窗口的百分比。200K 上下文的模型触发线是 20K tokens，1M 上下文的模型触发线是 100K tokens。

这里的工程经验值非常具体：**典型 50+ MCP 工具 72K tokens 的前缀，启用懒加载后降到约 8.7K tokens（搜索工具约 500 tokens，按需展开 3 到 5 个工具约 3K tokens），整体削减 85%，保住约 95% 的上下文窗口**。

但阈值是百分比这件事在 1M 上下文下出问题。Claude Code issue #39279（2026-03-26）记录的反馈是：Opus 4.6 默认 1M 上下文后，3 到 5 个 MCP server（30 到 50K tokens）不再触发延迟加载，因为 10% = 100K token 远高于此。

解法是手动设置 `ENABLE_TOOL_SEARCH=true` 或用更小的百分比阈值（如 `auto:2`）。**百分比阈值随上下文窗口缩放，用更小的百分比或直接强制启用更稳**。

配置项 `ENABLE_TOOL_SEARCH` 支持四种模式：`auto`（10% 阈值）、`auto:N`（自定义百分比，如 `auto:5`）、`true`（强制）、`false`（关闭，全部预载）。核心内置工具（Bash、Read、Edit）始终预载且不计入阈值；`alwaysLoad: true`（v2.1.121+）可豁免延迟。

代理/非官方端点会自动关闭 `ENABLE_TOOL_SEARCH`（多数代理不转发 `tool_reference` 块），这是另一个常见踩坑。

### Anthropic Tool Search Tool：服务端搜索 + 内联展开

Tool Search Tool 是 Anthropic Messages API 的服务端内置工具，2025 年 11 月随 `advanced-tool-use-2025-11-20` beta 发布，现已 GA。

调用格式是在 `tools` 数组里放一个 `tool_search_tool_regex_20251119` 或 `tool_search_tool_bm25_20251119`，其余工具标 `defer_loading: true`。**所有工具定义仍须随每个请求完整发送**，但只展开被搜索引用的部分。

Anthropic 公开的核心数据是：

| 模型 | 无 Tool Search | 有 Tool Search |
|---|---|---|
| Opus 4 | 49% | 74% |
| Opus 4.5 | 79.5% | 88.1% |

**工具没换，模型没换，只是把"加载哪些工具"从一次性决定改成了按需决定**。Opus 4.5 的工具选择准确率提升了 8.6 个百分点，且在 30 到 50 个工具后断崖式下降的曲线被显著拉平。

关键机制是**展开发生在对话内联位置而非前缀**：搜索返回的 tool_reference 块在 API 内部被展开为完整定义并插入到对话流中，prompt caching 断点保持不变。这是 Code Mode 之外另一个"不破坏 prompt cache"的工程细节。

计费规则明确：Tool search 不单独计费，搜索本身免费，只按"展开进上下文的工具定义"收输入 token 费。

限制也清楚：deferred 工具上限 10,000 个/请求；每次搜索返回 ≤5 个；regex 模式查询 ≤200 字符，BM25 查询 ≤500 字符。

### LangChain 中间件：框架层的动态过滤

LangChain 1.0 的 `create_agent` 中间件系统提供 `wrap_model_call` 钩子，可以在每次模型请求前动态过滤工具列表。核心 API 是 `request.override(tools=filtered_tools)`，只影响当次模型请求，不改注册表：

```Python
from langchain.agents import create_agent
from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse
from typing import Callable

@wrap_model_call
def select_tools(request: ModelRequest,
                 handler: Callable[[ModelRequest], ModelResponse]) -> ModelResponse:
    relevant_tools = select_relevant_tools(request.state, request.runtime)
    return handler(request.override(tools=relevant_tools))

agent = create_agent(
    model="gpt-5.5",
    tools=all_tools,          # 全部工具注册给执行器
    middleware=[select_tools], # 模型只看到过滤后的子集
)
```

LangChain 还提供了 `LLMToolSelectorMiddleware`，在 `wrap_model_call` 里跑一个快速 LLM 从注册表挑相关工具再绑定给主模型。**与 Anthropic Tool Search 同构的框架层实现**。

一个踩坑是：动态添加工具必须配 `wrap_tool_call` 处理器。中间件在 `wrap_model_call` 里加了 `create_agent()` 未注册的工具，执行器会抛 "Middleware added tools that the agent doesn't know how to execute" 错误。

**过滤 ≠ 注册**，工具必须预先注册到 `create_agent(tools=...)` 或 `middleware.tools`，否则模型调了也执行不了。

JS 版本历史上还有动态工具注册 bug（issue #1934，2026-02-02 报出，2026-03-31 修复），早期版本的 langchainjs 1.2.15/langgraph 1.1.2 在 `wrapModelCall` 中动态添加新工具会被运行时验证拒绝。该 bug 已修复，但说明框架层实现比 API 层更脆弱。

### EASYTOOL：离线精简，前置优化

EASYTOOL（arXiv:2401.06201）的思路完全不同：不动检索机制，直接把工具描述精简。论文给出的数据是 ToolBench 文档从 2,530 tokens 精简到 748 tokens（削减 70.43%），ChatGPT 工具调用成功率从 15% 提到 52.8%。

为什么精简反而提升？**因为工具描述里的噪声被去掉了**。原始文档存在三类问题：不一致（同一概念在两个工具里描述不同）、冗余（参数说明重复）、不完整（缺少使用场景）。EASYTOOL 用两阶段 LLM 流程：先把原始文档提炼为统一格式描述，再为每个函数生成 Scenario-Parameters 示例对。

EASYTOOL 与 Tool Search 不是竞争关系，是叠加关系：**EASYTOOL 是离线文档精简**（改工具描述本身），Tool Search 是**在线检索**（不改描述、只改加载时机）。一离线一在线，恰好叠加互补，这是工程上经常被忽略的对比点。

### 五种方案的对比

把这五种机制放在一起对比（EASYTOOL 严格说是离线前置优化，不算"持续过程"，放进来是为了展示完整方案谱系）：

| 机制 | 层级 | 触发条件 | 核心收益 |
|---|---|---|---|
| Claude Code defer_loading | 客户端 | 10% 上下文阈值 | 85% token 削减 |
| Anthropic Tool Search Tool | API | 显式调用搜索 | Opus 4.5: 79.5%→88.1% |
| LangChain 中间件 | 框架 | 每次请求前 | 灵活但需自实现 |
| EASYTOOL | 离线 | 一次性 | 70% token 削减 + 成功率 15%→52.8% |
| MCP 2026-07-28 协议 | 协议 | TTL + 通知 | 缓存原语（提示性）+ 跨客户端一致 |

前四种是工程实现层，第五种是协议层。协议层的演进改变了前四种的存在意义：以前每个客户端都要自建缓存逻辑，协议层把这件事规范化了。

---

## 协议层怎么回应：MCP 2026-07-28

MCP（Model Context Protocol）在 2024 年 11 月发布时，主要解决的是"怎么把工具传输给模型"。到 2026 年 7 月 28 日的稳定版发布，重心已经从"传输"移到了"发现"。

这条演进线值得看一下：

- 2024-11-05：初版，tools/resources/prompts 三原语
- 2025-03-26：OAuth 2.1、Streamable HTTP、工具注解
- 2025-06-18：结构化工具输出、elicitation、`MCP-Protocol-Version` 头必填
- 2025-11-25：OIDC Discovery、图标元数据、JSON Schema 2020-12 默认
- 2026-05-21：2026-07-28 RC 锁定，无状态核心
- **2026-07-28**：稳定版，无状态化、ttlMs/cacheScope、subscriptions/listen、Mcp-Method 头路由

2026-07-28 是 MCP 迄今最大一次修订。三个改动直接对应工具检索的需求。

### 无状态化：把会话拉平

删除了 `initialize` 握手与 `Mcp-Session-Id`，每个请求自带协议版本与能力声明（`_meta`），新增 `server/discover` RPC 做能力预检。**这意味着远程 MCP server 可以跑在普通 round-robin 负载均衡器后面**，按 `Mcp-Method` 头路由，工具检索的发现层不再依赖 session 状态。

代价是此前在握手阶段一次性完成的能力协商现在要在每个请求里重复，认证与协议版本检查的开销前移到请求路径上；长连接场景下，本由 session 状态维护的会话上下文需要客户端自己持久化。这是无状态化换取可水平扩展的直接成本。

### ttlMs 缓存：让客户端知道"什么时候重拉"

`tools/list` 响应里加了一个 `ttlMs` 字段，是"新鲜度提示"（类比 HTTP `Cache-Control: max-age`），告诉客户端工具列表多久内不需要重拉。缺省值是 0（每次都重拉），TypeScript SDK 缺省发射 `ttlMs: 0, cacheScope: 'private'`，是最保守的策略。

`cacheScope` 是 `"public"`（共享中间层可缓存）或 `"private"`（仅客户端）。**`ttlMs` 是提示而非保证**——服务端可能在 TTL 内改了数据，需要 `list_changed` 通知做即时失效。

一个工程细节是确定性工具顺序。规范要求 `tools/list` 返回确定性顺序，否则"map 迭代序"会让缓存命中率和 prompt cache 命中率悄悄下降。PacketNebula 在 2026-07-29 的分析里点名了这一点：**顺序不稳定是 2026-07-28 之后最容易踩的协议层坑**。

### subscriptions/listen：把推送变成 opt-in

2025-11-25 及之前是"非请求式推送"（服务端声明 `listChanged: true` 后随时推 `notifications/tools/list_changed`）。

2026-07-28 改为**客户端 opt-in 的 `subscriptions/listen` 长连接流**：客户端打开流、filter 声明 `toolsListChanged: true`，服务端确认后通知带 `subscriptionId` 标签。**服务端绝不发送未请求的通知类型**。

频率限制没有硬性上限，靠客户端 opt-in 与 TTL 缓存天然削峰。

这三个改动合起来构成了**工具发现的协议层原语**。

Cloudflare 官方博客的话很直接："can now run behind a plain round-robin load balancer, route traffic on an Mcp-Method header, and let clients cache tools/list responses for as long as the server's ttlMs permits"。

### 1M 上下文下阈值失效的协议层影响

MCP 2026-07-28 没有直接解决 Claude Code issue #39279 的问题（10% 阈值随上下文窗口缩放），但提供了**协议层的补救路径**：通过 `ttlMs` 和 `subscriptions/listen` 客户端可以做更细粒度的缓存，减少每次请求的工具列表传输成本；通过 `defer_loading` 标记的标准化，工具搜索可以在协议层而非应用层实现。

协议层的好处是**一次定义，多端实现**。Cloudflare Agents SDK 在 2026-07-28 当天就完成了支持，Sentry、Linear 在规范定稿前已经上线未炸。

## 还没解决的问题

按需发现能压住大部分工具检索失败，但有几类问题当前的方案还摸不到。

- **向量检索的多工具意图天花板**。ScaleMCP 的数据指出 dense retrieval（即上文向量检索）在工具检索上 MAP 卡在 0.50 附近。单向量无法同时捕捉多个工具的意图，是 embedding 范式的物理限制。集合级检索 HYSET（arXiv:2607.25718）把工具集作为评分单元是这条线的新方向，但还没有公开部署案例。

- **工具描述质量的隐藏变量**。EASYTOOL 证明工具文档可压缩 70-97% 且提升性能，但 ToolScope 发现公开基准中 79-96% 的工具描述质量偏低。**多数检索方案都假设工具描述质量足够，但生产环境的工具描述质量普遍不达标**。审计工具描述比选检索算法更优先。

- **检索感知训练（retrieval-aware training，RAT）的工程落地**。Gorilla 证明训练时附加检索文档可让模型学会"判断检索器"，但评估时非最优检索器会显著降性能（BM25 导致 52.27% 精度下降）。检索质量与模型训练必须协同，但当前没有标准协议。

- **Tool Search 的全量传输局限**。Tool Search 优化的是展开环节，但所有工具定义仍须随每个请求完整发送，工具规模大时带宽与输入 token 成本依然存在。

- **Code Mode 的可观测性**。代码在沙箱中执行，失败时 `{ code, result, logs }` 的日志质量决定 agent 能否自愈，尚无标准。Anthropic 独立探索了 Programmatic Tool Calling（Claude 写 Python 编排代码在沙箱执行），与 Code Mode 思路同构但执行模型不同。

- **量化敏感性**。本地模型上，同样的工具定义，量化前后行为可能差很多。这让用开源小模型做路由的方案在精度上打了折扣。

---

## 回到那个 50%

回到开篇 LiveMCPBench 的那条数据：一半的失败发生在工具检索环节。这条结论如果成立，意味着 Agent 工具调用的问题有相当一部分不在模型侧，而在系统侧。

过去一年，行业对"工具幻觉"的认知经历了三个阶段的转变：从"模型不会用工具"到"工具多了模型选不对"，再到"工具压根没到模型手里"。第三个阶段是 MCP 2026-07-28 把"工具发现"写进协议层的重要动因之一。

**把工具找对，比让模型变聪明更重要**——这句话不是否认模型能力的价值，而是承认在工具库规模增长远超模型注意力扩展速度的现实下，检索和路由的工程化是更可控的优化变量。

Anthropic 公开的数据是最直接的证据：Opus 4.5 在启用 Tool Search Tool 之后，工具选择准确率从 79.5% 提到 88.1%，而模型本身没换、工具集没换。换的只是"哪些工具在什么时机进上下文"。

这件事对工程团队的启示很具体：

- 先审工具注册表，再换模型
- 先做按需发现，再加 reranker
- 先实现协议层缓存，再优化 embedding 模型

这条优先级在 Jigar Joshi 的 47 工具注册表审计案例里得到验证：47 个工具、每次模型调用约 14KB 工具描述开销、错选率 22%。

至少在可预见的未来，工具检索很难变成"装上就忘了"的事。但协议层把它从应用代码搬到了规范里，框架层把它从手写过滤搬到了中间件，API 层把它从一次性决定搬到了按需加载。每一层都让这件事变得可控一点。

下次再有人问"为什么我的 Agent 调用工具总出错"，第一反应不应该是"换更强的模型"，而应该是"先看看工具是怎么被送进上下文的"。
