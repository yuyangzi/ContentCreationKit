# Cordis 范式深读：可逆效应与响应式余效应

> **导读**：Cordis 是 DeepSeek Harness（dsh）的底层微内核，论文《A Programming Paradigm for Spatiotemporal Composability》在 88 页里把"动态组合"拆成两个正交维度——时间可组合（组件卸载即回滚）和空间可组合（依赖声明式响应式）。本文按论文 + dsh 真实代码 + Koishi 四年生产验证，拆开这套范式在工程层究竟意味着什么。

---

## 2026-08-13：为什么需要重新发明插件系统

DeepSeek 在 2026-08-13 同时发布了两件事：开源 dsh agent harness（developer preview，GitHub 截至 2026-08-22：183k stars / 20k forks），以及配套的 88 页形式化论文《A Programming Paradigm for Spatiotemporal Composability》（作者：Yifan Shi、Wei Zhang、Tianyi Cui，所属：北京大学 + DeepSeek-AI，preprint）。dsh README 在 "Developer preview" 小节以全大写加粗写明 "THERE WILL BE COMPATIBILITY-BREAKING CHANGES"，论文 README 的 preprint 声明以 "This is a preprint under active revision" 开头——两件事都还没定型，但选择同一天公开。这不是巧合：v4 的 Cordis 与 dsh 是同步设计的产物，论文把 v4 的范式动机讲清楚。

dsh 的"Everything is a Plugin"不是营销口号，它的可行性依赖于 Cordis 的运行时机制——**可逆效应（revertible effects）+ 响应式余效应（reactive coeffects）+ 统一上下文类型（single context type）**。这个组合解决了普通插件系统的两个老问题：插件卸载时残留状态、与依赖图断裂后的级联崩盘。

理解 dsh 必须理解 Cordis。但理解 Cordis 不一定要从 dsh 进入——这套范式有 4 年生产历史，比 dsh 早得多。

## 普通插件系统难在哪：VSCode 与 Koishi 的对照

VSCode 是当下最成功的插件式应用之一，但论文指出了一个不常被讨论的事实：截至 2026-06-09，VSCode Marketplace 排名前 100 的扩展里，**87 个包含可执行代码，激活后无法在运行时单独卸载，禁用或删除后必须重启扩展宿主**。这意味着你"禁用"了一个扩展，但其余扩展的运行时也可能跟着滚一次——你以为是关一个开关，实际是关一扇门，门后所有东西都得重置。

普通插件系统的问题是双重的：

**第一是"卸载即残留"。** 一个模块可能注册了事件监听、开了定时器、持有连接、修改了共享配置。代码停掉以后，这些副作用有没有被完整回收，通常只能依赖作者记得写清理逻辑。Java 的 classloader 就面临类似问题——卸载不彻底，残留累积到一定程度，进程不重启就要崩。

**第二是"依赖关系隐式"。** A 模块依赖 B 模块的某个功能，但如果没有显式声明，系统不知道 B 必须在 A 之前加载，也不知道 B 退出时 A 该怎么办。手工写一串"先启 A 再启 B"的启动脚本能解决一部分问题，但每次依赖变化都要改一次脚本，长期演进必然失控。

Cordis 的解法是用两个运行时原语同时解决这两个问题：可逆效应管"卸载时干净"，响应式余效应管"依赖图正确"。两者被论文统一到一种上下文类型里，构成完整的动态组合编程范式。

Koishi 是这套范式最早的实战场所。它是开源跨平台 chatbot framework（2019 年立项），核心在 Cordis 上已连续运行 4 年。论文自己披露：**4000+ 社区贡献的插件**，覆盖 IM 适配器、数据库驱动、管理控制台和各类用户功能，四年里无数次插件更新，无需为更新重启进程。这不是个干净的对照实验，但是个可信的存在性证明——这套机制在工程上是站得住的。

## 时间可组合性：可逆效应

可逆效应（revertible effect）的核心定义来自论文摘要：**每个上下文变换都携带一个逆操作，运行时跟踪它**。

说人话：每次你修改了一个东西（注册了一个服务、监听了事件、开了个定时器），框架都要求你同时给一个"撤销函数"。卸载的时候，框架按注册逆序调用这些撤销函数，把系统恢复到加载前的状态。

Cordis 的入口 API 是 `ctx.effect()`：

```TypeScript
import type { Context } from '@deepseek-ai/cordis'

// 一个可逆效应：心跳定时器 + 清理函数
ctx.effect(() => {
  const timer = setInterval(() => {
    console.log('tick')
  }, 1000)

  // 返回的函数就是 disposer，运行时在卸载时按注册逆序调用
  return () => {
    clearInterval(timer)
    console.log('heartbeat cleaned up')
  }
})
```

`ctx.effect` 的语义是：**正向操作"开一个定时器"和反向操作"关这个定时器"绑定在一起，注册即绑定**。插件卸载时，运行时按注册逆序回滚所有 disposer。LIFO（后进先出）顺序很重要——后注册的先撤销，就像一摞盘子，最后放上去的先拿走，避免两个相互依赖的 effect 撤销顺序颠倒留下野指针。

```TypeScript
// 多个 effect 按注册逆序回滚
ctx.effect(() => {           // 注册 1
  const db = openDatabase()
  return () => db.close()     // 撤销 1（最后执行）
})

ctx.effect(() => {           // 注册 2
  const server = startServer()
  return () => server.stop()  // 撤销 2（先执行）
})
// 卸载顺序：server.stop() → db.close()
// 加载顺序：openDatabase() → startServer()
```

注意 `ctx.on()`、`ctx.set()`、`ctx.tools.register()` 这些内置 API **本身就是 effect**——你不用显式调 `ctx.effect`，注册动作已经附带自动生成的 disposer。这是 Cordis 的工程友好之处：常见操作不需要手写清理函数，只有像定时器、网络连接这种"系统外资源"才需要显式 `ctx.effect` 包一层。

论文对可逆效应做了一个关键的形式化保证：confluence（汇合性）。无论组件以什么顺序被加载或卸载，最终状态都是相同的。这听起来抽象，但工程意义明确——**你不用担心"先卸载 A 还是先卸载 B"的顺序选择，结果一致**。

不过可逆效应有自己的边界。论文明确指出：打开文件、分配内存、注册服务这些"获取动作"可以在系统边界内被记录并撤销；但**写到外部文件、发到网络请求、收款成功**这些"发送动作"已经越过边界，不能靠撤销函数消失——只能延迟提交或做补偿动作（退款、删除、反向事件）。Cordis 的保证是"如果你纳入上下文并提供撤销语义，它就进入恢复理论"；越过边界的输出，得靠业务层自己设计。

## 空间可组合性：响应式余效应

余效应（coeffect）和效应是对偶概念。效应描述"程序对世界做了什么"，余效应描述"程序从世界要求了什么"。经典类型论里有完整的余效应体系，论文把其中一个分支**响应式余效应**做成运行时机制，专门处理"组件依赖动态变化"的问题。

```TypeScript
import type { Context } from '@deepseek-ai/cordis'

// 一个插件声明它需要哪些服务
export const name = 'reminders'

// inject 是响应式余效应：声明依赖，运行时据此驱动激活/停用
export const inject = ['database', 'logger']

export function apply(ctx: Context) {
  const timer = setInterval(async () => {
    const due = await ctx.database.get('reminders', { channelId: 'general' })
    if (due.length) {
      ctx.logger.info(`You have ${due.length} reminders`)
    }
  }, 60_000)

  // 注册可逆效应
  ctx.effect(() => () => clearInterval(timer))
}
```

`inject` 的语义是：**这个插件需要的依赖**。依赖未到位时，插件不进入 `ACTIVE` 状态——它的 fiber 停在 `PENDING`，等待。依赖到位时，运行时自动激活 fiber；依赖撤离时，运行时通知 fiber，fiber 撤销自己的 effect 后再让依赖真正卸载。

这是论文所谓"响应式"的关键：**依赖关系不是一次性检查，是持续监听**。Cordis 内部维护一个依赖表，每次 `ctx.set` 或 `ctx.unset` 都会触发通知机制——遍历所有活跃 fiber，检查变化的 key 是否在它的 inject 声明里，并且解析到同一个隔离域；若受影响，重新计算目标视图，决定加载、卸载或保持。

工程上最直接的好处是消除"启动顺序"问题。传统插件系统的开发者要手工写启动脚本，"先启 A 再启 B"；Cordis 里 A 和 B 的关系通过 `inject` 声明自动推导。dsh 的 `ctx.tools`、`ctx.llm`、`ctx.sessions` 等服务就是被消费方 `inject` 的——消费方没声明就拿不到，声明了但服务未注册就等待，整个过程不需要中心化的 boot 编排。

副作用是**调试体验的改变**：一个插件"什么都没输出"，最常见的原因不是 bug，是它卡在 `PENDING` 等依赖。引入 Cordis 后，团队得把"检查 fiber 状态"纳入日常诊断，而不是只看异常堆栈。

## 一个 Context：能力句柄和依赖声明的合体

论文的关键一步是：把 effect context（对世界施加作用）和 coeffect context（向世界要求输入）**统一为单一上下文类型**。

```TypeScript
// 在 Cordis 里，每个插件拿到的都是同一个 ctx
export function apply(ctx: Context) {
  // 这一行既是注册（effect）
  ctx.tools.register({
    name: 'my-tool',
    schema: { /* ... */ },
    execute: async (args) => { /* ... */ },
  })

  // 这一行既是声明依赖（coeffect）
  // 也是注册可逆效应（effect）
  ctx.on('fs/read', async (req, next) => {
    if (req.path.startsWith('/secret')) return null
    return next()
  })
}
```

`ctx` 同时是能力句柄（你从这里调用服务）和依赖声明面（你在这里声明需要什么）。这是论文"范式（paradigm）"一词的字面含义——**这个类型同时承担两种相反的角色**，从此构建可动态组合的系统只需要一种类型。

这一点与 DI、FRP、AOP、Algebraic effects 这些传统体系形成对比，完整对照见下文「与传统体系对照」一节。

Cordis 与这些体系**不是替代关系而是并列关系**——它专攻"运行时动态组合"这一类问题，并把 effect 和 coeffect 从静态类型论提升为可执行的运行时机制。

论文的关键洞察是：**单独的"可热重载"和单独的"依赖解析"都有，单独的"运行时回滚"也有，但三者要在同一个 context type 上联合成立，并且互相不破坏——这件事之前没人形式化证明过**。论文给出了 10 条操作语义规则和 4 个元理论属性（preservation、global spatiotemporal composability、progress、confluence），证明这套机制能从一个组件的保证扩展到整个系统的保证。

## Fiber 状态机：插件生命周期的形式化

Cordis 把"一个插件实例"形式化为 fiber——**一个运行时句柄，承载生命周期状态、校验后的配置、所有注册的 effect**。每个 fiber 在自己的状态机里：

```
PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED
                            ↘ FAILED
```

| 状态 | 含义 |
|------|------|
| `PENDING` | 已声明，但某个必需的服务还没出现 |
| `LOADING` / `ACTIVE` | `apply` 函数正在跑 / 已完成 |
| `UNLOADING` / `DISPOSED` | disposer 正在跑 / 全部清理完 |
| `FAILED` | `apply` 或 config 校验抛错 |

Fiber 暴露的方法与生命周期对应：`fiber.dispose()` 等待所有清理（含 async disposer）完成后解析，并递归卸载所有子 fiber；`fiber.restart()` 销毁后立即用当前配置重新加载；`fiber.update()` 在配置变更时尝试原地更新，否则降级为完整 reload。

dsh 里这套机制跑在 Profiles × Bundles × Patch 的组合层之上——bundle 是声明式的，loader 负责配置协调（reconciliation）和热模块替换（HMR）。当你修改一个插件的配置，loader 判断能否在已注册的 fiber 上 `update`，不能就 `dispose` 后 `restart`；其他 fiber 不受影响，事件监听、定时器、订阅状态都活着。这是 HMR 在 dsh 这种 agent runtime 上能成立的原因（它不是 dev-only 工具，是 runtime 必备能力）。

工程上 fiber 状态机的最大用途是**故障定位**。一个插件不工作，先看 fiber 是不是 `PENDING`——多数"为什么不响应"问题不是代码 bug，是依赖图断裂。dsh 在 `dsh --profile web --dump-config` 里把整棵 fiber 树打印出来，正是为了这个诊断场景。

## 论文自承的限制：什么时候 Cordis 给不出保证

论文自己列出保证成立依赖的几条纪律，并强调**失败被显式排除在汇合性结论之外**。这些是范式的边界，不是缺陷：

1. **每个 effect 给的撤销函数必须真的能撤销**。Cordis 不会自动证明你写的清理逻辑正确——它只承诺"如果清理正确，组合和恢复就正确"。这条论文自己写明：运行时不会自动证明回调返回的清理函数真的正确，这仍然是组件作者的义务。

2. **跨组件共享状态应通过依赖键暴露**。如果你绕过 `ctx.set` 直接改全局变量，Cordis 不会知道，也救不了你。

3. **任意顺序卸载或交错执行时，效应/键操作必须独立**。如果你有两个 effect 修改同一个状态，先注册的那个的撤销函数可能"看到"后注册的那个还没撤销——这违反了独立性，需要你用隔离机制（realm）显式分开。

4. **依赖优先关系必须无环**。A 依赖 B、B 依赖 C、C 又依赖 A，Cordis 的调度会失败。

5. **失败被显式排除**。任何一个 effect 抛错或异步清理超时不返回，confluence 都不成立。Cordis 会进入 `FAILED` 状态但不会自动恢复——需要外部介入。

第 6 章还讨论了**系统边界**（可获取资源能撤销、已发送动作不能撤销，划分见前文）对 self-evolving agent 的影响：Agent 给自己发了请求、改了别人数据库，这类动作理论上都不能"卸载即撤销"。

论文末尾坦诚，验证数据只来自 Koishi 单一生态与 TypeScript 单一语言，尚未与其他架构做受控对比（论文限制节，意译）——这是单一生态、单一语言的存在性证明，不是 controlled performance comparison。预印本而不是 peer-reviewed。

## 与传统体系对照

Cordis 在编程语言理论的坐标里并不孤立：

- **Algebraic effects**（Haskell、Koka、Eff、Unison、Effekt、Frank）：经典 effect/coeffect 是**静态类型系统工具**——编译期检查 effect 类型、推断 effect 多态。Cordis 把这两个概念从静态提升到 runtime，最接近的研究语言是 Effekt（capability-passing style + HMR），但 Effekt 是门语言，Cordis 是 TypeScript 框架。
- **DI / IoC 容器**（Spring、Guice、Dagger、React Context）：注入时建立关系，提供者替换或撤回时**没有响应式重解析**——Cordis 用 reactive coeffects 填这个空白。
- **FRP**（ReactiveX、RxJS、solid-js signals）：在**值粒度**传播变化，框架组件、状态机本身不被传播；Cordis 在**组件粒度**操作，加异步生命周期语义，两者互补。
- **AOP**：pointcut + advice 处理横切；AOP 是 oblivious 的，可匹配任意 join point——这既是它的能力也是它的弱点，确定性差、难追溯。Cordis 把横切限制为组件显式声明的 coeffects，确定性、可追溯、随生命周期回滚。
- **OSGi / Eclipse plugin / VS Code extension**：传统企业级插件体系，**卸载通常需要重启宿主**，论文对此有直接批评。
- **Node `require` / Python `sys.modules`**：模块缓存层只有"加载"语义，没有"卸载"语义；hot reload 是 dev hack，不是 runtime guarantee。

Cordis 与上述体系不是替代关系。它专攻"运行时动态组合"这一类问题——当你的系统需要"组件随时出现又消失，且消失不留残留、依赖断裂不崩盘"时，Cordis 的范式给出工程答案。

## 为什么这件事在 agent 时代被重新提起

论文摘要里写得很明白："from plugin systems to self-evolving agent harnesses"。Cordis 不是为了 dsh 写的，dsh 也不是 Cordis 的第一个用户——Koishi 用了 4 年。但 DeepSeek 把它在 2026 年正式形式化并发表论文，动机来自 agent 时代对运行时动态组合的硬需求。

**agent 可能要自己修改自己的运行时**。未来 Agent 可能会根据任务，自己生成一个工具，自己把工具装进运行时，发现有问题以后，再自己把它替换掉。如果每次改一行代码都要把整个进程重启，那之前积累的上下文、缓存、连接全部可能崩掉。这是论文所谓"时间可组合性"的硬需求。

更进一步，agent 写出的工具可能互相依赖。一个 agent 自己写的 tool A 可能依赖它自己写的 tool B；如果 B 后来被替换了，A 必须知道这件事并相应调整，否则引入循环依赖，重新加载时整个 agent 进程很可能崩掉。这是论文所谓"空间可组合性"的硬需求。

Cordis 把这两件事变成可以推理、可以验证的运行时机制。dsh 的 `cordis_define` / `cordis_run` / `cordis_stop` / `cordis_undefine` 这套自指工具就是这套范式在生产代码里的体现——模型可以在 runtime 里定义一个 Cordis 插件，挂上去跑任务，跑完撤销。

但这种"自指"是有边界的。论文第六章讨论部分明确说：自进化 agent 是**未来的工作（future work），不是已展示的成果**。Koishi 4 年验证的是"插件系统在长时间运行下不会崩"，不是"agent 自己改自己不会崩"。这两个问题的难度不在一个量级。把 Cordis 看作 self-evolving agent 的**基础设施**，而不是**已实现的方案**，是更准确的理解。

## 最佳实践：什么时候看 Cordis，什么时候不看

1. **需要"运行时热替换"作为产品特性时借鉴 Cordis 思想**。Cordis 解决的不是"如何写一个插件"，是"如何让插件随时出现又消失而不留残留"。如果你的产品里插件只是"启动时加载、运行时固定"，你不需要 Cordis；如果你的产品里插件要支持运行时热更新、HMR、灰度发布，按需挂载，Cordis 的可逆效应 + fiber 状态机是值得参考的工程模式。

2. **实现"声明式依赖"时用 coeffect 而不是手工 boot 脚本**。传统插件系统的痛点之一是启动顺序——A 必须在 B 之后加载，B 又依赖 C……手工维护的脚本难以演进。把依赖关系作为数据声明（`inject`），让框架推导加载顺序，是更长期友好的选择。

3. **做"agent 修改自己"的实验时把 Cordis 当基础，但不要当作已验证的方案**。Cordis 提供可逆效应和响应式余效应这两个原语，但 self-evolving agent 的安全保证还需要在 Cordis 之上额外设计——比如撤销范围限定、修改审计、失败恢复。dsh 的 Code Mode 官方定位是 "containment, not a security boundary"，Creator 模式还允许模型实时挂载插件——两者都不是 sandbox。

4. **遇到"插件卸载不干净"的系统性问题时考虑 Cordis**。如果你在生产环境长期运行的系统里遇到"重启才能解决"的故障频次高，多半是某个插件的卸载链没写好。Cordis 的 ctx.effect + disposer 模式是这类问题的工程标准答案——**把清理逻辑从开发者记得写，变为框架强制要求**。

5. **不要把 Cordis 当 effect type system 用**。如果你需要静态分析 effect 类型（Haskell 风格），用 Koka 或 Eff；如果你需要运行时动态组合，用 Cordis。把 Cordis 当 effect type system 用会失望——它不阻止你写有害 effect，只在卸载时尽量撤销。

---

## 常见误区：理解 Cordis 时容易掉进的坑

1. **把"可逆效应"理解成"完全可逆"**。Cordis 只对系统边界内的获取动作保证撤销（边界的完整划分见前文），已发送动作不在保证范围内。把"可逆"理解为"万能撤销"会高估 Cordis 的能力边界。

2. **把"响应式余效应"理解成响应式编程（FRP）**。两者都叫"reactive"但语义不同：FRP 在**值粒度**传播变化，Cordis 在**组件粒度**传播依赖状态变化。Cordis 的 coeffect 不是"signal 是 reactive 的"，是"组件对依赖的声明是 reactive 的"——语义粒度完全不一样。

3. **把 ctx 理解成全局变量**。`ctx.tools`、`ctx.llm`、`ctx.sessions` 这些 key 是**服务契约**而不是全局命名空间——同一份业务代码在不同 ctx 下可以拿到不同的实现（开发环境本地存储、生产环境远程存储；A profile 一个模型 adapter、B profile 换另一个）。这正是 dsh 的 Profiles × Bundles × Patch 想利用的能力。如果你在 ctx 上挂业务状态而不是声明服务，就违背了设计意图。

4. **把"self-evolving agent"理解成已经能用**。论文摘要里写了这个词，但论文将 self-evolving agent 明确列为未来工作（future work），未给出已验证的实现。把"插件系统健壮"和"agent 自修改安全"这两件事混为一谈，会高估 dsh 的成熟度。

---

## 写在最后

Cordis 的论文值得读，不是因为它提出了新概念——effect 和 coeffect 在类型论里都有；而是因为它**把这两个静态概念落到运行时**，并用 10 条操作语义 + 4 个元理论属性证明这套机制能从单个组件扩展到整个系统。论文的可贵之处是把范式动机讲清楚（动态组合为什么难、为什么需要形式化、为什么过去没人这样做）；至于 Koishi 4 年 4000+ 插件的验证，存在但有局限。

**什么时候借鉴 Cordis 思想**：你的系统需要"组件随时出现又消失而不留残留"，需要"声明式依赖管理"，需要"运行时 HMR 作为产品特性"——这几个需求任意一个成立，Cordis 的可逆效应 + 响应式余效应模式都值得借鉴。

**什么时候不要看 Cordis**：你的系统不需要热替换、依赖关系稳定、启动一次跑到底——传统插件架构已经够用。把 Cordis 引入这类系统会增加学习成本和调试成本，不会带来对应收益。

**什么时候该关注**：当"agent 修改自己的 harness"从口号变成具体工程问题时，Cordis 提供的是目前最完整的运行时基础。但论文自己说这是 future work；把它当"已实现的 self-evolving agent 基础"会失望，把它当"值得严肃研究的范式原型"会更准确。

88 页论文里有一些推导骨架本文没展开——尤其是 confluence 性质的完整证明和 calculus of dynamic composition 的细节。这些留给读完本文还想再深入的人，按论文 README 的指引读 preprint PDF 即可。Cordis 仓库本身不大（核心库 + loader + 一个 HMR 插件），从代码反推论文也是可行路径。
