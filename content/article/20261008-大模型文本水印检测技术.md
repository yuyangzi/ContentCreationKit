# 大模型文本水印的底层逻辑：藏在采样里的信号

> **导读**：水印从论文走进了产品。它把"这段字是模型写的"变成一个可统计检测的信号，靠的不是给文字贴标签，而是在采样那一刻动手脚。绿名单与无失真两条路线、检测背后的假设检验、以及边界为什么比宣传里窄，是理解它的三个入口。

2026 年 8 月 2 日，欧盟《人工智能法案》第 50 条开始适用，要求生成式 AI 的提供者以机器可读的方式标记输出（存量系统过渡至 12 月 2 日）。到了 10 月初，OpenAI 宣布在欧盟的 ChatGPT 和 Codex 里加入文本水印，说是为了合规，采用会在此后数周逐步铺开。再往前，Google 已经把 SynthID-Text 放进了 Gemini 应用和网页端。

监管在推进，产品在跟进。水印能在多大程度上把"这段文本由哪个模型生成"钉死，取决于它的工作方式。

水印能做到的，比监管文件的口气要谨慎得多：文本水印不是在文字上做记号的。

---

## 一、水印不是贴标签，是给采样动手脚

图像水印可以改像素，音频水印可以改频谱，因为它们都是连续信号，动一点点人耳人眼察觉不到。文本不行。文本是一串离散的 token，改一个 token 就是改一个词，语义立刻就变。想在字面层藏一个不可见的比特，无处可藏；比特只能藏在"从哪个词里选"这件事上。

能利用的只有随机性。

大模型每生成一个 token，本质上是从整个词表按概率分布做一次采样。同一个 prompt，两次采样的结果通常不会完全一样，这个"不一样"就是随机性。水印的思路是：不改变语义，只让这次采样在下笔之前先看一眼密钥，然后悄悄偏向某一部分词。

> 水印不是写在文字上的记号，而是写进采样噪声里的记号。人读到的是语义，检测器读的是这次采样有没有按密钥"偏心"。

**主动水印**（watermarking）与**被动检测**（detection）常被混为一谈。主动水印要求能访问模型的解码过程，生成时就埋信号；被动检测只看最终文本，靠统计特征猜，比如 GPTZero 那一类。被动检测没有形式化保证，理论上可以模仿、可以对抗，主动水印才谈得上"证明"。这篇文章讲的是前者。

主动水印往下走，分出两条路线。

---

## 二、绿名单：把信号藏进词表的随机划分

最直观的一条是 Kirchenbauer 等人在 2023 年提出的绿名单方案（论文 *A Watermark for Large Language Models*，arXiv:2301.10226），也是很多商业系统的基础。

它的做法是这样：每生成一个 token，先拿前面已经生成的 token 算一个哈希，用这个哈希当随机种子，把整个词表随机分成两份，一份叫绿名单（green list），一份叫红名单（red list）。绿名单一般占词表的 γ 比例。然后，对绿名单里所有 token 的 logits 加上一个正的偏置 δ，再从改动后的分布里采样。

logits 是模型输出的未归一化分数，softmax 之后就是概率。加偏置的意思是，在语义允许的范围内，模型会更倾向从绿名单里选词。

伪代码如下：

```Python
# Kirchenbauer 水印：生成阶段
for t in range(T):
    logits = model(input_ids[:t])             # 原始 logits
    seed = hash(input_ids[t-1])               # 用前一个 token 做种子
    green = prng(seed).sample(vocab, γ * |V|) # 随机划分出绿名单
    logits[green] += δ                         # 只对绿名单加偏置
    input_ids[t] = sample(softmax(logits))     # 从改动后的分布采样
```

关键在于绿名单不是一张固定的表，而是随上下文滚动的。如果对每个位置都用同一张绿名单，攻击者统计几次就能把哪些词"偏绿"反推出来，然后手动避让。用前一个 token 的哈希当种子，等于让绿名单跟着文本走，检测端用同一把密钥就能重建出每一位置的绿名单；在密钥不泄露的前提下，攻击者很难重建。这类以哈希做种子的设计，实现里常按 seeding scheme 区分：用前一个 token 的记作 left hash，用当前 token 自身的记作 self hash，各有取舍。

生成之后是检测，而检测这一步的设计，决定了整套方案的性质。

---

## 三、检测：一次假设检验

水印的检测不是模式匹配，是一次统计假设检验。

检测端只拿到文本和密钥。它做的事和生成端对称：对文本里每个位置，用前一个 token 的哈希重建出那一位置的绿名单，然后数一数，整段文本里落在绿名单上的 token 有多少个，记作 |s|_G。

接下来是最关键的一步。**零假设 H₀** 是：这段文本和绿名单规则无关。要么是别的模型写的，要么是人写的，总之生成时没有向绿名单偏心。在这个假设下，每个位置的 token 落在绿名单上的概率就是 γ（绿名单占词表的比例），整段长度 T 的文本里命中数服从二项分布，期望是 γT，方差是 Tγ(1-γ)。

把观测到的命中数和期望之间的偏离做标准化，就得到 z-score：

```
z = (|s|_G − γT) / sqrt(T · γ · (1 − γ))
```

z 越大，说明命中数越离谱，越不像是"无关"的结果。取阈值 z > 4，对应单侧 p 值大约 3×10⁻⁵，也就是自然文本被误判成水印的概率约在百万分之三十这个量级。

检测的伪代码和生成一样短：

```Python
# 检测阶段：只需要文本和密钥
green_count = 0
for t in range(T):
    seed = hash(tokens[t-1])
    green = prng(seed).sample(vocab, γ * |V|)
    if tokens[t] in green:
        green_count += 1

z = (green_count - γ * T) / sqrt(T * γ * (1 - γ))
# z > 4 判为水印，单侧 p ≈ 3e-5
```

这套东西成立，依赖两个前提。这两个前提，加上下面要说的熵，大致划定了水印的边界。

第一个前提是密钥。在私有模式下，检测端必须用生成时的同一把密钥重建绿名单。密钥泄露，水印就形同虚设，任何人都能复制。这也是为什么 HuggingFace 的文档专门提醒，水印配置必须安全存储。

第二个前提是文本长度。看公式：如果水印真的在起作用，命中数会比期望高出与 T 成正比的一截，而分母里的波动只按 √T 增长，所以 z 大致随 √T 增大。文本越长，检测越稳；反过来，短文本的检测力会迅速塌下去。

公式里还藏着一个不那么直观的因素：熵。δ 是把分布往绿名单推的一点力，但这个力能不能推动，取决于原来的分布有多"平"。创意写作这类高熵文本，下一个词本来就有很多可能性，加一点偏置很容易改变选择；代码、事实性问答这类低熵文本，分布本来就尖，正确答案的概率已经很高，δ 能撬动的空间很小。所以同样是水印，写在小说里比写在代码里好检测。

绿名单方案的可检测性，来自它对分布的改动。

---

## 四、代价：它改了模型的分布

给绿名单加偏置，等于改了模型的输出分布。加了水印的模型，和没加的正主，严格来说是两个不同的生成器。这就是文献里说的有偏水印，与后面的无失真（distortion-free）相对。

soft watermark 的参数调得温和时，对高熵文本的质量影响很小，Kirchenbauer 的论文报告困惑度（perplexity，衡量文本"意外程度"的指标）只有小幅上升。但改分布总要付出偏移的代价，偏移多少、会不会在长尾场景里暴露，不容易完全保证。

另一条路线试图不改分布。

这条路线可以做到，而且更早。2022 年 Scott Aaronson 在一篇博文里提过一个思路，2023 年 Christ、Gunn、Zamir 把它形式化，写成 *Undetectable Watermarks for Language Models*（arXiv:2306.09194）。它的核心是用密钥驱动的伪随机数（PRF，pseudorandom function）来决定采样。

采样这一步可以这样理解。要从概率分布 p 里采样，有一个等价做法，叫 Gumbel-Max trick：给词表里每个 token 配一个独立的均匀随机数 u_i，然后取 `argmax_i ( log(u_i) / p_i )`。这样选出来的 token，其分布恰好就是 p。注意"恰好"两个字，这不是近似，是精确等价。

水印的妙处在这里：既然采样依赖一组随机数 u_i，那就别用真随机数，改用密钥驱动的伪随机数。生成端用密钥算出 u_i，检测端用同一把密钥也能算出 u_i。只要 u_i 在密钥下呈均匀分布，用 PRF 生成的 u_i 就等价于从 p 采样，输出分布不变。Christ 等人的原文用累积分布阈值取 token，和 Gumbel-Max 同属保分布采样，下面的伪代码用 Gumbel-Max 形式示意。

```Python
# 无失真水印（Gumbel-Max 形式示意）：用密钥驱动的噪声做 argmax
for t in range(T):
    p = softmax(model(input_ids[:t]))          # 原始分布，不动
    u = prf(secret_key, prefix, t)             # 密钥算出的随机数
    input_ids[t] = argmax_i(log(u[i]) / p[i])  # Gumbel-Max，分布不变
```

**这就是无失真（distortion-free）：即便观察者没有密钥，生成分布也和原始模型一致。**

检测不查分布是否偏移，而是检查文本和密钥生成的随机数是否"对得上"。Christ 等人的检测量大致是：对每个位置算一个 v_j，如果文本选的 token 和 PRF 指向的方向一致，v_j 就偏小，最后把 log(1/v_j) 累加起来。没有水印时，v_j 服从 U(0,1)，评分项 log(1/v_j) 的期望是 1，总分期望约等于 T；有水印时，总分显著高于 T。超过 T + λ√T 就判为水印。原文给出的假阳性上界是对文本可能的高熵起点位置数 L 取并集，至多 L·(4/5)^λ，λ 越大衰减越快。

这条路线和绿名单最大的区别，就是标题里那个词：undetectable。**没有密钥的攻击者，即便能任意查询模型、拿到再多输出，在计算上也无法区分水印模型和原始模型。**这是绿名单方案给不了的密码学保证。

两条路线摆在一起，性质几乎是对着来的：

| | 绿名单（有偏） | 无失真（Gumbel） |
|---|---|---|
| 分布 | 被改变 | 保持原样 |
| 无密钥可检测性 | 可能被逆向（需查询模型 API） | 计算上不可检测 |
| 检测需要 | 密钥 + 足够文本（长度、熵） | 密钥 + 足够文本（长度、熵） |
| 工程落地 | 开源生态成熟，已内置进 HF | 工程化难，落地少 |

> 注：表中对比的是绿名单与 Christ 式无失真两条路线；生产环境里部署最广的文本水印 SynthID-Text 未列其中（见第七章）。

无失真不等于没有代价。它的安全保证建立在密码学假设和足够的文本熵之上，工程实现比 logits 加个偏置复杂，所以到今天，生产环境里跑得更多的是绿名单系和 SynthID 这类工程化方案；Christ 这种纯密钥 PRF 的无失真方案，更多还停留在理论与框架层面。

但检测方拿到的，往往不是模型的原始输出。

## 五、抗改写：语义水印这条支线

绿名单和无失真的一个共同软肋是，它们都盯着 token 本身。一旦文本被改写、翻译，token 序列变了，信号会明显衰减。语义层面的改动，token 级信号扛不住。

一个方向是把水印从 token 级挪到语义级。代表性的方案有 SemStamp（arXiv:2310.03991）和 SIR（semantic invariant robust，arXiv:2310.06356）。SemStamp 把生成的句子映射到句向量空间，在嵌入空间里划分"水印区"和"非水印区"，用拒绝采样保证句子落进水印区；SIR 则是用语义 embedding 训练一个 watermark model，输出偏置 Δ，把它加到 logits 上。

这样做的直接好处是，改述一句话的用词，句向量往往还在附近，水印得以保留。代价是 SemStamp 这类句级方案把检测搬到了句级，词表级那种简洁的 z-score 不再适用，检测逻辑变重，生成时的拒绝采样也更容易拖慢速度，还会影响文本的自然度。SIR 系仍可用 z-score 检测，但生成要额外做语义 embedding 推理，也更重。语义水印更像是"用质量换鲁棒性"的一笔交易，离生产还有距离。

## 六、边界：当水印遇到对手

水印的数学形式很整齐，但把参数代进真实场景，情况会迅速变差。

1. **短文本**：z 随 √T 增长的直觉意味着，文本越短越检测不出。少于 100 个 token 的片段，多数方案的检测率都很低。社交媒体上一句评论、一次简短问答，基本在射程之外。
2. **低熵内容**：代码、模板化输出、事实性回答，本身分布就尖，δ 撬不动，检测更弱。
3. **改写与翻译**：He 等人的跨语言水印研究（*Can Watermarks Survive Translation?*，arXiv:2402.14007）显示，在固定 FPR=0.1 下（比前面的 z>4 宽松得多），X-SIR 在英文原文上的检测率为 0.994（Baichuan-7B，官方实现仓库实测），译成日语后降到 0.696。翻译几乎重排了整段 token 序列，把 token 级信号打散。
4. **水印窃取**：Jovanović 等人在 ICML 2024 的工作（*Watermark Stealing in Large Language Models*，arXiv:2402.19361）表明，攻击者只要通过 API 大量查询，就能近似逆向出绿名单规则，进而伪造水印（spoofing，让无水印文本被误判）或者更精准地擦除。这让"闭源 API 上的水印一定安全"这个想法站不住。
5. **开源模型的结构性悖论**：闭源水印的威力来自"只有厂商能控制解码"。开源模型把权重和解码过程都交出去了，用户可以自己改采样、自己重训、自己合并权重，植入的水印很容易被绕过。这也解释了为什么水印多出现在闭源产品的合规清单里。

把这些放在一起，结论是清楚的：

> 水印是存在性证据，不是排除性证据。检测到高分，能支撑"这段文本大概率由带密钥的模型生成"；在短文本或低熵内容上检测不到，几乎什么都证明不了。

这句话反过来解释了监管和技术之间的那条缝。EU AI Act 第 50 条要求"以机器可读方式标记"，中国《人工智能生成合成内容标识办法》也从 2025 年 9 月 1 日起施行、鼓励采用数字水印这类隐式标识。但水印能做到的，是让"愿意被识别的内容"可被识别，而不是让"所有 AI 生成内容"无所遁形。一个不配合、或者只是改写几句的对手，就足以让检测失效或大幅衰减。

## 七、水印还在往哪走

绿名单和无失真只是骨架，围绕它们长出了不少分支。下面三个方向最有代表性。

**多比特水印**：零比特水印只能回答"是不是"，多比特水印能往文本里编码一个字符串，比如用户 ID、会话 ID、模型版本，用来做溯源，而不只是鉴别。从 *Towards Codable Watermarking*（arXiv:2307.15992）起，这个方向一直在扩，代价是容量、鲁棒性和文本质量三者之间要反复权衡。

**密码学水印**：除了 Christ 的不可检测水印，还有公开可验证水印（arXiv:2307.16230，验证者不需要密钥也能验）、不可伪造水印等。它们想把水印从"统计信号"抬升到"密码学承诺"，但更强的保证通常换来更重的计算和更苛刻的前提。

**工程工具**：真要用，入口已经不高。HuggingFace transformers 内置了水印配置类和检测器，支持绿名单系和 SynthID（SynthID 检测器需自行训练）；研究侧的对比评估可以用清华团队主导的 MarkLLM（arXiv:2405.10051）；SynthID 也有官方开源参考实现，但明确标注非生产级。

## 八、如果动手做一个水印，从哪开始

下面这五条是实践里最容易踩坑的地方。

1. 先明确目标：要"检测是否 AI 生成"（零比特），还是"溯源到具体用户"（多比特）？两者的参数和评估指标完全不同，别混着做。
2. 选工具：产品集成用 HuggingFace 内置的水印配置，研究对比用 MarkLLM，想复现 SynthID 看官方参考实现。
3. 调参别只看检测率：δ 和 γ 调大，检测是强了，但困惑度也上去了。要画权衡曲线，找到质量还能接受的拐点，而不是把检测率推到顶。
4. 评估要对着真实攻击：至少跑一遍改写、翻译、截断、复制粘贴，再决定阈值。只看无攻击情况下的检测率，等于没评估。
5. 承认边界：短文本、低熵内容、开源模型场景下，要预期它失效。把水印当唯一防线，等于没防线。

---

水印并不能把"这段文本由哪个模型生成"完全钉死。

它能把一部分情况钉住，条件写得很清楚：

1. 文本够长
2. 熵够高
3. 密钥没泄露
4. 对手没改写
5. 解码端在生成方控制之下（闭源或服务端调用）

这五条同时成立的时候，一次假设检验确实能把 p 值压到极低。可现实里，这五条很难同时凑齐。

水印是一个诚实的技术，它的能力边界写在公式里，也写在每一次被绕过的实验里。监管想要的是一个全称判断，水印能给的是一个条件判断。这道缝短期内不会自动合上，因为改写和开源部署都握在对手手里。
