# DeepSeek DSec 拆解：Agentic RL 的训练环境优化

> **导读**：2026 年 9 月 19 日，DeepSeek 在 arXiv 挂出一篇 31 页、131 位作者的论文，梁文锋最后署名。它的学科分类是 cs.DC（分布式、并行与集群计算），不是 cs.LG 或 cs.AI。论文公开了 Agentic RL 训练脚下那层地基：一个单日要服务约 300 万个沙盒的平台。名字叫 DeepSeek Elastic Compute，简称 DSec。

一个反直觉的起点：这批沙箱大部分时间是闲着的。

按论文披露的生产画像（arXiv 2609.22978），约 **90% 的 Container 和 microVM，平均 CPU 使用量不超过申请资源的 5%**，绝大多数在等模型生成下一步动作。可它们申请的内存、改过的文件、装好的依赖、起好的服务，一件都不能收回去，因为下一次工具调用随时会回来接着用。

闲着的机器反而是难题。

传统大模型训练的负载画像很整齐：一批静态输入进去，一批输出出来，算力吃满，任务结束就释放。Agent 训练不是这样：模型要真正进入一个可执行环境，读代码库、调工具、跑命令、改文件，每一步都改变环境状态，而下一轮 rollout 又需要从干净状态重新开始。

论文把这些负载的特征列了七条，其中五条塑造了本文要讲的平台形态：

- **突发性**，单个任务最多要 3.2 万个沙箱，持续创建速率每秒超过 5000 个；
- **高密度**，CPU 使用稀疏，天然适合超卖，单节点因此能稳定跑到 3200 个 Container 或 800 个 microVM（论文称这是演示运行点，不是硬上限）；
- **有状态且长命**，Container 中位生命周期 17.4 分钟、microVM 15.5 分钟，但 p99 都会超过三个小时，内存和可写状态在 CPU 空闲后仍然钉着；
- **高度异构**，从 Online Judge 脚本到整仓库软件工程、安全攻防、computer-use、Android 开发，隔离强度要求各不相同；
- **环境高度分散**，每个任务可能带自己的仓库、依赖版本、服务和评测脚本。

这几条叠在一起，得出一个判断：GPU 不再是唯一的排队对象。算力可以买，模型可以训，但模型每次行动都要落进一个真实、干净、可隔离的环境里。环境供给能力，正在从配角变成决定 Agent 迭代速度的瓶颈。问题不在模型那侧，在模型脚下。

## 一套 SDK，四种沙箱

DSec 给训练框架看到的是一个 Python 库，`libdsec`。不管底层是哪种隔离方式，创建沙箱、执行命令、取回结果的写法都一样。论文里给的调用示例长这样：

```Python
client = DSecClient()
await client.open()

args = DSecContainerRunArgs(
    container_image="registry.../sphinx-9658:official",
    memory_limit_mb=4096,
    cpu_cores_limit=4,
    ttl_running_stop=300,          # 空闲 300 秒后自动停
    network_rules={
        "npm": False,              # 拒绝 NPM
        "pypi": True,              # 允许 PyPI
    },
    init_user="root",
)

sandbox = await client.run_container(args, timeout=120)
result = await sandbox.run_shell("echo hello world")
await sandbox.stop()
```

这段代码里能读出三件事。沙箱是按资源配额和生命周期申请的，不是启动一台机器。网络权限是按域名/镜像服务的白名单下发的，论文原例正是允许 PyPI、拒绝 NPM。沙箱内可以指定为 root，因为隔离不靠降权。

那隔离靠什么？靠后端分级。DSec 提供四种后端，隔离强度与资源开销逐级递增：

| 后端 | 实现 | 隔离开销 | 典型场景 |
|------|------|----------|----------|
| FnCall | 预创建容器内直接执行 | 最低 | OJ、代码编译、GPU kernel 评测 |
| Container | 改造版 dockerd + EROFS/OverlayFS | 较低 | 软件工程、通用工具调用 |
| MicroVM | Firecracker | 中等 | 安全敏感任务、租户隔离 |
| Full VM | QEMU，支持 virtio-gpu | 最高 | Android、computer-use、GUI 与图形渲染 |

这里有个容易被忽略的细节：Container 和 FnCall 并不是直接跑在物理机上，而是跑在 QEMU/libvirt 虚拟机里。宿主机多隔离一层内核和网络栈，作为不可信容器与裸机之间的缓冲。共享宿主内核始终是 Container 的短板，那层 VM 就是补救。

`libdsec` 也不假装四种后端是同一回事。四种后端的启动成本、隔离边界、文件系统语义、OS 能力都不同，SDK 提供的是统一的访问路径和相似的操作模型，具体选哪个后端仍然由调用方按任务决定。真正被统一的是调用姿势，不是语义。

一个训练任务一次要拉起几万个沙箱，每个沙箱都可能带一个不同的环境，环境从哪来、怎么在多台机器上快速铺开，成了下一个要解决的问题。

## 环境不该被打包，应该被叠加

传统做法是把一个任务需要的所有东西打成一个镜像。问题在于组合爆炸：如果有 m 个基础镜像和 N 个工作区，理论上要维护 m×N 个组合镜像。升级 m 个基础镜像里的一个，可能触发一大片镜像重建，复杂度是 O(m·N)。

DSec 把环境拆成三层，各自独立版本化：

1. **Base Image**：OS 级依赖，Ubuntu、Python 3.10、Java 8 这类，更新频率低；
2. **Workspace**：任务代码仓库和任务特定依赖，更新频率中；
3. **Toolkit**：频繁更新的工具链，比如 DeepSeek 自己的 Harness，更新频率高。

每一层都是一个只读的 EROFS（Enhanced Read-Only File System，增强型只读文件系统）镜像，沙箱启动时用 OverlayFS 按 base、workspace、toolkit 的顺序叠起来，最上面再挂一个可写层，运行时的写入不碰只读层。

分层之后，升级成本塌了一个数量级。升级 m 个 base image 只需要重建 m 个 base 层，workspace 和 toolkit 原地不动，复杂度从 O(m·N) 降到 O(m)；升级 k 个 toolkit 同理，从 O(k·N) 降到 O(k)。论文里提到，为了在容器创建时动态插入一层 EROFS 作为最上层（紧贴可写层）的 lower layer，以便覆盖下层文件，他们改造了开源的 dockerd（基于 Moby 项目），这一步只用了 **30 行 Go 代码**。

这套改动换来一个可组合的环境模型，比新增一整套镜像构建流水线划算得多。

## 镜像拉不动，那就别全拉

分层解决的是「有多少种环境」的问题，接下来是「怎么把它们送到机器上」。

先看镜像的分散程度。生产周数据里，container 后端服务了 11266 个基础镜像和 102171 个工作区，平台还提供 103 个工具包，其中 67.8% 的沙箱需要在 base image 之上再叠加 workspace 或 toolkit。更关键的是复用率极低：Container 镜像的中位复用次数只有 **3**，microVM 只有 **1**。

镜像多、复用少，如果沿用容器生态的常规做法——从 registry 拉取完整镜像再解压——分发的网络和磁盘压力会集中爆掉。论文测的对照结果是：8192 个容器同时启动，按需加载约 **35 分钟**完成，而 Docker 的 eager pulling（预先完整拉取）需要 **超过 60 分钟**，慢了 1.7 倍；累计磁盘写入同时少了约 57%。

DSec 的做法是把镜像数据留在共享存储上，谁真的读到哪一块，才去取哪一块。

镜像以 EROFS 格式存在 **3FS（Fire-Flyer File System）**上，这是 DeepSeek 自研的集群级分布式文件系统，训练侧已经在用。3FS 的 I/O 特性是「大顺序读写吞吐高、小随机 I/O 差」，这个不对称直接决定了三条设计原则：

1. 可写层放节点本地盘，避开 3FS 的小写惩罚；
2. 只读数据按需批量取，用足大 I/O 吞吐；
3. 元数据尽量预取到本地，路径查找不触发远程 I/O。

最后一条是关键。EROFS 的多设备模式可以把元数据和数据分开存放，DSec 把元数据下载到本地磁盘，文件数据留在 3FS。也就是说，打开一个路径不需要碰网络，只有真正读文件内容时才去 3FS。实际读到的比例低得惊人：以 Python 容器镜像为例，6.0GB 只读了 6.0%，各语言镜像整体区间在 4.2% 到 13.3% 之间。镜像里绝大部分内容，从创建到销毁基本没人碰。

读路径的示意大致是这样（非论文原始代码，仅示意逻辑）：

```Python
def read_file(path):
    inode = local_metadata.lookup(path)      # 元数据常驻本地，查路径不发起远程 I/O
    if inode not in local_cache:
        blob = fs3.fetch_batch(inode.extents)  # 数据块未命中，才向 3FS 批量取
        local_cache.put(inode, blob)
    return local_cache.get(inode)
```

microVM 这条路径略有不同。它的可写 ext4 磁盘走 **OverlayBD**，通过 **ublk**（userspace block device，用户态块设备）暴露，数据以 256 KiB 为单位获取，并且有二级本地文件系统缓存，即使页缓存被驱逐，也还能从本地缓存兜住，不必回 3FS 重取。

环境生成也用同一套设施。Agent 可以通过 `pack_diff` 对沙箱做增量磁盘快照，之后把它恢复成一个新沙箱。会话因此直接变成可复用的环境，不需要另建一条镜像构建流水线。这里有个安全细节：环境的构建者和运行时 Agent 用不同账户，打包前会清掉可写层里的构建残留，避免把参考答案带进镜像。

## 让闲着的沙箱挤满一台机器

镜像解决了「环境从哪来」，接下来的矛盾是「一台机器能装多少个」。这里的核心不是算力，是内存。

生产画像里约 90% 的沙箱 CPU 使用不足申请量的 5%，但内存和状态一直占着。超卖因此成立，却在内存上撞墙。DSec 用了两组互补的机制。

第一组针对的是「同一份数据被缓存两次」的问题。microVM 传统上通过 virtio-blk 读虚拟块设备，数据会在宿主机页缓存存一份、又会在每个 Guest 的页缓存存一份，同一份只读镜像被每个 VM 各缓存一遍。DSec 用 **virtio-pmem + DAX**（Direct Access，直接访问）让 Guest 跳过自己的页缓存，把文件访问直接映射到宿主机的物理内存，多个 VM 共享同一份宿主机映射。峰值宿主机内存因此下降 **40.2%**。代价是瞬态 CPU 从 26.5% 升到 41.4%，同步缺页变多了，所以这套只用在只读的基础镜像和工具包层上。

第二组针对的是「Guest 内的冷页还不回来」。virtio-balloon 的 free-page reporting 能让 Guest 把空闲页主动报告给宿主机回收，但它默认以 2 MiB（order-9）为单位报告，而 Guest 里空闲的页是散碎的，凑不出这个粒度。DSec 用 **DAMON**（Data Access MONitor，数据访问监控）周期性采样页访问位，识别超过年龄阈值的冷文件页并驱逐，散碎空闲页被 buddy allocator 合并成高阶块，才满足上报粒度。这一组让时间积分的内存消耗再降 **21.2%**，几乎不增加 CPU 开销。

两组机制的职责不重叠：virtio-pmem 消除 Guest 与宿主之间的缓存冗余，DAMON 加 balloon 回收 Guest 内部不再使用的页，叠加起来才有最低的整体内存消耗。

CPU 侧的问题换了形态。沙箱被分成延迟敏感型和尽力而为型，后者设 `SCHED_IDLE` 优先级，只有在没人用 CPU 时才跑。但只靠这个还不够：Linux 的兄弟超线程会共享执行单元，一个跑在兄弟核上的尽力而为任务，照样能拖慢延迟敏感任务。DSec 再叠一层 Linux core scheduling，禁止跨优先级占用兄弟超线程。效果是，在 50% 背景负载下，延迟敏感任务的延迟膨胀从 45.2% 压到 **17.3%**；而如果只用 `SCHED_IDLE`，改善最多 3.4%。剩下的退化来自睿频降低、内存带宽和末级缓存争抢，core scheduling 覆盖不到，论文认为已在可接受范围。

当整个集群的利用率超过 80%，DSec 还会把一部分负载甩到云上。它提前准备约 30TB 的去重 EROFS 镜像集，按生产访问 trace 估算能覆盖约 70% 容器任务的文件依赖，单生产单元用 200 台云 VM 就能吸收约 30% 的峰值。

## GPU 可以被抢，Agent 的状态不能丢

环境、镜像、密度解决之后，还有一个和训练框架绑在一起的坑：抢占。

早期架构里，Agent 的推理循环和 GPU 训练任务跑在同一个 Pod 里。GPU 被抢占，执行循环就没了，虽然沙箱状态还在 DSec 上，但恢复只能靠重放命令日志来重建进度。问题是命令不都是幂等的，重放会制造重复写入这类副作用。

从 DeepSeek-V4.1 起，rollout 被拆了出来，分成两个都运行在可抢占 GPU 池之外的组件：**Agent sandbox** 托管脚手架和工具，提供真实的执行环境；**Worker container** 管理沙箱，维护 rollout 的控制状态。两者共同持有完整的 rollout 状态，成为唯一事实来源。GPU 任务被抢占后重新连上就能继续，不再需要靠日志重放，RL 框架里那套状态恢复逻辑也被拿掉了。

被抢占时的暂停与恢复对沙箱是透明的。Container 走 `docker pause` 冻结进程树，开启 swap，用 `memory.reclaim` 主动回收内存；恢复时用 `MADV_WILLNEED` 异步预取，再 `docker unpause`。microVM 则是保存内存和执行状态快照，直接终止 Firecracker 进程释放运行时内存，恢复时启动新进程加载快照。对上层而言，后续请求到达时沙箱会自动恢复再执行。

把有状态的 rollout 从可抢占的 GPU 上摘下来，是这一整套设计里最像「把一个训练框架的问题还原成一个系统问题」的一步。GPU 的节奏是「随时可能被打断」，Agent 的节奏是「状态必须连续」，两件事从架构上分开，各自的假设才站得住。

## Agent 会作弊，这是设计假设

论文专门用一章记录 Agent 在训练中自己发现的作弊手段。

沙箱内负责 Agent 与外界通信的组件叫 Chronus，它执行某些操作时会调用系统 bash。Agent 发现这一点后，**试图覆盖 `/bin/bash`**，把命令注入到后续的 shell 会话里，去截获题目答案或特权信息。它也试过直接向 Chronus 的套接字发送构造好的 RPC 消息来伪造用户请求，或者翻 Chronus 的日志找残留的答案。

文件级的读写和套接字访问控制上线之后，Agent 转向了更底层的手段。它用 `XFS_IOC_SWAPEXT` 这个 ioctl 把两个文件的底层数据块映射互换，让受保护的内容出现在自己持有的文件描述符上，绕过文件级访问控制。这个操作的副作用比作弊本身更危险：它损坏了 XFS 元数据，直接导致文件系统崩溃。

还有一类漏洞在沙箱之外。Agent 会扫描可达的端口和服务，找可访问的镜像源；通过 Go module proxy 从 GitHub 拉取代码；安装更新版本的软件包来获取现成的实现。这些行为从最终输出上很难发现，因为 Agent 确实把题做对了，只是手段不正当。论文的原话是，仅靠最终输出检查，无法可靠判断 Agent 是否按预期方式解题。

另外几起事故算不上蓄意，是普通命令和操作失误闯的祸：

- Agent 从根目录递归 grep，一路遍历到 `/proc/kpagecgroup`，触发内核 bug，把宿主机内核打崩；
- 在安全攻防任务里，本该发给目标虚拟机的攻击命令执行在了自己的容器里，同样打崩内核；
- 调用 `yes`，它异步记录的输出累积到几十 GB，把存储灌满。

防御是分层的：

1. **AppArmor** 控制文件读写权限和 Unix 域套接字访问，这些策略即使 Agent 在沙箱里以 root 运行也生效；
2. **eBPF**（extended Berkeley Packet Filter）负责网络层的细粒度管控，按每个沙箱下发程序，对 IP、端口、协议三重过滤，策略可以随任务阶段动态更新；
3. 用户隔离用来缩小资源尖峰或内核级故障的影响半径。

论文对这一点没有把话说满：

> 没有单一机制能防住所有 Agent 不当行为与系统故障。

它承认这些控制只覆盖了问题的一部分，对触发内核 bug 这类破坏行为给不出通用防御。整体姿态是隔离、观测、发现新问题、持续加固，而不是宣称已经解决。Agent 执行不可信在这套系统里是一个设计假设，不是一份待整改的事故清单。

## 写在最后

一台机器上的三千多个容器大部分时间闲着，反而是最难的部分，因为闲着的不是资源，是 CPU；钉着的是内存、状态和隔离边界。谁能在单位成本内造出更多可交互、可验证、可隔离的环境，谁的 Agent 就有更多试错次数。评估一家公司的 Agent 能力，除了看模型榜位，还要看它一天能跑多少沙盒、围栏能不能挡住预料之外的越狱路径。DSec 最有价值的贡献或许不是那 300 万这个数字，而是它把「Agent 会怎么搞坏系统」当成了必须先回答的问题。

这篇论文讲的是可交互、可验证、可隔离的训练环境，而它自己的全部规模数字都来自厂商自述。亮出的数字要打折扣，坏掉的方式往往更可信，因为后者是拿真实的崩溃换来的。

我们此前讲过应用层怎么用 checkpointer 做断点续跑，DSec 把这套思路下沉到了平台层：GPU 可抢占、Agent 有状态，这对节奏错位，正在成为基础设施默认要处理的假设，而不再是每个 Agent 框架自己实现的补丁。
