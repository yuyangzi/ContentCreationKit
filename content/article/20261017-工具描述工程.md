# Agent 工具描述工程：如何让模型选对工具

> **导读**：工具定义不是配置项，是 prompt。模型每次推理都要把 name、description 和参数 schema 读一遍，所以描述写得清不清楚，直接决定它选不选得对。2026 年的一批研究把这件事量化了：修好描述，工具选择准确率能涨十几个百分点。但同一年另一项注意力研究给出了更难消化的事实，模型有八成时候已经把注意力落在正确工具上，最后还是选错了，而描述能挽回的失败不到四分之一。
>
> 工具被写出来的那一刻，是幻觉检测和路由问题的上游。

---

## 一句给新员工的交接文档

Anthropic 在那篇讲工具设计的工程博客里给过一个判断标准：写工具描述时，想象你要把这个工具讲给一个刚入职的同事听。

这个比喻好用，是因为它指向了一个容易被忽略的事实。工具定义在 API 调用时会被序列化成文本，和 system prompt、用户消息一起挤进同一段 token 流。模型看不到"结构化的对象"，它读到的是一段文本。

> "Tool definitions and specifications should be given just as much prompt engineering attention as your overall prompts."
> Anthropic《Building Effective AI Agents》，2024 年 12 月

说白了，description 不是文档，是 prompt。文档写给同行看，允许有默认共识；prompt 写给一个只会照字面理解的协作者看，它默认什么都不懂。你脑子里那些"这还用说吗"的上下文，对模型来说就是黑箱。工具的命名、描述、参数说明，三者合起来是模型判断"该不该调、调哪个、传什么"的全部依据。

## 一个反直觉的注意力实验

如果描述工程真这么关键，那描述写到极致，大多数选错工具的问题应该能解决。2026 年 6 月那篇《Looking Is Not Picking》（arXiv:2606.16364）给出的数据恰好相反。

研究者做了一件很细的事。他们不看模型最终调了哪个工具，而是逐段看模型对每个工具定义的注意力分布。结论是：按每个候选的注意力 argmax（取注意力最强的那一段）统计，模型有 80% 的时候注意力落在正确工具上，随机基线只有 21%。

换句话说，大多数时候模型已经"看到"了该用的工具。但它还是选错了。

研究者接着做了干预实验，把修复分成两侧。输入侧的修复，也就是重排工具顺序或者把正确的工具定义复制一遍，最多只能挽回 23% 的失败。输出侧的干预，不管是在注意力 logit 上加一个偏置，还是在残差流上放一个 steering vector，都能挽回 59% 到 91%。两种完全不同的表示方法，挽回的是同一批失败，per-task Jaccard 达到 0.865。

结论指向：**瓶颈更可能不在"模型没看到"，而在"模型看到了却没选"那一层。**

这条结论限制了描述工程的作用范围，但方向很清楚。描述改善的是工具的可辨识性，也就是让正确的那个工具在文本上更容易被认出来；它主要管不了决策层的置信度，也就是模型在最后一步凭什么押注。输入侧修复能挽回的那 23%，正属于可辨识性这一层的失败；剩下的七成多，是模型看到了却没选。把这两件事混为一谈，正是很多团队反复调描述却收效有限的原因。

## 描述仍然值得写，只是要放回边界内

收益是真的，前提是把它放在边界之内看。2026 年 2 月，三篇论文几乎是连着发的，它们做的是同一件事：把"描述写得好不好"从主观判断变成可测量的变量。

先看规模最大的一篇。《From Docs to Descriptions》（arXiv:2602.18914）把软件文档的成熟做法和 agent 的工具使用需求糅成一套四维质量标准，准确性、功能性、信息完整性、简洁性，下面挂 18 类具体问题，然后在 10,831 个 MCP（Model Context Protocol，模型上下文协议）server 上跑了一遍。结果里有两个数字：73% 的 server 存在工具重名，而且大量工具的参数字义写错或者根本没写返回值。研究把这套现象总结成一个词，叫 "code-first, description-last"，意思是先把代码写好，描述最后凑两笔交差。

更关键的是修复收益。研究者用受控的方式给描述"植入"和"修复"问题，发现功能性维度的修复让工具选择准确率提升 11.6%，准确性维度提升 8.8%（p < 0.001）。在多个功能等价的 server 互相竞争的设定下，达到标准的描述获得 72% 的选择概率，基线只有 20%。

另一篇《MCP Tool Descriptions Are Smelly!》（arXiv:2602.14878）把镜头拉近。它抽查 103 个 server 上的 856 个工具，发现 97.1% 的描述至少踩中一种"异味"。把描述按六种组件补全之后，任务成功率中位数提升 5.85 个百分点。但同一组实验也给出了代价：执行步骤多了 67.46%，还有 16.67% 的场景性能反而退化。

两篇论文合起来给了一个平衡的结论。描述工程的收益是真的，但它有代价，也有边界。收益来自"让模型更容易认出对的那个"，代价是它往上下文里塞了更多 token、更多步骤；边界则是上一个实验说的，它基本够不着决策层。

边界之内的写法，可以从四件事入手。

---

## 写法一：先把名字起对

描述工程里最先该动的不是句子，是名字。名字是模型最早、也最省 token 的一眼。

Anthropic 的建议是按服务加前缀，`asana_search`、`jira_search`，跨 server 时再用资源细分，`asana_projects_search`、`asana_users_search`。这么做不只是为了整齐，而是把"这个工具属于哪个域"编码进了名字本身，模型在候选里扫一眼就能过滤。前缀还是后缀（`github_list_prs` 还是 `list_prs_github`）的差别并不小，而且随模型变化，所以别照抄，用自己的评测集选。

参数名同理。Anthropic 给的原话是把 `user` 换成 `user_id`，多一个后缀，消掉的是一个宽度很大的歧义。MCP 规范对工具名给了一组建议约束，1 到 128 个字符，大小写敏感，只允许字母、数字、下划线、连字符和点号，同一个 server 内唯一。这些是底线，不是设计。

真正制造麻烦的是近义词并存。同一个注册表里 `get_user`、`fetch_user`、`retrieve_user_profile` 三个都在，模型就得花注意力去分辨它们的差别，而它们大概率做的是同一件事。Anthropic 在另一个案例里用的是 `notification-send-user` 和 `notification-send-channel`，两个名字都对、都清楚，但模型选错的时候分不清该走哪个。这类冲突的修法不是改描述，是合并或者删掉冗余工具。

## 写法二：每一段描述都在回答四个问题

名字定完，才轮到 description。Anthropic 官方给的模板可以压缩成四问：

1. 这个工具做什么
2. 什么时候该用
3. 什么时候**不该**用，包括它不返回什么
4. 每个参数是什么意思，会怎样影响行为

第三问是大多数团队会跳过的一问，也是收益最直接的一问。Anthropic 官方文档里的好例是 `get_stock_price`，它除了说清功能和参数，还专门补了一句"不会提供关于该股票或公司的其他任何信息"。这一句是在替模型划边界，防止它把股价工具当成万能查询入口。官方文档对长度的要求是一句很朴素的话，每个工具描述至少 3 到 4 句，复杂的工具更长。

```JSON
{
  "name": "get_stock_price",
  "description": "Retrieves the current stock price for a given ticker symbol. The ticker symbol must be a valid symbol for a publicly traded company on a major US stock exchange like NYSE or NASDAQ. The tool will return the latest trade price in USD. It should be used when the user asks about the current or most recent price of a specific stock. It will not provide any other information about the stock or company.",
  "input_schema": {
    "type": "object",
    "properties": {
      "ticker": {
        "type": "string",
        "description": "The stock ticker symbol, e.g. AAPL for Apple Inc."
      }
    },
    "required": ["ticker"]
  }
}
```

差描述大概是另一副样子：一句 "Gets the stock price for a ticker."。信息量看着差不多，但它把"什么算合法的 ticker""返回什么货币""什么时候用"全留给了模型猜。四段式的价值不在于长，而在于把那些你默认存在的上下文显式写出来。

## 写法三：别让模型猜参数

第三个误区是把 description 和 schema 当成一回事。分工其实很清楚，描述管发现，schema 管校验。该写进 schema 的约束，塞进描述文本里是浪费；该写在描述里的场景，藏在 schema 里模型也看不见。

参数上的防呆有几条现成的做法：

1. 必填的字符串参数，尽量配 enum、pattern、example 或 default 之一，让取值空间收窄
2. 参数名具体化，`user_id` 而不是 `user`，`repo_name` 而不是 `repo`
3. 用 `strict: true` 配 `additionalProperties: false`，让调用严格贴合 schema，多余字段直接拒绝
4. 每个参数在 description 里给一句 example，比如 "The stock ticker symbol, e.g. AAPL for Apple Inc."

Anthropic 把这个思路叫 poka-yoke，防呆。他们在 SWE-bench 上做过一个具体的改动，把文件编辑工具里的相对路径改成强制绝对路径，模型的使用就从偶发出错变成了基本不出错。参数设计的目标不是给模型自由，是让它更难犯错。反过来看，参数层面的错误在工具调用失败里占了不小的比重，所以这一块的投入回报通常比抠描述文本更高。

## 写法四：长度是成本，不是美德

长度有代价，分显性和隐性两面。

显性的一面是 token。Anthropic 提过，工具定义加上工具返回值，有时在 agent 读到用户请求之前就已经吃掉 50,000 以上的 token，而这些 token 每次请求都要重新读一遍。EASYTOOL（arXiv:2401.06201）做过一组对照，把冗长的工具文档压缩成统一格式的简洁指令，在 ToolBench 上平均 token 从 2530 降到 748，砍掉七成，成功率不降反升。压缩之所以有用，是因为原文里有大量噪声：同一个概念在两个工具里描述不一致、参数说明重复、使用场景缺失。

代价还有隐性的一面。《MCP Tool Descriptions Are Smelly!》那组实验里，把描述按六种组件全量补全，执行步骤涨了 67.46%，16.67% 的场景反而退化。多出来的描述给了模型更多决策依据，也给了它更多犹豫的理由。

所以长度该按工具复杂度分档。简单的工具几十个词就够，典型工具一百词上下，复杂工具两百词，再往上就要考虑是不是该拆工具，或者把细节链到外部文档。比长度更值得做的是合并，Anthropic 举的例子是 `create_pr`、`merge_pr`、`review_pr` 三个工具，功能上有依赖、名字上又像，合成一个带 `action` 参数的工具，选择歧义直接消失。**判断工具该不该合并的标准很简单，如果模型必须懂顺序才知道用哪个，那多半该合。**

## 两个顺手该做的细节

有两件事放在写法之外，但没做就有隐患。

**示例是有条件的。** Anthropic 提供了 `input_examples` 字段，把 schema 校验过的调用示例挂上去。它在"两个工具很像、需要举例消歧"的场景里最有用，对那种单参数、格式标准的工具几乎没用。有一条反直觉的提醒来自 OpenAI 官方文档，给推理模型加示例可能反而损害性能。所以示例不是多多益善，是看工具有没有歧义要消。

**质量门禁可以自动化。** 描述质量已经有了可以挂进 CI 的静态检查，社区工具 mcp-assert 这类 linter 会盯着几个信号，描述过短或过长、两个工具描述相似度超过八成、单个工具定义超过一千 token、一个 server 暴露超过二十个工具。这些阈值是社区经验，不是官方标准，但先拦住明显有问题的描述，比人肉评审划算得多。

## 描述够不着的地方

回到开篇那个实验。描述写得再好，也只能改善工具在文本上的可辨识性，决策层选不选得对，是另一套机制。这一层认识决定了描述工程的投入优先级：先写对，再用自动化守住，然后接受它够不着的那部分，把剩下的交给选择本身。

有一类问题比选错工具更隐蔽。2026 年 2 月的《Don't believe everything you read》（arXiv:2602.03580）分析了 10,240 个 MCP server，发现约 13% 的描述与代码实现存在实质不一致，也就是说描述说的和工具实际做的不是一回事。模型据此建立的"心智模型"从一开始就是错的，写得再规范也救不回来。这已经越过了描述工程的边界，进入审计和信任的范畴。

还有一个正在发生的转折。Anthropic 的 Tool Search 把工具定义变成按需加载，同一段 description 因此有了第二个身份，它既是给模型看的 prompt，也是给检索器用的索引。写法要求跟着变了，关键词和同义词的权重上升，因为这段文本现在要先过一遍 BM25 或者向量检索。研究侧也在同步，2026 年 2 月的 Trace-Free+（arXiv:2602.20426）用课程学习自动改写工具描述，在候选工具扩到 150 个以上时把准确率退化降低了 29.23%。写描述这件事，正在从纯手工变成有人替你草拟、你来把关。

---

Anthropic 那个"讲给新员工听"的比喻，真正有用的地方不在比喻本身，而在它点出的那个落差。写描述的人默认对方什么都懂，读描述的是一个什么都不懂的模型，中间那段被省略的上下文，就是出错的温床。把这个落差填上，能拿回不少失败；但填完之后会发现，还有一层瓶颈不在文本里，在模型最后拍板的那一刻。描述工程能做到的，是让正确的工具不被埋没；至于模型为什么看着它还是走开，那是另一个还没有标准答案的问题。
